# Research Agents Rent the Index, Then Read

No mainstream assistant, Codex included, turns the internet into a local vector database. Codex's web search tool answers by default from **"an OpenAI-maintained index of web results"** on OpenAI's servers ([Codex config basics](https://learn.chatgpt.com/docs/config-file/config-basic)), and its open-source harness contains no embedding or code index of any kind; it searches your repository by running `rg` in a sandboxed shell ([openai/codex](https://github.com/openai/codex)). Every other product follows the same template. An LLM rewrites the request into many short keyword queries, sends them to a hosted web index that someone else spent decades and billions building (Google for Gemini, Bing for Copilot, a mix of OpenAI's own index and scraped Google for ChatGPT, Brave and possibly newer providers for Claude, its own index for Perplexity), fetches a handful of chosen pages at query time, shrinks them before they enter the context window, loops until it judges the evidence sufficient, and then writes a cited answer. The premise needs one correction in the other direction, though: embedding the whole indexed web is *not* impossible. At web scale the vectors themselves cost about **$5 million of GPU time and 13 TB to 3.3 PB of storage** by this report's estimate, and Bing, Exa, Perplexity and OpenAI already keep vector indexes server-side as one layer of hybrid engines. The expensive, hard parts are the crawl, spam fighting, freshness and the ranking signals learned from links and billions of clicks. Quality therefore comes from two places: ranking evidence inherited from the search engine, and inference spent persistently, since token usage alone explains **80% of performance variance** on a hard browsing benchmark in Anthropic's tests ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). That design is *index-light and inference-heavy*. The typed databases and searchable knowledge bases in the user's earlier research are the reverse: *index-heavy and inference-light*. They pay at ingestion to get exactness, stable provenance, permissions and determinism, which are precisely the things independent audits find web research agents lack. Citation links are valid more than 94% of the time, yet only **39–77% of cited claims are supported** by their source ([Cited but Not Verified](https://arxiv.org/abs/2605.06635)), and ten identical runs of one commercial agent shared **under 2% of their citations** ([Pykälä & Kaski](https://arxiv.org/abs/2610.26421)). The practical conclusion is that the user's data lake should not imitate web research. It should become the exact, citable evidence backend that those research agents already know how to call.

*Evidence base.* This report synthesizes five research tracks: web search infrastructure, deep research agents, coding-agent retrieval, reading/synthesis/citation, and search quality signals. Their manifests contain 470 entries, which reduce to **429 distinct sources** (247 papers and 182 web sources such as documentation, engineering blogs, court records and pricing pages) after de-duplicating by arXiv ID, DOI and normalized URL. The combined source catalog for this project lives in `papers/README.md` and `papers/manifest.csv`. PDFs are kept locally only, because many licenses forbid redistribution, and are rebuilt by passing the research-notes folders (including this one, `research_notes/How AI research agents retrieve information`) to `scripts/download_papers.py`. Labels used throughout: **confirmed** means the operator documents it; **reported** means journalism, court testimony or strong third-party inference; **reverse-engineered** means traffic or code analysis the vendor has not confirmed; **vendor-reported** means a company measured its own product; **independent** means a third party measured it. Many 2026 sources are unreviewed arXiv preprints. Status is as of November 2026.

## Nobody embeds the web locally; every product queries a hosted index

### Codex has two unrelated retrieval mechanisms, and neither is a local vector store

"Codex retrieval" splits cleanly in two. For **code**, Codex lets a model trained with reinforcement learning run shell commands in a sandbox. Its prompts say "prefer using `rg` or `rg --files` respectively because `rg` is much faster than alternatives like `grep`." The tool-handler directory holds a shell runner, `apply_patch`, planning, image viewing, MCP handlers, multi-agent handlers and `tool_search`, and no dedicated read-file, grep or semantic-search tool. A search of the Rust source for embedding or vector-store code finds none. The only ranking-based retrieval in the harness is `tool_search`, which uses the Rust `bm25` crate to search *connector and tool metadata* so that tool definitions load on demand. The `codex-file-search` crate is a fuzzy *filename* finder for the UI's @-file picker ([openai/codex](https://github.com/openai/codex)). Persistent project knowledge arrives as concatenated `AGENTS.md` files, walked from the git root to the working directory and capped at **32 KiB** by default ([Codex AGENTS.md guide](https://learn.chatgpt.com/docs/agent-configuration/agents-md.md)). Long sessions survive through server-side compaction and a local "handoff summary" prompt ([openai/codex](https://github.com/openai/codex); [OpenAI: Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop)).

For the **web**, Codex calls a hosted Responses-API `web_search` tool with four modes. `cached` is the default and "serves results from a web search cache … an OpenAI-maintained index of web results … cached mode returns pre-indexed results instead of fetching live pages." `indexed` permits external access only when the search index gates the request. `live` fetches current pages and becomes the default under `--yolo` or other full-access sandboxes. `disabled` turns search off ([Codex config basics](https://learn.chatgpt.com/docs/config-file/config-basic)). OpenAI justifies the cached default partly on security grounds: it "reduces exposure to prompt injection from arbitrary live content", and the docs add "Treat web results as untrusted" ([Codex web search docs](https://learn.chatgpt.com/docs/web-search)). Cloud Codex goes further and blocks internet access during the agent phase by default, allowing it only for setup scripts or optional allowlists ([Codex cloud internet access](https://learn.chatgpt.com/docs/cloud/internet-access)). So the user's intuition is correct about the client: nothing on the user's machine embeds the web. It is wrong only about the industry, because OpenAI maintains exactly such an index server-side.

### Embedding the indexed web costs single-digit millions, and several companies already do it

The intuition that "embedding the internet is impossible" fails on the numbers. Bing had encoded "more than 150 billion" items as vectors and could search "100 billion-plus vectors … in 5 milliseconds" by 2019 ([The Register](https://www.theregister.com/2019/05/15/bing_algorithm_github/)). Its 2026 Web IQ service extends DiskANN "into a distributed retrieval fabric" over disk-resident vector spaces ([Bing blog](https://blogs.bing.com/search/June-2026/Announcing-Microsoft-Web-IQ)). Exa embeds tens of billions of pages. It truncates 4096-dimension Matryoshka embeddings to 256 dimensions, binary-quantizes them to one bit per dimension, clusters documents into 100,000 IVF cells, and reranks the top candidates with uncompressed vectors. Exa keeps **inverted indexes for filters** such as date, domain and keyword ([Exa vector DB blog](https://exa.ai/blog/building-web-scale-vector-db)). Perplexity indexes every document as text *and* vectors ([Vespa blog](https://blog.vespa.ai/perplexity-builds-ai-search-at-scale-on-vespa-ai/)). Reverse engineering found approximate-nearest-neighbor search inside ChatGPT's shopping index ([Peec AI](https://peec.ai/blog/chatgpt-built-its-own-search-index)). The building blocks are mature. DiskANN indexes one billion vectors on a single workstation with 64 GB of RAM plus SSD at under 3 ms mean latency ([Subramanya et al. 2019](https://proceedings.neurips.cc/paper_files/paper/2019/file/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Paper.pdf)), and FreshDiskANN sustains thousands of real-time inserts and deletes per second ([Singh et al. 2021](https://arxiv.org/abs/2105.09613)).

The estimate below is this report's own arithmetic, not a vendor figure. It assumes about 1,000 tokens of extracted main text per page, and every result scales linearly with that assumption. The cited inputs are an embedding throughput of about **45,000 tokens per second per H100** for an 8B embedding model ([Tensor Economics](https://www.tensoreconomics.com/p/why-are-embeddings-so-cheap)), API pricing of $0.02 per million tokens for text-embedding-3-small ([OpenAI pricing](https://developers.openai.com/api/docs/pricing)), Google's 2020 testimony of about 400 billion indexed documents ([Zyppy](https://zyppy.com/seo/google-index-size/)), and Google's statement that its index is "well over 100,000,000 gigabytes" ([How Search Works](https://www.google.com/search/howsearchworks/how-search-works/organizing-information/)).

| Scale | Embedding compute | Vectors, 4096-dim fp16 | Vectors, 256-bit binary (Exa-style) |
|---|---|---|---|
| 10B pages (Exa or ClueWeb22 scale) | ~62k H100-hours ≈ **$120k** (≈$200k via API) | ~82 TB | ~320 GB |
| 400B pages (Google 2020 scale) | ~2.5M H100-hours ≈ **$5M** (≈$8M via API) | ~3.3 PB | ~13 TB |
| 400B pages × 5 passages | ≈ $25M | ~16 PB | ~64 TB |
| Freshness: ~1.5B page updates/day | ~9k H100-hours/day, about **400 H100s running continuously** | — | — |

Even the most generous row is smaller than the text index it would sit beside. The freshness row, derived from Perplexity's "tens of thousands of index update requests" per second ([Perplexity Search API](https://www.perplexity.ai/hub/blog/introducing-the-perplexity-search-api)), shows that re-embedding is an ongoing operating cost, not a one-off. Managed services price that cost steeply. Vector search over 3 billion image embeddings cost about **$99k per month** as a static index on Vertex AI, **$1.5M per month** with daily streaming updates and **$37.2M per month** with hourly updates ([GDELT Project](https://blog.gdeltproject.org/ai-in-production-a-deep-dive-into-the-costs-of-multimodal-embedding-search-over-3-billion-images/)). The real barrier sits around the vectors. One Common Crawl snapshot of 2.14 billion pages is 360 TiB uncompressed ([Common Crawl](https://commoncrawl.org/blog/august-2026-crawl-archive-now-available)). Kagi likens building an index to "building a parallel national railroad" and cites about $100 billion of Microsoft spending on Bing over 20 years ([Kagi](https://blog.kagi.com/waiting-dawn-search)).

Vectors alone also retrieve badly, which is why nobody ships a pure vector web index. A Google DeepMind result shows that the number of top-k subsets a single-vector embedder can return is bounded by its dimension, and "even state-of-the-art models fail" on the simple LIMIT dataset ([Weller et al. 2025](https://arxiv.org/abs/2508.21038)). Across 18 zero-shot BEIR datasets, "BM25 is a robust baseline" and dense retrievers often generalize worse ([Thakur et al. 2021](https://arxiv.org/abs/2104.08663)). Perplexity left a vector-database approach because "vector databases could not reliably support even simple boolean filters" ([Vespa case study](https://vespa.ai/case-studies/why-perplexity-chose-vespa-for-ai-search/)). Every serious web engine is therefore hybrid: an inverted index for exact terms, filters and identifiers; dense ANN as an extra candidate path; and a cross-encoder reranker over the few hundred merged candidates. That is the same stack the user's knowledge-base research recommended, at a different scale.

## One pipeline runs from fan-out to citation in every product

### The seven stages

Every mainstream system, whether chat search, a coding agent's web tool or a 30-minute deep research run, implements the same pipeline. The products differ in how many times they loop, how they compress, and whether the loop is learned or prompted.

```
 USER PROMPT
     │
 [1] CLARIFY / PLAN ........ ChatGPT clarifier model; Gemini editable plan; Claude lead saves plan to memory
     │
 [2] REWRITE + FAN-OUT ..... 2–5-word keyword queries (Copilot); 1–3 → 20+ (ChatGPT); ~80–160 (Gemini Deep Research)
     │  many short queries, often in parallel
     ▼
 [3] HOSTED INDEX (remote) . Google | Bing | OpenAI index + scraped Google | Brave | Perplexity | Exa
     │   crawl → dedup/spam filter → inverted index (+ vectors) → shards, tiers, caches
     │   cheap candidates (BM25/dense) → link, click, freshness, spam signals → neural rerank
     ▼   returns ~10 URLs + snippets (or passages / "evidence objects") per query
 [4] SELECT / RERANK (LLM) . choose what to open; source priors; domain allow/block lists; dedupe
     │
 [5] FETCH + READ JIT ...... HTTP fetch (cached) → HTML/PDF → text → truncate | code-filter |
     │                        query-time chunk scoring | goal-conditioned summary → notes; clear raw text
     ▼
 [6] REFLECT / ITERATE ◄──── gaps? contradictions? budget left?  (RL-trained persistence,
     │        └──────────────► back to [2]                       parallel subagents, compaction)
     ▼
 [7] SYNTHESIZE + CITE ..... write after research; span-level url_citation / cited_text,
                             or a post-hoc CitationAgent pass
```

| Stage | What happens | Typical mechanism | Where it breaks |
|---|---|---|---|
| 1. Clarify and plan | Turn a vague prompt into a brief or plan | Intermediate clarifier model (ChatGPT); user-editable plan (Gemini); research brief (LangChain) | Underspecified queries make agents "rely more on their learned prior" ([UNDERSPEC-DR](https://arxiv.org/abs/2610.39413)) |
| 2. Rewrite and fan out | Many short keyword sub-queries | LLM query writing; RL-trained query policies | Sub-queries decide which pages can be cited at all |
| 3. Hosted index | Retrieve candidates and rank them | Inverted index plus dense ANN, link and click signals, rerankers | Coverage limits, licensing, SEO spam |
| 4. Select | Choose which results to open | LLM reranking with priors | Position and recency bias; shallow credibility judgment |
| 5. Fetch and read | Turn pages into compact evidence | Fetch, extract, filter, summarize | No JavaScript, paywalls, syndicated copies, context rot |
| 6. Iterate | Decide whether to search again | Learned or prompted loop, subagents | Early findings bias later queries; hand-off loss |
| 7. Synthesize and cite | Write report, attach sources | Span annotations or post-hoc citation | Valid links that do not support the claim |

### Stage 2: the LLM's real job is writing many short queries

The first piece of "intelligence" is query writing. Microsoft documents that Copilot "parse[s] the user's prompt and identifies terms" and sends Bing "a few words informed by the user's prompt" ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-365/copilot/manage-public-web-access)). A reverse-engineering study found ChatGPT's standard mode running one to three parallel searches and thinking modes running more than 20, with recency parameters of 7, 30 or 365 days, fused by reciprocal rank fusion ([RESONEO](https://think.resoneo.com/chatgpt/)). Google says AI Mode works by "breaking down your question into subtopics and issuing a multitude of queries simultaneously", and Deep Search "can issue hundreds of searches" ([Google blog](https://blog.google/products/search/google-search-ai-mode-update/)). Fan-out works because each narrow sub-query lets the search engine's own ranking operate on a short, well-posed query of the kind it was tuned on. The effect is large. An independent 90-day study of 158,099 ChatGPT answers found that "every page ChatGPT cites is one its own search retrieved". Which pages that search returned, for sub-queries that "rarely coincide with Google's or Bing's results", explained **32% of citation variance against 2.8% for page properties** ([Chen & Koudas 2026](https://arxiv.org/abs/2610.15033)). The model also "writes brands it knows into its searches", so its prior knowledge shapes what it can find.

Query rewriting has limits that matter for private corpora. Pseudo-document expansion such as Query2doc improves BM25 by 3–15% ([Wang et al. 2023](https://arxiv.org/abs/2303.07678)), and HyDE's hypothetical answers help unsupervised dense retrieval ([Gao et al. 2022](https://arxiv.org/abs/2212.10496)). A study of 11 expansion methods across 24 retrievers, however, found "a strong negative correlation between retriever performance and gains from expansion"; expansion "generally harms stronger models" ([Weller et al. 2023](https://arxiv.org/abs/2309.08541)). Learned strategies beat prompting. Search-R1 trains a model with outcome-only reward to issue multiple queries during reasoning and improves 41% over RAG baselines at 7B ([Jin et al. 2025](https://arxiv.org/abs/2503.09516)). DeepRetrieval RL-trains query generation against real search engines and SQL databases ([Jiang et al. 2025](https://arxiv.org/abs/2503.00223)). The practical prompt lesson is Anthropic's: agents defaulted to overly long, specific queries, and the fix was to "start with short, broad queries, evaluate what's available, then progressively narrow" ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)).

### Stage 3: a web index is a sharded, tiered, cached inverted index with neural reranking on top

A web engine is a crawl-and-index pipeline feeding a sharded, replicated, mostly in-memory inverted index, with caches in front and multi-stage ranking on top. The architecture has been stable since the early 2000s. Google's 2003 design split the index into shards, each holding a random subset of documents with a pool of replicas. A query "reads hundreds of megabytes of data and consumes tens of billions of CPU cycles", and a second phase fetches titles and snippets from document servers ([Barroso, Dean & Hölzle 2003](https://static.googleusercontent.com/media/research.google.com/en//archive/googlecluster-ieee.pdf)). Between 1999 and 2009 Google grew about 100x in documents while update latency fell "from months to minutes". Result and snippet caches had "hit rates typically 30–60%" ([Dean, WSDM 2009](https://static.googleusercontent.com/media/research.google.com/en//people/jeff/WSDM09-keynote.pdf)). Freshness came from incremental processing. Percolator cut the average age of documents in results by about 50% ([Peng & Dabek 2010](https://www.usenix.org/legacy/event/osdi10/tech/full_papers/Peng.pdf)), and court findings describe an index tiered by "how fresh it needs to be", where "the fresher tiers are rebuilt more frequently" ([U.S. v. Google, Mehta opinion](https://storage.courtlistener.com/recap/gov.uscourts.dcd.223205/gov.uscourts.dcd.223205.1033.0_3.pdf)).

Neural models were layered onto this structure rather than replacing it. Google lists RankBrain, neural matching, BERT, passage ranking, freshness systems, deduplication, site diversity and SpamBrain among its ranking systems ([Google ranking systems guide](https://developers.google.com/search/docs/appearance/ranking-systems-guide)). Bing applied transformer models to "every Bing search query globally" from 2019, serving more than a million BERT inferences per second on 2,000+ GPU VMs ([Azure blog](https://azure.microsoft.com/en-us/blog/bing-delivers-its-largest-improvement-in-search-experience-using-azure-gpus/)). Perplexity's public description of an AI-first index is the most detailed. An ML model predicts which URLs deserve indexing and a second schedules recrawls under a fixed budget. Learned models keep authoritative documents in hot tiers. Documents are split into "self-contained spans" scored individually. Lexical and dense retrieval run together, stale content is prefiltered, and cross-encoders rerank the survivors. Perplexity reports a p50 latency of 358 ms (vendor benchmark) ([Perplexity Research](https://www.perplexity.ai/hub/blog/architecting-and-evaluating-an-ai-first-search-api)). Indexes built for agents are moving from blue links to passages. Microsoft's Web IQ returns "structured evidence objects" ([Bing blog](https://blogs.bing.com/search/June-2026/Announcing-Microsoft-Web-IQ)), DeepSeek returns `authority` and `rerank_score` fields ([DeepSeek API](https://api-docs.deepseek.com/guides/search/)), and Firecrawl runs typed vertical indexes for research, developer and government content ([Firecrawl](https://docs.firecrawl.dev/features/search)).

### Stage 4: the LLM adds a second, biased ranking layer

The model then decides what to open. LLMs are strong zero-shot rerankers. Listwise RankGPT is "competitive, even superior" to supervised rerankers ([Sun et al. 2023](https://arxiv.org/abs/2304.09542)), and open 7B models such as RankZephyr match GPT-4 ([Pradeep et al. 2023](https://arxiv.org/abs/2312.02724)). The same layer carries biases. Listwise ranking depends on input order, and shuffle-and-aggregate improves it by 7–18% ([Tang et al. 2023](https://arxiv.org/abs/2310.07712)). Fake recent dates shift items by up to 95 ranks ([Fang et al. 2025](https://arxiv.org/abs/2509.11353)). LLMs judge credibility mostly by topical relevance, "largely ignoring stylistic features that humans find important such as whether a text contains scientific references" ([Wan, Wallace & Klein 2024](https://arxiv.org/abs/2402.11782)), and their preference for institutional sources "can be reversed by simply repeating information from less credible sources" ([Schuster et al. 2026](https://arxiv.org/abs/2601.03746)). The resulting citations depart from the engine's ranking. Nearly **30% of domains cited by Google's AI Overviews do not appear in the co-displayed organic results** ([Xu, Iqbal & Montgomery 2026](https://arxiv.org/abs/2605.14021)). Across ten AI search platforms, the top 20 domains capture 20.5–70.8% of each platform's citations ([Liu et al. 2026](https://arxiv.org/abs/2610.11932)). Products now expose domain control as a feature: OpenAI allows up to 100 allowed or blocked domains ([OpenAI web search guide](https://developers.openai.com/api/docs/guides/tools-web-search)), and Claude has `allowed_domains` and `blocked_domains` ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)).

### Stage 5: fetch a few pages and shrink them just in time

Reading is cheap infrastructure, not an index. Vendor fetch tools are mostly server-side HTTP fetchers with caches. Anthropic's `web_fetch` returns full text or the raw PDF, "currently does not support websites dynamically rendered with JavaScript", caches results, and fetches only URLs that already appeared in the conversation ([Anthropic web fetch docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool)). Gemini's URL Context tool first checks "an internal index cache, which is optimized for speed" before fetching live ([Gemini URL context docs](https://aistudio.google.com/docs/url-context)). OpenAI's browsing models have `search`, `open_page` and `find_in_page` actions ([OpenAI web search guide](https://developers.openai.com/api/docs/guides/tools-web-search)). Pages are large. Anthropic estimates an average web page at about 2,500 tokens, a large documentation page at 25,000 and a research-paper PDF at **125,000** ([Anthropic web fetch docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool)). Extraction is imperfect even with the best open tools; Trafilatura's own benchmark puts it at 0.926 F1 for main-content extraction ([Trafilatura evaluation](https://trafilatura.readthedocs.io/en/latest/evaluation.html)).

So agents compress before reading. Anthropic calls this "just in time" context: agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.)" and load data at runtime, "Rather than pre-processing all relevant data up front" ([Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). The compression methods vary. Jina's DeepSearch splits four or five fetched pages per step into about 500-token chunks and scores them against the query in memory, "without a vector database" ([Jina AI](https://jina.ai/news/snippet-selection-and-url-ranking-in-deepsearch-deepresearch/)). That is query-time chunking, and it is the direct answer to how agents get vector-quality page reading without a global vector DB: a handful of pages yields only hundreds of chunks. Claude's dynamic filtering lets the model write code that filters results "before they reach the context window". Anthropic reports **about 11% higher accuracy with 24% fewer input tokens** on average, with BrowseComp rising from 45.3% to 61.6% for Opus 4.6 (vendor-reported) ([Claude blog](https://claude.com/blog/improved-web-search-with-dynamic-filtering)). Alibaba's WebSailor passes each page plus a "goal" to a summarizer model, so the agent sees only goal-conditioned summaries ([Li et al. 2025](https://arxiv.org/abs/2507.02592)). After reading, old tool results are cleared or compacted. Anthropic's context editing plus a memory tool improved an internal agentic-search eval by 39% and cut tokens 84% in a 100-turn web-search eval (vendor-reported) ([Claude blog](https://claude.com/blog/context-management)).

### Stage 6: the deep research loop is persistence, trained by RL

Deep research products run stages 2 to 5 many times. They differ in architecture, training and budget, but none of them builds its own corpus.

| System | Architecture | Training | Budget per task |
|---|---|---|---|
| **OpenAI deep research** | Single agent; o3 tuned for browsing, GPT-5.2-based since Feb 2026; clarifier model before the run | End-to-end RL on browsing tasks, graded by a chain-of-thought model on rubrics ([System Card](https://cdn.openai.com/deep-research-system-card.pdf); [Wikipedia](https://en.wikipedia.org/wiki/ChatGPT_Deep_Research)) | 5–30 min ([Sequoia podcast](https://sequoiacap.com/podcast/training-data-deep-research)); ~$1.8 per query measured by third parties ([DR Tulu](https://arxiv.org/abs/2511.19399)) |

| **Gemini Deep Research** | Editable plan, asynchronous task manager, self-critique passes | "Multi-step reinforcement learning for search" ([Google blog](https://blog.google/technology/developers/deep-research-agent-gemini-api/)) | ~80 queries, ~250k input tokens, $1–3; Max ~160 queries, ~900k tokens, $3–7 ([Gemini docs](https://aistudio.google.com/docs/deep-research)) |

| **Tongyi DeepResearch** (open) | 30B-A3B MoE; ReAct or "Heavy" parallel mode | Agentic pre-training, SFT, GRPO with pure 0/1 reward in simulated and cached environments ([arXiv 2510.24701](https://arxiv.org/abs/2510.24701)) | ≤128 tool calls, 128K context |

Training has converged on a recipe whose central ingredient is hard data. BrowseComp's 1,266 questions were written to be "inverted": hard to find, easy to verify. Human trainers gave up on 70.8% after two hours, and OpenAI's deep research model was trained on data built to teach this skill ([Wei et al. 2025](https://arxiv.org/abs/2504.12516)). Open systems generate such questions synthetically. WebSailor samples knowledge-graph subgraphs and obfuscates features such as dates ([arXiv 2507.02592](https://arxiv.org/abs/2507.02592)). They train first on teacher trajectories; OpenResearcher's SFT on 97,000 offline trajectories added 34 points on BrowseComp-Plus ([arXiv 2603.20278](https://arxiv.org/abs/2603.20278)). Then comes outcome-reward RL in simulated or cached search environments with 100+-call horizons. Long-form report tasks need rubric rewards instead. AI2's DR Tulu-8B, trained with evolving rubrics, averaged 65.6 across four long-form benchmarks against 64.9 for OpenAI deep research, at "almost three orders of magnitude" lower cost (author-reported) ([arXiv 2511.19399](https://arxiv.org/abs/2511.19399)). Short-answer RL agents generalize poorly to reports; Search-R1-7B scored 14.9 on the same benchmark average.

### Stage 7: citations are attached as spans or by a second pass

Citations come from three mechanisms. The first, from WebGPT onward, collects quotes while reading and writes only from them ([Nakano et al. 2021](https://arxiv.org/abs/2112.09332)). The second has the API return span-level pointers. OpenAI and Gemini attach `url_citation` annotations with start and end indices ([OpenAI web search guide](https://developers.openai.com/api/docs/guides/tools-web-search); [Gemini docs](https://aistudio.google.com/docs/google-search)), and Claude's search citations carry up to 150 characters of `cited_text` ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)). The third attaches citations post hoc: Claude Research's CitationAgent processes the documents and the finished report to "identify specific locations for citations" ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Writer design matters more than citation formatting. LangChain moved writing out of the parallel phase because parallel section-writing "produced disjointed reports" ([LangChain](https://www.langchain.com/blog/open-deep-research)). CLAIMWRITER extracts source facts, maps them to an outline and writes only from source-linked claims, which cut hallucination **2.6–4.5x** when swapped into three deep research frameworks ([Hayashi et al. 2026](https://arxiv.org/abs/2608.28643)).

## Quality comes from inherited ranking signals and persistent inference, not from vectors

The question "how do they get high-quality results" has a two-part answer, and neither part is a better embedding.

### The engine's moat is links, clicks and spam fighting

When an LLM calls a search API, the top ten results already encode evidence from outside the pages. Brin and Page saw the 1997 web as a ranking problem, not a coverage problem: "'Junk results' often wash out any results that a user is interested in" ([Brin & Page 1998](https://www.cs.uoi.gr/~tjortjis/google-white.txt)). Kleinberg made the structural point that matters most for private corpora: "there is no purely endogenous measure of the page that would allow one to properly assess its authority", while "hyperlinks encode a considerable amount of latent human judgment" ([Kleinberg 1999](https://www.di.ens.fr/~busic/mar/ref/auth.pdf)). Click data is now the bigger signal. The DOJ v. Google court found that Navboost "pairs queries and documents through memorizing user click data", trained on 13 months of data, and that "thirteen months of user data acquired by Google is equivalent to over 17 years of data on Bing". An internal Google document called user feedback "perhaps the central way that web ranking has improved for 15 years." Google's generalization models (RankBrain, DeepRank, RankEmbed) are themselves trained on that user data. LLM signals "did not replace Navboost and QBST" and are balanced against them, and Navboost can beat LLMs on freshness ([Mehta opinion 2024](https://storage.courtlistener.com/recap/gov.uscourts.dcd.223205/gov.uscourts.dcd.223205.1033.0_3.pdf)). The 2025 remedy treats this data as the moat, ordering Google to share index and user-interaction data with qualified competitors ([Search Engine Roundtable](https://www.seroundtable.com/google-monopoly-ruling-remedy-40041.html)). Spam fighting is the third inherited layer. Google's March 2024 update cut low-quality, unoriginal content in results by **45%** ([Google blog](https://blog.google/products/search/google-search-update-march-2024/)), though a year-long independent study still found all major engines "seem to lose the cat-and-mouse game that is SEO spam" on product reviews ([Bevendorff et al. 2024](https://gwern.net/doc/technology/google/2024-bevendorff.pdf)). Google states plainly that AI Overviews and AI Mode cite only pages that are "indexed and eligible to be shown in Google Search with a snippet", and that "All existing SEO fundamentals continue to be worthwhile" ([Google Search Central](https://developers.google.com/search/docs/appearance/ai-features)).

### The agent's contribution is query skill, persistence, filtering and verification

The second half of quality is bought with inference. The table ranks the measured drivers by strength of evidence.

| Driver | Evidence | Status |
|---|---|---|
| **Tokens and persistence** | On BrowseComp three factors explain 95% of variance; "token usage by itself explains 80%" ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). Accuracy "scales smoothly" with browsing compute ([Wei et al.](https://arxiv.org/abs/2504.12516)). Accuracy "improves predictably" with interaction depth ([MiroThinker](https://arxiv.org/abs/2511.11793)) | Vendor and author |
| **Base model strength** | "Upgrading to Claude Sonnet 4 is a larger performance gain than doubling the token budget on Claude Sonnet 3.7" ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)) | Vendor |
| **Query writing and fan-out** | Retrieved sub-query results explain 32% of citation variance vs 2.8% for page properties ([Chen & Koudas](https://arxiv.org/abs/2610.15033)); clue decomposition lifted BrowseComp-Plus from 83.1% to 90.5% ([Question's Gambit](https://arxiv.org/abs/2609.14412)) | Independent / author |
| **Filtering and context hygiene** | Dynamic filtering +11% at −24% tokens ([Claude blog](https://claude.com/blog/improved-web-search-with-dynamic-filtering)); context management alone moved Kimi K2.5 BrowseComp from 60.6% to 74.9% ([arXiv 2602.02276](https://arxiv.org/abs/2602.02276)) | Vendor |
| **Verification and selection** | Best-of-N on the model's own confidence adds 15–25% because BrowseComp is "easier to verify than to find" ([Wei et al.](https://arxiv.org/abs/2504.12516)); a rubric reviewer (Critique) gave +7.0 on DRACO ([Microsoft](https://techcommunity.microsoft.com/blog/Microsoft365CopilotBlog/introducing-multi-model-intelligence-in-researcher/4506011)) | Vendor |
| **Parallel subagents** | Up to 90% less wall-clock time ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)); gated isolation of peers lifted BrowseComp-Plus from 74.5% to 82.6% ([ArcticSwarm](https://arxiv.org/abs/2609.01870)); but "flat is optimal for yield" and only 0.7–11.3% of production sessions are worth delegating ([Decomposition Buys Integrity](https://arxiv.org/abs/2609.17464)) | Mixed, mostly author |
| **Source-quality heuristics** | Early agents "favored SEO-optimized content farms" until prompts added source-quality heuristics ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)) | Vendor |

Two findings complicate the "just spend more" story. More retrieval does not produce more faithful citations: fact-check accuracy of citations "drops by approximately 42%" as tool calls scale from 2 to 150 ([Cited but Not Verified](https://arxiv.org/abs/2605.06635)). Short-answer benchmarks are also close to saturation. BrowseComp went from **51.5% for the first deep research model in April 2025** ([Wei et al.](https://arxiv.org/abs/2504.12516)) to roughly 86–92% for frontier systems by late 2026 on aggregator figures that mix harnesses and attempt counts ([BenchLM](https://benchlm.ai/benchmarks/browsecomp)). Long-form and breadth benchmarks remain far from solved. On Mind2Web 2 the best system reached 0.54 partial completion against 0.79 for humans ([arXiv 2506.21506](https://arxiv.org/abs/2506.21506)). On WANDR, built from product logs, the strongest of six production systems scored only **0.363 soft F1** at enumerating target sets ([arXiv 2608.14747](https://arxiv.org/abs/2608.14747)). In ResearchRubrics, "implicit reasoning and synthesis jointly account for 45-50% of all failures" ([arXiv 2511.07685](https://arxiv.org/abs/2511.07685)). The frontier problem has moved from *finding* to *handling evidence*: completeness, faithful attribution and stable answers.

## Coding agents abandoned embedding indexes for grep, with conditions

### Product retrieval stacks in late 2026

Coding agents are the clearest natural experiment on vector indexes, because several vendors built them, measured them and then publicly changed course.

|---|---|---|---|
| **Codex** | Model runs `rg`, `cat`, `sed` in a sandbox; AGENTS.md ≤32 KiB; BM25 only over tool metadata | None ([openai/codex](https://github.com/openai/codex)) | No public rationale or ablation |

Cursor's reversal is the strongest real-world data point. Cursor had trained its own embedder on agent traces and published the most-cited pro-embedding result. Eight months later it stopped "computing embeddings of your code or storing them on our servers for search" in favor of a regex index, because frontier models had become good enough at grep ([Cursor forum](https://forum.cursor.com/t/what-do-you-think-about-cursor-removing-the-codebase-indexing-settings/165899)). It kept an *index*, but changed what it indexes from meaning to exact text. It anchors that index to a git commit because "an index for regular expression search also needs to be _very fresh_" ([Cursor fast regex](https://cursor.com/blog/fast-regex-search)). It also removed its @Docs crawler because "The agent is now much better at finding and reading documentation on its own", and told users to keep docs as local markdown ([Cursor forum](https://forum.cursor.com/t/how-to-add-documnets/170530)). The user complaints in the same thread mark where grep falls short. Concept questions with no seed identifier ("where do we handle DTC ship updates") got worse, and agents grepped stale archive files as "current product truth." Those are the two gaps a semantic or metadata layer still fills.

The vendors that keep semantic indexes are mostly platform or index owners: GitHub owns the repositories, and Augment and JetBrains sell the engine. Where they measure agent-level outcomes rather than offline retrieval metrics, the effect is small, at −2% time for Copilot and +0.3% retention for Cursor. Docs retrieval follows the same "someone else's index behind a tool" pattern as web search. Context7 keeps a private, version-specific docs index behind `resolve-library-id` and `query-docs` tools, and its crawling and parsing engines are closed ([upstash/context7](https://github.com/upstash/context7)). llms.txt is cheap to publish but barely used: one study saw no automatic requests in 45 trials across 15 tools, and 97% of domains with the file recorded no requests ([arXiv 2610.38361](https://arxiv.org/abs/2610.38361)).

### The grep-versus-embedding evidence is conditional, not settled

The 2026 research literature explains the convergence and also marks its limits. Frontier models plus grep do well partly because code benchmarks are "saturated with keyword references (e.g. file paths, function names)", and state-of-the-art localization drops "catastrophically" on a benchmark without naming hints ([arXiv 2604.16021](https://arxiv.org/abs/2604.16021)). The table summarizes the main results.

| Study | Finding | Implication |
|---|---|---|
| mini-SWE-agent ([GitHub](https://github.com/SWE-agent/mini-swe-agent)) | Bash only, about 100 lines, >74% on SWE-bench Verified | Strong models need no special retrieval tools on identifier-rich tasks |
| SWE-Explore ([arXiv 2606.07297](https://arxiv.org/abs/2606.07297)) | BM25, TF-IDF and a light dense retriever "remain close to Random", while every agentic explorer (Claude Code, Codex, OpenHands) is far higher | One-shot retrieval loses to exploration (weak dense baseline) |
| ExecRetrieval ([arXiv 2609.01865](https://arxiv.org/abs/2609.01865)) | Top dense system: exec@10 = 1.00 but exec@1 = 0.331; rank-1 misses are the buggy near-clone 91.5–99.4% of the time | Embeddings find the topic, not the correct code |
| Small coding agents ([arXiv 2610.33958](https://arxiv.org/abs/2610.33958)) | Graph and embedding tools add 17–21 points at 1.7–4B but only 4–5 at 32B | Indexes matter most for weaker or cheaper models |
| Deep Agentic Search, SWE-QA ([arXiv 2608.01507](https://arxiv.org/abs/2608.01507)) | Vector-index agent 65.2% vs 46.2% for a planner delegating grep to a subagent; **41.8% of failures at the hand-off**, usually silent | Concept QA favors semantic search; summary-only hand-offs are dangerous |
| CodeGrep ([arXiv 2608.05886](https://arxiv.org/abs/2608.05886)) | Retrieval at precision 0.375 degrades the agent, 0.445 is neutral, 0.677 starts to cut cost | Low-precision injected context hurts |
| Code Isn't Memory ([arXiv 2606.22417](https://arxiv.org/abs/2606.22417)) | Structural index: resolve 41.9% → 50.4% in one harness (authors built it) | A good structural index can still help |
| CodeNib ([arXiv 2607.25431](https://arxiv.org/abs/2607.25431)) | Incremental index repair reproduced a full rebuild on only **13 of 24** changes | Index freshness is a correctness risk |
| LSP vs grep ([arXiv 2608.13568](https://arxiv.org/abs/2608.13568)) | "The answer is conditional and usually negative"; LSP costs +6% to +118% tokens | Richer tools are not automatically used or useful |
| Is Grep All You Need? ([arXiv 2605.15184](https://arxiv.org/abs/2605.15184)) | Grep beat ANN plus rerank (93.1 vs 83.6 for Opus 4.6); writing results to a file instead of inline dropped one harness from 93.1 to 55.2 | Result delivery and harness matter as much as the retriever |
| Coding agents as long-context processors ([arXiv 2603.20432](https://arxiv.org/abs/2603.20432)) | Agents over file-organized text beat published SOTA by 17.3% on long-context, RAG and QA tasks | The file-and-grep interface transfers beyond code |

The pattern that is winning is neither grep alone nor vectors alone. It combines a fresh lexical index, optional semantic and structural views of the same snapshot, a small always-loaded map file, and fast read-only search subagents, with everything tuned for precision. The coding evidence also refines what the map file should contain. An ETH study found context files "do not generally improve task success rates, while increasing inference cost by over 20%", helping mainly with "non-standard coding practices" ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). With a deliberately stale instruction file, **90.1% of agent choices followed the file over the code**, and one sentence giving code precedence moved code-following from 4.2% to 91.4% ([arXiv 2610.30571](https://arxiv.org/abs/2610.30571)).

## Measured failures: valid links, unsupported claims and unstable answers

### Citation audits, separating independent from vendor numbers

Independent audits agree on one point. The pipeline rarely invents sources outright. It cites real pages that do not support the claim, cites syndicated copies, or states the claim more strongly than the source does.

Native span citations eliminate fabricated pointers but not unsupported claims, because a valid pointer can still sit under an overstated sentence. Error localization in multi-agent research points at the writer, not the reader. Agents that summarize single documents make few errors, but **84.7% of final-report errors in one system originated at the orchestrator**, as information passes "through agents like a telephone game" ([Hirsch et al. 2026](https://arxiv.org/abs/2608.24306)). Across seven systems, agents "consistently produce stronger claims than warranted", collapsing conflicting evidence into decisive narratives ([Singha Roy et al. 2026](https://arxiv.org/abs/2610.35793)).

### One run is a sample, not a census

Run-to-run instability is the failure that matters most for anyone treating a research agent as a data source. Ten identical prompts to one commercial deep research system gave a median pairwise entity Jaccard of **0.12** and a citation Jaccard **below 0.02**, with discovery curves that "do not visibly saturate" ([Pykälä & Kaski 2026](https://arxiv.org/abs/2610.26421)). Ai2's Asta showed unstable cited-reference sets across identical queries ([Orduña-Malea & Lopezosa 2026](https://arxiv.org/abs/2606.08301)). AI Overviews are less consistent across repeated runs and less robust to minor query edits than organic search ([Grossman et al. 2026](https://arxiv.org/abs/2604.27790)). Path dependence has a mechanism: "early findings redirect later queries, document choices, and stopping, so the documents an agent reads form a selective sample", and a well-cited report can still reach a misleading conclusion ([Xiao et al. 2026](https://arxiv.org/abs/2609.39026)). Benchmarks inherit the problem through live search. Agents retrieve benchmark answers online and inflate scores by up to 4% ([arXiv 2606.05241](https://arxiv.org/abs/2606.05241)), which is why reproducible evaluation is moving to fixed corpora such as BrowseComp-Plus ([Chen et al. 2025](https://arxiv.org/abs/2508.06600)).

### Poisoning, GEO and prompt injection target the reading step

Every signal an LLM engine relies on is now attacked. Generative engine optimization (GEO) rewrites that add quotations, statistics or citations raised visibility by **up to 40%** in controlled settings and by 22% for one strategy on live Perplexity ([Aggarwal et al. 2024](https://arxiv.org/abs/2311.09735)). A critical survey of 45 GEO studies finds those gains "conditional on a source already being present in a fixed context" and finds no stable longitudinal effect ([Martinez 2026](https://arxiv.org/abs/2607.14035)). Cheap publication paths work fast: "A $14 GEO purchase produced 13 public posts, and one AI-search platform cited GEO-posted content … within one hour" ([Liu et al. 2026](https://arxiv.org/abs/2610.11932)). Appending as few as **13 words** to one frequently retrieved page got that text retrieved in 57–76% of deep research runs and cited in 38–51% of reports ([Zhang, Triedman & Shmatikov 2026](https://arxiv.org/abs/2605.24245)). Seeding one plausible false document caused **66–88 point accuracy drops** for strong agents, which kept deferring to the answer-like document even after retrieving truthful records ([DRNOISE](https://arxiv.org/abs/2607.17291)). Neural retrievers themselves rank LLM-generated text higher ([Dai et al. 2023](https://arxiv.org/abs/2310.20501)), and about 16% of sources cited by four major assistants showed signs of being AI-generated ([Allaham & Diakopoulos 2026](https://arxiv.org/abs/2605.23684)). In private knowledge bases, PoisonedRAG reached 90% attack success with five malicious texts per target question in a corpus of millions ([Zou et al. 2024](https://arxiv.org/abs/2402.07867)).

Indirect prompt injection makes every fetched page untrusted input ([Greshake et al. 2023](https://arxiv.org/abs/2302.12173)). Independent benchmarks still show high partial success: in WASP, simple human-written injections partially succeed in up to 86% of cases ([Evtimov et al. 2025](https://arxiv.org/abs/2504.18575)). Brave's disclosure showed hidden Reddit text making Perplexity's Comet browser exfiltrate a user's email one-time password ([Brave](https://brave.com/blog/comet-prompt-injection/)). Vendor-reported attack success against their own adaptive attackers is much lower. Anthropic reports 1.4% for Opus 4.5 with safeguards against 8.0–13.8% for the model alone, while stating "No browser agent is immune to prompt injection" ([Anthropic](https://www.anthropic.com/research/prompt-injection-defenses)). OpenAI reports 0–0.51% for text injections on deep research after mitigations, including a rule that the agent cannot "navigate to or construct arbitrary URLs" ([System Card](https://cdn.openai.com/deep-research-system-card.pdf)). The defenses that work act on structure rather than on judgment. Spotlighting, which marks the provenance of untrusted input, cut attack success from over 50% to under 2% on GPT models ([Hines et al. 2024](https://arxiv.org/abs/2403.14720)). Anthropic's fetch tool only opens URLs that already appeared in the conversation, and Codex's cached mode keeps arbitrary live pages out of the loop.

### Long contexts degrade, so compression is not optional

Long context windows do not remove the need for selective reading. Accuracy is highest when relevant information sits at the start or end of the context ([Lost in the Middle](https://arxiv.org/abs/2307.03172)). With minimal lexical overlap between question and answer, 11 of 13 models fall below half their short-context baseline at 32K tokens, and GPT-4o drops from 99.3% to 69.7% ([NoLiMa](https://arxiv.org/abs/2502.05167)). Only half of 17 models claiming 32K+ context perform satisfactorily at 32K ([RULER](https://arxiv.org/abs/2404.06654)). Across 18 models, focused prompts of about 300 tokens beat full prompts of about 113,000 tokens on LongMemEval for every model ([Chroma](https://www.trychroma.com/research/context-rot)). Outdated passages that sit next to current ones "substantially" reduce accuracy even when current information is available ([HoH](https://arxiv.org/abs/2503.04800)), and the main temporal bottleneck is "post-retrieval reasoning rather than retrieval" ([TREK](https://arxiv.org/abs/2610.25323)). Answering from snippets without opening pages is associated with more outdated answers and unfaithful citations ([Walters, Chen & Toni 2026](https://arxiv.org/abs/2610.21731)).

## Web research and the user's lakes solve opposite problems

### Where each approach pays, and what it buys

The user's earlier research designed two stores. The first is a **typed deterministic database**. An LLM runs once at ingestion as a non-deterministic compiler, fills a closed, versioned schema with span-grounded values, and publishes snapshot-pinned tables that agents query only through exact predicates. The second is a **searchable knowledge base** of typed, versioned knowledge units (concepts, rule cards, procedures, articles). Each unit carries source spans, ACLs and validity and authority metadata, and agents reach the units through a markdown file tree and a handful of hybrid search tools. Web research agents occupy a third corner. The side-by-side comparison shows they are complements, not competitors.

| Dimension | Web research agents (Codex web search, ChatGPT, Claude, Gemini deep research) | Searchable knowledge base (earlier research) | Typed deterministic database (earlier research) |
|---|---|---|---|
| **Where cost is paid** | At query time: 10–160+ searches, ~250k–900k input tokens, $1–7 and 3–30 minutes per deep task ([Gemini docs](https://aistudio.google.com/docs/deep-research)); index cost amortized by the provider at $0.75–35 per 1k queries | Mostly at ingestion (parsing, structure-led chunking, optional enrichment, embeddings), plus a short query loop | Almost entirely at ingestion (extraction, validation, human review); queries are near-free |
| **Index vs inference** | Index-light for the agent (rented), inference-heavy | Balanced: hybrid index plus a short agent loop; two retrieval rounds capture 95% of gains ([arXiv 2606.21553](https://arxiv.org/abs/2606.21553)) | Index-heavy, inference-light: the LLM never runs at query time |
| **Freshness** | Provider crawl from minutes to weeks; cached modes lag; live fetch possible; no supersession markers | Content-hash incremental sync; validity windows; superseded units filtered, not ranked down | Snapshot rebuilds; versioned extractions; explicit as-of queries |
| **Exactness** | Probabilistic; poor enumeration (0.363 soft F1 on WANDR, [arXiv 2608.14747](https://arxiv.org/abs/2608.14747)) | Ranked evidence the agent reads and judges | Exact predicates: extraction-then-SQL 50.9 vs 6.0 recall on intersection queries ([QO-Bench](https://arxiv.org/abs/2606.04646)) |
| **Provenance** | URL plus character span; pages change, rot, sit behind paywalls or are syndicated; 3–13% fabricated URLs | Immutable unit and span IDs back to verbatim sources | Every value grounded to `(doc, page, char span, spec_id)` |
| **Permissions** | Public web only; domain allow/block lists | ACL pre-filters on every chunk, fail-closed sync | ACL columns on every row, enforced in the data layer |
| **Determinism** | Citation Jaccard <0.02 across identical runs ([Pykälä & Kaski](https://arxiv.org/abs/2610.26421)) | Retrieval reproducible per snapshot; generation varies | Identical repeat answers via snapshot pinning; models vary up to 15% across "deterministic" runs, so determinism must come from data ([Atil et al.](https://arxiv.org/abs/2408.04667)) |
| **Ranking signals available** | Links, anchors, 13 months of clicks, spam systems, rater-tuned quality models, all inherited for free | None for free: must build references, usage logs, ownership, verification and validity | Not needed for predicates: keys, types and filters replace ranking |
| **Adversarial pressure** | High: SEO spam, GEO, poisoning, injection | Low, except ingested external content and tool descriptions | Low; defended at the write path by validation |
| **Best question type** | Open-world discovery of external, recent or unknown facts | "What applies here": concepts, policies, procedures | "How many", filters, joins, changing attributes |

The deepest difference is ownership of the freshness loop and the quality evidence, not retrieval mathematics. Both web engines and the user's knowledge base converge on the same hybrid stack: an inverted index, dense candidates, a reranker and passage units. The web side owns neither the corpus nor its quality evidence, so it rents a crawl and compensates at query time with fan-out, persistence and verification. The user's side owns the corpus, so it can afford what the web cannot: complete re-indexing, exact typed fields, immutable spans and permission columns. The independent failure data points the same way. Web agents fail mostly at evidence handling (unsupported citations, smoothing, incomplete enumeration, instability), and these are exactly the properties a pre-structured lake provides by construction. Microsoft's finding that enterprise queries needed **30–50% more iterations** than web queries for equivalent coverage ([Microsoft](https://techcommunity.microsoft.com/blog/microsoft365copilotblog/researcher-agent-in-microsoft-365-copilot/4397186)) shows that unstructured internal corpora are *harder* for these agents than the web, not easier. The web's crawl-rank-click machinery is missing there.

The web industry is also drifting toward the user's design from the other side. OpenAI's reverse-engineered index is split into typed vertical sub-indexes, Perplexity scores self-contained spans, Web IQ returns structured evidence objects, and DeepSeek exposes authority and rerank fields. A toolkit that compiles documents and tools into typed, chunked, hybrid-indexed records with provenance is structurally aligned with where AI-first search engines are heading.

### Private corpora have no link graph or click log, so the signals must be manufactured

A private corpus lacks the web's free, outside-the-document quality evidence. Intranet research found the strongly connected core of IBM's intranet was only about 10% of nodes, so PageRank and HITS discriminate poorly. Creators "have little reason" to build hubs, and many queries have one "right answer" rather than a best one. Because intranets are largely spam-free, anchor text, titles and headings become reliable, and anchor text roughly doubled recall@20 for popular queries ([Fagin et al. 2003](https://mccurley.org/papers/www2003/p641-mccurley.html)). An enterprise search survey concluded that "the most successful techniques of the web, based on link analysis do not apply" ([Mirza 2008](https://scitepress.org/PublishedPapers/2008/16742/16742.pdf)). The court record offers encouragement for small corpora: for small engines, "even a small amount of data can result in meaningful improvements" ([Mehta opinion](https://storage.courtlistener.com/recap/gov.uscourts.dcd.223205/gov.uscourts.dcd.223205.1033.0_3.pdf)). The substitutes map one-to-one onto web signals.

| Web signal | What it does on the web | Private-corpus substitute |
|---|---|---|
| Links and anchor text | "Latent human judgment" of authority | Explicit references between units (citations, "see also", supersedes, ticket-to-commit, code imports) and a searchable "how others refer to this" field on the target |
| Navboost / click memorization | Remembers which documents satisfied which queries | Agent and user usage logs: results opened, cited, used in a successful task, or skipped and followed by a re-query; a small query-to-unit success table fed back into reranking |
| siteAuthority, E-E-A-T, raters | Quality priors and evaluation | Owner, review status, verified-by and verified-at, canonical vs draft, source trust tier, given to the reranker as priors; a reliability prior raised P@5 from 0.48 to 0.72 in one small study ([Koganti & Garrido-Lestache](https://arxiv.org/abs/2607.22584)) |
| Query-deserves-freshness and index tiers | Fresh results for time-sensitive queries | Typed validity windows, superseded-by links, last-verified dates, volatility class per collection |
| Spam team | Demotes manipulation | Write-path controls: allow-listed sources, signed policy documents, quarantine and spotlighting for external or user-contributed text |
| Human raters | Evaluate ranking changes | LLM judges calibrated on a small gold set, plus nugget-style answer evaluation ([Thomas et al.](https://arxiv.org/abs/2309.10621); [TREC 2024 RAG](https://arxiv.org/abs/2411.09607)) |
| Fan-out over a strong engine | Many short queries exploit good ranking | Cheap, repeatable, fielded BM25 and filter tools plus a reranker the agent can call many times |

Kleinberg's observation that a page's own text cannot certify its authority is the central design constraint. LLMs judge credibility shallowly, so in a private lake authority and currency must arrive as metadata the tools can filter on. They cannot be left for the model to infer from prose.

## Ten design implications for the toolkit

The evidence translates into specific requirements for the user's agent-ready data lake. Each row below is a design inference traceable to the cited findings; none is itself a measured result of the proposed toolkit.

| # | Build this | Why (evidence) |
|---|---|---|
| 1 | **Expose the lake as an MCP and file-search backend that deep research agents call** | OpenAI's deep research API queries private stores through MCP, with a cookbook server fronting vector-store file search ([OpenAI Cookbook](https://raw.githubusercontent.com/openai/openai-cookbook/main/examples/deep_research_api/introduction_to_deep_research_api.ipynb)); Gemini's agent accepts `mcp_server` and `file_search` ([Gemini docs](https://aistudio.google.com/docs/deep-research)); STORM and LangChain open_deep_research accept custom retrievers and MCP ([STORM](https://github.com/stanford-oval/storm); [LangChain](https://www.langchain.com/blog/open-deep-research)). The lake becomes the agents' evidence layer instead of competing with their loop |
| 2 | **Serve the five loop primitives: search → ranked snippets, open by ID, find in document, notes store, citation by span** | OpenResearcher reduces browsing to search, open and find ([arXiv 2603.20278](https://arxiv.org/abs/2603.20278)); CORE's best-snippet-plus-expand with duplicate suppression gives state-of-the-art evidence recall up to 553M documents ([arXiv 2611.07859](https://arxiv.org/abs/2611.07859)); OpenAI exposes `open_page` and `find_in_page` |
| 3 | **Ship a snapshot-tied lexical index (BM25 plus trigram or sparse n-gram regex) as a first-class tool** | Cursor anchors Instant Grep to a git commit with an overlay because grep "needs to be very fresh" ([Cursor](https://cursor.com/blog/fast-regex-search)); grep beat ANN plus rerank in one study ([arXiv 2605.15184](https://arxiv.org/abs/2605.15184)); a BM25/grep-only harness answers 85% of BrowseComp-Plus ([arXiv 2610.41172](https://arxiv.org/abs/2610.41172)). Keep semantic and structural views as optional tools over the *same* snapshot, verified against rebuilds ([CodeNib](https://arxiv.org/abs/2607.25431)) |
| 4 | **Materialize a file-tree map with a small, generated, linted always-loaded index** | Codex caps AGENTS.md at 32 KiB and Claude Code targets under 200 lines ([Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md.md); [Claude Code memory](https://code.claude.com/docs/en/memory)); overviews add cost without benefit ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)); stale files override ground truth 90.1% of the time ([arXiv 2610.30571](https://arxiv.org/abs/2610.30571)). Put pointers and non-obvious conventions in the map, and content behind tools |
| 5 | **Make authority and currency filterable fields: status, effective dates, superseded-by, owner, verified-at, trust tier** | Grep cannot tell archives from "current product truth" ([Cursor forum](https://forum.cursor.com/t/what-do-you-think-about-cursor-removing-the-codebase-indexing-settings/165899)); one outdated passage harms answers ([HoH](https://arxiv.org/abs/2503.04800)); recency stamps alone over-steer rerankers ([Fang et al.](https://arxiv.org/abs/2509.11353)); credibility judgment is shallow ([Wan et al.](https://arxiv.org/abs/2402.11782)) |
| 6 | **Require evidence-returning subagent hand-offs: paths, unit IDs, spans and quotes, not summaries alone** | 41.8% of delegated-search failures happened silently at the hand-off ([arXiv 2608.01507](https://arxiv.org/abs/2608.01507)); 84.7% of report errors originated at the orchestrator ([Hirsch et al.](https://arxiv.org/abs/2608.24306)); writing from source-linked claims cut hallucination 2.6–4.5x ([CLAIMWRITER](https://arxiv.org/abs/2608.28643)) |
| 7 | **Log usage as a ranking signal: opened, cited, used in a successful task, skipped, re-queried** | Click memorization is the web's central quality signal ([Mehta opinion](https://storage.courtlistener.com/recap/gov.uscourts.dcd.223205/gov.uscourts.dcd.223205.1033.0_3.pdf)); small data helps small engines; Cursor trained its embedder on agent-trace rankings ([Cursor](https://cursor.com/blog/semsearch)). No study yet measures this for agents over private corpora, so treat it as an experiment with an evaluation gate |
| 8 | **Return compact, precise results with caps, paging, server-side filtering and novelty signals** | SWE-agent's 50-result cap and summarized search beat no search, while iterative search scored worse than none ([arXiv 2405.15793](https://arxiv.org/abs/2405.15793)); low-precision retrieval degrades agents ([CodeGrep](https://arxiv.org/abs/2608.05886)); dynamic filtering cut tokens 24% ([Claude blog](https://claude.com/blog/improved-web-search-with-dynamic-filtering)); "N already returned this session" supports diminishing-returns stopping (Microsoft's threshold rule; Jina's gap queue, [GitHub](https://github.com/jina-ai/node-DeepResearch)) |
| 9 | **Route enumeration, counting and filters to deterministic queries and say so in the tool descriptions** | Research agents "recover the set but not the rows": 0.363 soft F1 on WANDR, under 2% citation overlap across runs; extraction-then-SQL wins on intersections and counts ([QO-Bench](https://arxiv.org/abs/2606.04646)) |
| 10 | **Treat ingested external text as untrusted: provenance marking, trust tiers, quarantine, verifiable citation targets** | Spotlighting cut injection success to under 2% ([Hines et al.](https://arxiv.org/abs/2403.14720)); PoisonedRAG reached 90% success ([Zou et al.](https://arxiv.org/abs/2402.07867)); a URL-liveness tool cut bad citations to under 1% ([Rao et al.](https://arxiv.org/abs/2604.03173)); immutable span IDs let a verifier re-read and judge support cheaply |

Three further choices follow from the web findings. First, when the toolkit itself needs the public web, it should define a pluggable `search_backend` interface (Brave, Exa, Tavily, Perplexity, DeepSeek or a self-hosted index) with a local result cache and Codex-style cached, indexed and live modes. Cached mode is both cheaper and safer against injection. A fetcher that identifies itself honestly, honors robots.txt and handles HTTP 402 pay-per-crawl responses ([Cloudflare](https://blog.cloudflare.com/introducing-pay-per-crawl/)) avoids the legal exposure of SERP scraping. Second, because Codex keeps prompts append-only for cache hits ([OpenAI agent loop](https://openai.com/index/unrolling-the-codex-agent-loop)) and history deletion can raise uncached prefill by 608.5% ([arXiv 2610.34763](https://arxiv.org/abs/2610.34763)), tool outputs and the always-loaded map should respect prompt-cache prefixes. Third, the lake can serve as its own training and evaluation environment. An offline, deterministic search/open/find environment over the user's corpus, plus synthesized hard questions with verifiable answers sampled from the lake's entity graph, reproduces the recipe that trains open research agents ([Tongyi](https://arxiv.org/abs/2510.24701); [WebSailor](https://arxiv.org/abs/2507.02592)). It also gives users a fixed-corpus benchmark in the BrowseComp-Plus mold rather than an irreproducible live-web one.

## Conclusion

The question assumed that high-quality search requires owning a giant index. The evidence shows the opposite division of labor. Vectors are the cheap part; the web's scarce asset is the decades-old ranking evidence (links, clicks, spam demotion) and the crawl that keeps it fresh. The agent's own contribution is behavioral: writing many short queries, persisting, filtering before reading and verifying. RL training makes that behavior better each year, and benchmarks that reward finding are already near saturation. What has not improved at the same pace is evidence integrity. Faithful attribution, complete enumeration and stable answers across runs remain weak in every independent audit. Agents that read more do not cite more faithfully. That shifts where value sits. On the open web, quality depends on the engine and the persistence of the agent. Over a private corpus, there is no engine-supplied quality to inherit, and whoever structures the corpus decides the outcome.

For the user's toolkit, the implication is to stop treating "how Codex searches" as a competitor to compiled lakes and to treat it as the client. Frontier research agents already know how to fan out, loop and read. They lack exact typed answers, immutable citation targets, permission-aware filters, currency and authority metadata, and a substitute for click and link evidence, and those are precisely what the earlier designs build. The open question that would test the whole thesis has not been answered by anyone: no study yet runs the same deep research agent over one corpus served as raw documents and as a pre-structured lake. Running that comparison, on a fixed corpus with nugget-scored answers and repeated runs, is the experiment the toolkit is best placed to publish first.
