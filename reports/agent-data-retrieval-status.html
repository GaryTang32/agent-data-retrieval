Key points
  • The repository is still work in progress. Phase 0, the evaluation harness and its baseline, is merged. Phase 1, the evidence store, is built and measured on the working branch but not merged to main yet. Phases 2–6 are not started.
  • The evidence store works as specified. All 2,425 documents round-trip losslessly, every leaf element carries a character span, a 1% edit re-embeds at most 0.55% of chunks, 100 PDFs are searchable in 8.4 minutes with all cores embedding, and rankings are identical from run to run (section 2.7).

  • Answers are no better. No accuracy difference is significant on any corpus. The reranker lowered quality on every corpus and is switched off.
  • So the baseline stays the reference. Phase 1 does not meet its acceptance rule. The store, its spans and its adr tools are what later phases build on; baseline-linear remains the system to beat.
  • The yardstick is unchanged. Three verified golden sets (1,300 questions) and the baseline under version 2 of the metric definitions: accuracy 0.71–0.72 with RRF fusion and 0.75–0.81 with tuned linear fusion (section 2.6). Three Phase 0 exit items still need outside input.

Part 1 · Objective and plan

One toolkit, three goals, seven gated phases

Build what is hard to retrofit firstA phase is done only when its exit criteria pass in CI

1.1Objective

An agent that answers a question about a rule, a procedure or an obscure fact should get the same, best-supported evidence every time, and be able to show where it came from.

G1 · CompileRaw documents into data products

From documents in any form, build what makes later search work: evidence with hashes and character spans, typed tables, typed relations, searchable knowledge units (rules, procedures, concepts) and tool records.

G2 · Query understandingA question into a structured query

From the user's input, produce the form that matches the G1 products: which store, which operation, which filters and entities, and as of which date.

G3 · RetrievalThe best related result, every time

Retrieve deterministically from those products, with quality measured separately for domain-specific and rare knowledge.

TermWhat it means hereHow it is ensured
DeterministicIdentical question + identical data snapshot ⇒ identical resultsBy construction: pinned snapshots, fixed tie-breaks, no language-model call inside retrieval. Tested on every run.
Best related resultCannot be proven, only measuredThe evaluation harness comes first; a later component is accepted only if it beats the recorded baseline without breaking determinism.

Checks every item must pass, and why

Span re-slice

The stored quote must equal the source text at its recorded offsets.

PurposeEvery answer can be traced to exact characters.

Recompute

Counts and lists are computed by code from structured fields.

PurposeThe model only phrases the question; it never decides the answer.

Evidence-only answer

A second model call answers from the cited evidence alone; a judge decides paraphrased text.

PurposeThe evidence really supports the answer.

Query execution

Where the gold query is executable, running it must reproduce the answer.

PurposeThe G2 target is correct by construction.

Deduplication

Near-duplicate questions are removed.

PurposeOne easy question cannot be counted several times.

Rarity and split

Items are tiered by how rare their key term is and split into dev and test by a seeded hash.

PurposeRare knowledge is reported separately; tuning never touches the test set.

Identical copies of the evidence count

On gov the same regulation text appears in several dated versions; 111 of 711 test evidence spans have a copy. Retrieving any copy now counts, except for questions with an as-of date. This is why gov MRR and citation precision rise.

nDCG@10 is a pure ranking score

Any chunk that touches the evidence earns full credit. Version 1 gave partial credit, which capped bench at about 0.65. Bench nDCG rises to 0.77 and 0.85; research is unchanged.

Identifiers match as whole identifiers

"47 CFR § 73.1740" is now correct for the gold "73.1740". This is the whole accuracy rise: 4 answers on gov RRF, 5 on gov linear, 2 on research RRF.

Query understanding is scored in three parts

Right kind of query, record match, and entity names with partial credit. Version 1 required every field to match exactly, which mostly measured naming conventions.

The gov linear weight was retuned

It moved from 1.00 to 0.85, so 191 of 242 gov linear questions were answered again. Under the same rules the new weight scores slightly lower than 1.00, so this is tuning noise, not a gain.

Checked against experiments first

Each rule was tested on the real corpora before it was adopted: a perfect ranking now scores 1.0 at every chunk size, and the identifier rule agrees with the judge on all 161 recorded identifier answers.

What the baseline shows

Tuned linear fusion retrieves better than RRF

Recall@10 is higher by 0.06 to 0.20 on all three corpora. Accuracy is also significantly higher on research and bench, but not on gov.

Tuning puts most of the weight on keyword search

The weight on BM25 is 1.00 on research, 0.85 on gov and 0.70 on bench. The dense index adds little on gov and research.

A flat baseline cannot count

On gov, count and filter questions score 0 of 27 with RRF and 2 of 27 with linear. This is the gap the typed database in Phase 3 is meant to close.

The model usually picks the right kind of query

84% on gov, 66% on research, 87% on bench. Its weak spot is routing procedure questions as plain facts.

Rare-term questions are neither harder nor easier

Leaving out count and filter questions, the rarest tier scores higher than the most common tier in two of six runs and lower in four.

Every run is below zero at t = 0.9

On gov and research the loss comes mainly from wrong answers where abstaining was better. On bench it comes mainly from partial answers.

What Phase 1 shows

The store does its job

Lossless on all 2,425 documents, a span on every leaf and a page on every PDF leaf, cheap re-indexing after an edit, and identical rankings from run to run and after a rebuild.

The one gain is fragile

The gov Recall@10 gain (+0.031) is significant only within its own comparison; across the five end-to-end measures its Holm p is 0.056. Against the baseline with BM25 alone (0.780) the gain is +0.022 and not significant.

Breadcrumbs recover what chunks lose

Structure-led chunks alone are level or slightly lower. Adding the breadcrumb field lifts gov Recall@10 by 0.037 over p1-struct, and brings research and bench back level with the baseline.

The reranker hurt everywhere

On dev it lowered nDCG@10 by 0.064 on gov, 0.135 on research and 0.081 on bench. A cross-encoder trained on web search queries probably does not suit these corpora. Only one was tried.

The golden evidence favours the baseline

Phase 0 drew overview and procedure evidence as exactly one baseline chunk. It fits inside one Phase 1 chunk only 34% of the time on gov and 18% on research, which costs Phase 1 coverage@10 on those questions.

Research PDFs are a real weak spot

On research questions other than overview and procedure, structure-led chunks lose about 0.03–0.04, most likely from the heuristic section boundaries in PDFs.

3.4Known limits to keep in mind

Phase 1 measurement

One repeat end to end

Phase 1 answers were generated and judged once, so answer agreement across repeats is not measured.

Small dev splits

43, 45 and 141 items, so the tuned weights are noisy. They were fixed before the test split was read.

Golden evidence favours the baseline

Overview and procedure evidence was drawn as exactly one baseline chunk, so it rarely fits one Phase 1 chunk. Golden set v0.2 should fix this.

One model each

One embedding model (the baseline's) and one reranker were tried. A better model might change the picture.

Same model family

The judge and the generator come from the same family, as in Phase 0.

One machine

The 8.4-minute install timing is for one idle 4-core machine, with the embedding model already downloaded.

Phase 0 baseline and golden sets

Same-family judge

Sonnet generates and Opus judges. Every report flags this until a second provider is available.

Judge-accepted items are not marked

Golden files do not record whether an item passed on an exact match or on the judge's verdict. The same judge later scores answers, which could make those items look easier.

Temperature is not pinned

Claude Code has no temperature setting. Saved calls replay exactly; a cold rerun may draft different questions.

Golden items are not human-checked

They are model-drafted and code-verified only.

Questions favour keyword search

A model wrote them while reading the source text, so they share its vocabulary. BM25's strength in the baseline may partly come from this.

Others cannot fully reproduce the runs yet

The research corpus needs the local PDF library, the research and bench golden sets are local only, and the gov corpus is fetched from live government sites that may change.

4.2Run it yourself

Install, check which model profiles are usable, then fetch, index, verify and estimate for one corpus. The last command makes no model calls.

pip install -e ".[dev]"
adr-eval doctor
adr-eval fetch gov
adr-eval index gov
adr-eval golden gov --verify
adr-eval run gov --system baseline-rrf --split test --repeats 1 --dry-run

Drop --dry-run to run for real. Add --max-calls N to cap a run. adr-eval report <run_id> then writes report.json and report.md.

The evidence store's adr command works on one store and one index. For a folder of loose files:

adr ingest --path <folder> --store <store>
adr index <store> --system p1-struct-bc --w-bc 2 --weight 0.9 --threads 0
adr search "<question>" --store <store> --top 10
adr read <doc_id> --store <store> --start 0 --end 500
adr grep "<pattern>" --store <store> --max 20

adr ingest <corpus> ingests a pinned corpus instead. --tuning <run> takes the weights an adr-eval retrieval run tuned on dev. --json gives machine-readable output, and every call appends one line to <store>/log/retrieval.jsonl. --threads 0 embeds on all cores with identical vectors.

Conclusion

Phase 0 is merged: the harness, three verified golden sets covering 1,300 questions, and a baseline recorded under version 2 of the metric definitions. Phase 1, the evidence store, is built and measured on the working branch. As a store it does what it was designed to do: every one of 2,425 documents round-trips losslessly, every leaf carries a span, a 1% edit re-embeds at most 0.55% of chunks, 100 PDFs are searchable in 8.4 minutes, and rankings repeat exactly.

As a retriever it is level with the baseline, not better. The one gain, gov Recall@10 from 0.771 to 0.802, is fragile; answer accuracy shows no significant difference on any corpus; and the reranker made things worse and is switched off. So baseline-linear stays the reference, and the store, its spans and its tools become the base for later phases. The next steps are to merge Phase 1 once you have reviewed it, then to start Phase 2, permissions and applicability, with the golden set v0.2, the layout parser, the reranker question, the research PDF sections and the three items that need outside input carried forward.
