Part 1 · Objective and plan

One toolkit, three goals, seven gated phases

Build what is hard to retrofit firstA phase is done only when its exit criteria pass in CI

1.1Objective

An agent that answers a question about a rule, a procedure or an obscure fact should get the same, best-supported evidence every time, and be able to show where it came from.

G1 · CompileRaw documents into data products

From documents in any form, build what makes later search work: evidence with hashes and character spans, typed tables, typed relations, searchable knowledge units (rules, procedures, concepts) and tool records.

G2 · Query understandingA question into a structured query

From the user's input, produce the form that matches the G1 products: which store, which operation, which filters and entities, and as of which date.

G3 · RetrievalThe best related result, every time

Retrieve deterministically from those products, with quality measured separately for domain-specific and rare knowledge.

TermWhat it means hereHow it is ensured
DeterministicIdentical question + identical data snapshot ⇒ identical resultsBy construction: pinned snapshots, fixed tie-breaks, no language-model call inside retrieval. Tested on every run.
Best related resultCannot be proven, only measuredThe evaluation harness comes first; a later component is accepted only if it beats the recorded baseline without breaking determinism.

Checks every item must pass, and why

Span re-slice

The stored quote must equal the source text at its recorded offsets.

PurposeEvery answer can be traced to exact characters.

Recompute

Counts and lists are computed by code from structured fields.

PurposeThe model only phrases the question; it never decides the answer.

Evidence-only answer

A second model call answers from the cited evidence alone; a judge decides paraphrased text.

PurposeThe evidence really supports the answer.

Query execution

Where the gold query is executable, running it must reproduce the answer.

PurposeThe G2 target is correct by construction.

Deduplication

Near-duplicate questions are removed.

PurposeOne easy question cannot be counted several times.

Rarity and split

Items are tiered by how rare their key term is and split into dev and test by a seeded hash.

PurposeRare knowledge is reported separately; tuning never touches the test set.

What the baseline shows

Tuned linear fusion retrieves better than RRF

Recall@10 is higher by 0.06 to 0.20 on all three corpora. Accuracy is also significantly higher on research and bench, but not on gov.

On gov and research, tuning chose keyword search alone

The tuned weight is 1.00, all on BM25. The dev score is nearly flat from 0.85 to 1.00, so read this as "the dense index adds little here". On bench the weight is 0.70.

A flat baseline cannot count

On gov, count and filter questions score 0 of 27 with RRF and 2 of 27 with linear. This is the gap the typed database in Phase 3 is meant to close.

Whole structured queries almost never match

0.2% on bench, 4% on research, 7% on gov. Only part of this is a model weakness: the score also reflects conventions in the gold queries.

Rare-term questions are not harder

Leaving out count and filter questions, the rarest tier scores higher than the most common tier in four of six runs and lower in two.

Every run is below zero at t = 0.9

On gov and research the loss comes mainly from wrong answers where abstaining was better. On bench it comes mainly from partial answers, which are penalised like wrong ones.

3.4Known limits to keep in mind

Same-family judge

Sonnet generates and Opus judges. Every report flags this until a second provider is available.

Judge-accepted items are not marked

Golden files do not record whether an item passed on an exact match or on the judge's verdict. The same judge later scores answers, which could make those items look easier.

Temperature is not pinned

Claude Code has no temperature setting. Saved calls replay exactly; a cold rerun may draft different questions.

Golden items are not human-checked

They are model-drafted and code-verified only.

Questions favour keyword search

A model wrote them while reading the source text, so they share its vocabulary. BM25's strength in the baseline may partly come from this.

Others cannot fully reproduce the runs yet

The research corpus needs the local PDF library, the research and bench golden sets are local only, and the gov corpus is fetched from live government sites that may change.

4.2Run it yourself

Install, check which model profiles are usable, then fetch, index, verify and estimate for one corpus. The last command makes no model calls.

pip install -e ".[dev]"
adr-eval doctor
adr-eval fetch gov
adr-eval index gov
adr-eval golden gov --verify
adr-eval run gov --system baseline-rrf --split test --repeats 1 --dry-run

Drop --dry-run to run for real. Add --max-calls N to cap a run. adr-eval report <run_id> then writes report.json and report.md.

Conclusion

The project has its yardstick and its first measurement, and both have been through a final review. The harness is built and tested, three verified golden sets cover 1,300 questions, and the flat hybrid baseline is recorded with one repeat. It answers 70% to 81% of test questions correctly and fails almost every count and filter question on gov. The review also showed that four metrics need their definitions settled before later phases are measured against them.

What remains in Phase 0 is the pull request; the 5-repeat run is optional. Phases 1–6, the toolkit itself, now have numbers to beat.
