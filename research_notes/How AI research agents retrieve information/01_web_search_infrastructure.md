# Web search infrastructure behind LLM assistants and research agents (state as of November 2026)

Scope: which index each assistant queries; how web-scale engines crawl, index, shard, refresh and serve; who builds neural/vector web indexes and what that costs; API economics and licensing; crawler access. Agent loops, coding-agent retrieval, page reading/citation, and ranking-quality signals are covered by other tracks.

Labels used below: **[official]** = vendor docs/blog/paper by the operator; **[vendor claim]** = self-reported performance or marketing; **[reporting]** = journalism or court reporting; **[reverse-engineered]** = third-party traffic/code analysis, not confirmed by the vendor; **[inference]** = my own reasoning from cited inputs.

## 1. Which search backend does each product use?

### Takeaway
No mainstream assistant embeds "the internet" locally. Every one calls a hosted search service at inference time, and almost all of them rent or blend indexes. As of late 2026: Google Gemini uses Google Search. Microsoft Copilot uses Bing. Claude uses Brave Search (inferred from strong evidence) and, per unverified secondary reports, newer providers. ChatGPT mixes OpenAI's own index ("Labrador", reverse-engineered) with scraped Google results bought from vendors, and Bing shows up mainly in Deep Research. Codex reads by default from an OpenAI-maintained *cached index*. Perplexity, Brave, Exa, You.com, Parallel and DeepSeek say they run their own indexes. The standalone Bing Search API, once the default "rent an index" option, was retired on 11 Aug 2025.

### Inferences
- A "search tool" in an assistant is three layers: (1) an LLM that rewrites the user turn into several short keyword queries (Copilot's documented examples are 2–5 word queries; ChatGPT fans out 1–3 to 20+), (2) a retrieval backend run by the lab or a vendor, and (3) a page fetch/extract step. The intelligence the user sees comes mostly from (1) and from iterating, not from an exotic index.
- Index independence is a spectrum. Google and Microsoft own full indexes. Brave, Perplexity, Exa, You.com, Parallel and DeepSeek claim their own indexes of varying size. OpenAI is mid-transition (own index for easy and free traffic, scraped Google for hard and paid traffic, as of mid-2026 observations). Anthropic appears to rent (Brave, possibly Parallel) while building a crawler-backed index. Kagi and many smaller tools resell or scrape.
- For an open-source toolkit, the realistic pattern is a pluggable `search_backend` interface (Brave/Exa/Tavily/Perplexity/SearXNG/own index) plus a local cache, mirroring Codex's cached / indexed / live modes.

## 2. How web-scale search engines work (crawl → dedup → index → shard/tier → refresh → serve)

### Takeaway
A web search engine is a crawl-and-index pipeline feeding a sharded, replicated, mostly in-memory inverted index, with caches in front and multi-stage ranking on top. Freshness comes from incremental indexing rather than periodic rebuilds. The core architecture has been stable since the early 2000s. Neural components (dense retrieval, transformer rerankers, passage scoring) were layered on top from about 2015 onward rather than replacing the inverted index. Index sizes run from about 2B pages (one Common Crawl snapshot) to tens of billions (Brave, Exa) to hundreds of billions (Perplexity's 200B+ tracked URLs; Google's ~400B documents in 2020).

### Cited Findings

**Classic architecture**
- [paper, 1998] Google's prototype used distributed crawlers fed by a URLserver. A storeserver compressed pages into a repository, and an indexer parsed documents into "hits" and wrote them into "barrels", producing a partially sorted forward index. A sorter inverted the barrels into the inverted index. Two inverted-barrel sets existed: short barrels for title and anchor hits, checked first, then full barrels. The ranking signals were PageRank and anchor text. The system covered 24M pages — [Brin & Page 1998](http://snap.stanford.edu/class/cs224w-readings/Brin98Anatomy.pdf)
- [paper, 2003] A query "reads hundreds of megabytes of data and consumes tens of billions of CPU cycles". The index is split into **index shards**, each holding a random subset of documents, with a replica pool per shard behind a load balancer. Query phase 1 runs on index servers, which intersect hit lists and score; phase 2 runs on document servers, which fetch titles and snippets. More replicas raise throughput and more shards absorb index growth. Raw documents were "several tens of terabytes"; the system ran on more than 15,000 commodity PCs — [Barroso, Dean & Hölzle, IEEE Micro 2003](https://static.googleusercontent.com/media/research.google.com/en//archive/googlecluster-ieee.pdf)
- [talk, 2009] From 1999 to 2009, Google's document count grew from ~70M to "many billion" (~100x), update latency fell from "months to minutes", and average query latency fell from <1s to <0.2s. Document-partitioned versus term-partitioned sharding trade-offs are discussed. An **in-memory index (early 2001)** improved throughput and tail latency. **Cache servers** for results and snippets had "hit rates typically 30–60%". Group varint decodes ~400M numbers/s. Low-latency indexing needs online approximations of global signals (PageRank, anchor text). The Universal Search rollout was 2007 — [Jeff Dean, WSDM 2009 keynote](https://static.googleusercontent.com/media/research.google.com/en//people/jeff/WSDM09-keynote.pdf)

**Freshness pipelines**
- [paper, 2010] Percolator provides incremental, transaction-based processing over a multi-PB repository, handling "billions of updates per day". Processing documents as they are crawled cut average document-processing latency by **100x** and the average age of documents in search results by **~50%** — [Peng & Dabek, OSDI 2010](https://www.usenix.org/legacy/event/osdi10/tech/full_papers/Peng.pdf)
- [official, 2010] Caffeine replaced a "layered" index whose main layer refreshed "every couple of weeks" with continuous small-batch updates. The result was "50 percent fresher results". It stores "nearly 100 million gigabytes" and adds "hundreds of thousands of gigabytes per day" — [Google Search Central blog](https://developers.google.com/search/blog/2010/06/our-new-search-index-caffeine)

**Index size today**
- [official] Google's index contains "hundreds of billions of webpages" and is "well over 100,000,000 gigabytes in size", likened to a book's back-of-book index with an entry for every word on every indexed page — [How Search Works](https://www.google.com/search/howsearchworks/how-search-works/organizing-information/)
- [court testimony, figure for 2020] Pandu Nayak put the index at "about 400 billion documents", said it was smaller "for a time", and said Google discovers "trillions" of pages it does not index. Gary Illyes said Google checks robots.txt on "about 4 billion host names" daily — [Zyppy](https://zyppy.com/seo/google-index-size/)
- [official] Perplexity tracks "over 200 billion unique URLs" on "exabyte-scale" storage, using "tens of thousands of CPUs and hundreds of terabytes of RAM" and running "tens of thousands of indexing operations per second" — [Perplexity Research](https://www.perplexity.ai/hub/blog/architecting-and-evaluating-an-ai-first-search-api)
- [official] Common Crawl CC-MAIN-2026-34 (Aug 7–20 2026): 2.14B pages, 360 TiB uncompressed, 40.2M hosts, 0.7B new URLs — [Common Crawl](https://commoncrawl.org/blog/august-2026-crawl-archive-now-available)
- [paper] ClueWeb22 offers 10B pages "aligned with the document distributions in commercial web search", with rendered visual and cleaned-text fields — [Overwijk et al. 2022](https://arxiv.org/abs/2211.15848). MS MARCO Web Search adds millions of real Bing click labels for web-scale retrieval research — [Chen et al. 2024](https://arxiv.org/abs/2405.07526)

**A modern AI-first index (Perplexity, the most detailed public description)**
- [official] **Crawl prioritisation**: an ML model predicts whether each URL should be indexed, calibrated to importance and expected update frequency. A second model schedules *when* to recrawl. A fixed budget forces refreshes to compete with new URLs. **Tiering**: cold and warm tiers, with learned models choosing which documents stay hot (authoritative domains, under-covered topics). **Units**: documents are split into "self-contained spans" scored at both document and sub-document level. **Retrieval**: lexical and dense retrieval run together and are merged ("not force a choice"), favouring recall first. **Ranking**: prefilter stale or non-responsive content, then fast lexical and embedding scorers, then cross-encoder rerankers. **Latency** (from AWS us-east-1): p50 358 ms / p95 763 ms, versus Brave 513/808, Exa 1375/2188 and a Tavily-style SERP 1342/1790 [vendor benchmark] — [Perplexity Research](https://www.perplexity.ai/hub/blog/architecting-and-evaluating-an-ai-first-search-api)
- [vendor, Vespa] Each document was indexed as text **and** vector embeddings, with metadata updated in real time. The full retrieve-and-rank pipeline had about 100 ms, "thousands of times per second" — [Vespa blog](https://blog.vespa.ai/perplexity-builds-ai-search-at-scale-on-vespa-ai/). Perplexity found that "vector databases could not reliably support even simple boolean filters". The workload was 780M+ queries/month — [Vespa case study](https://vespa.ai/case-studies/why-perplexity-chose-vespa-for-ai-search/)

**Neural layers in Google and Bing ranking**
- [official] Google lists RankBrain (relating words to concepts so pages rank without exact words), neural matching ("representations of concepts in queries and pages … match them to one another"), BERT, MUM ("not currently used for general ranking"), passage ranking, freshness systems and deduplication systems — [Google ranking systems guide](https://developers.google.com/search/docs/appearance/ranking-systems-guide)
- [official, 2019] BERT was applied to ranking for "one in 10 searches in the U.S. in English", served on Cloud TPUs — [Google blog](https://blog.google/products/search/search-language-understanding-bert/). Neural matching ("super synonyms") affected about 30% of queries in Sept 2018 — [Search Engine Journal](https://www.searchenginejournal.com/google-begins-using-neural-matching-to-understand-synonyms-impacting-30-of-queries/271035/)
- [official, 2019] Bing applied transformer models to "every Bing search query globally". A distilled 3-layer BERT took 77 ms on 20 CPU cores, too slow, so Bing moved to GPUs (about 800x throughput), serving more than 1M BERT inferences/s on 2,000+ Azure GPU VMs — [Azure blog](https://azure.microsoft.com/en-us/blog/bing-delivers-its-largest-improvement-in-search-experience-using-azure-gpus/)
- [survey] Production text ranking = multi-stage pipelines (cheap first-stage retrieval → transformer rerankers) and/or dense retrieval — [Lin, Nogueira & Yates 2020](https://arxiv.org/abs/2010.06467)

### Inferences
- "How is it done" in one sentence: a crawler fleet keeps a prioritised, deduplicated, continuously refreshed copy of the useful web. That copy is inverted (and increasingly also embedded) into thousands of shards held in RAM or SSD with replicas. A query is broadcast to all shards, each returns its top-k by cheap scoring, results are merged, and expensive neural rerankers run only on the merged few hundred candidates, with caches absorbing 30–60% of traffic.
- Agents add one twist: the "user" is an LLM issuing many cheap, narrow queries, and it wants passages rather than blue links. Hence span-level units (Perplexity), "evidence objects" (Web IQ) and excerpt-returning APIs (Parallel, Kimi Pro, Brave LLM Context).

### Gaps
- No current official Google index size beyond "hundreds of billions" and "well over 100M GB"; the 400B figure dates from 2020.
- No public, current description of Google's or Bing's production tiering (for example, how many documents sit in the in-memory tier) beyond the 2003–2010 materials.

## 3. Neural/vector web indexes: who builds them, how, and is embedding the web "impossible"?

### Takeaway
Embedding the web is not impossible, and several companies have done it at billion to hundred-billion scale. Bing had over 100B vectors in 2019 and builds Web IQ on DiskANN. Exa embeds tens of billions of pages. Perplexity stores text and vectors per document. Google has used neural matching since 2018. With ANN on SSD (DiskANN/SPANN), Matryoshka truncation and binary quantization, storing vectors for the whole indexed web costs terabytes to low petabytes, smaller than the text index itself. Embedding compute is single-digit millions of dollars at most. What is hard and expensive is everything around the vectors: crawling, parsing, spam and dedup, continuous re-embedding for freshness, filters, low-latency distributed serving, and legal access. Pure vector retrieval also has quality limits, so every production system is hybrid (lexical + dense + reranker). A coding agent like Codex therefore does not build a local vector DB of the internet. It calls a hosted index (OpenAI's cache/index, or a live search) and reads a handful of pages.

### Cited Findings

**Who builds vector indexes of the web**
- [reporting, 2019] Bing had encoded "more than 150 billion" items (words, snippets, pages, images) as vectors and could search "100 billion-plus vectors … in 5 milliseconds" [company claim]. SPTAG was open-sourced (MIT) — [The Register](https://www.theregister.com/2019/05/15/bing_algorithm_github/); SPTAG was "released by Microsoft Research (MSR) and Microsoft Bing", now including SPANN and SPFresh — [SPTAG GitHub](https://github.com/microsoft/SPTAG)
- [official, 2026] Web IQ extends DiskANN "into a distributed retrieval fabric" over "large, disk-resident vector spaces" — [Bing blog](https://blogs.bing.com/search/June-2026/Announcing-Microsoft-Web-IQ). Bing's **Harrier-OSS-v1** embeddings (27B / 0.6B / 270M, 32k context, 100+ languages) ranked #1 on multilingual MTEB-v2 (74.3) as of Apr 6 2026, and "will also be coming to Bing" [vendor benchmark] — [Bing blog](https://blogs.bing.com/search/April-2026/Microsoft-Open-Sources-Industry-Leading-Embedding-Model)
- [official] Exa trains "specialized transformer models" to turn each document into one or more embeddings. It built its own vector DB and crawls with its own parser, storing pages in S3. The "Exacluster" is 144 H200 GPUs (18×8). Exa says it is "the only lab … training the next generation of search" [vendor claim] — [Exa blog, Mar 2025](https://exa.ai/blog/how-to-build-nextgen-search). Its embedding model was pretrained and fine-tuned for "over a month on a 144x H200 cluster". The Rust vector DB gained new clustering and lexical compression. Exa Fast claims <350 ms P50 and Exa Deep about 3.5 s P50 [vendor benchmark] — [Exa 2.0](https://exa.ai/blog/exa-api-2-0)
- [official] **Exa's compression recipe**: 4096-dim Matryoshka embeddings are truncated to 256 dims (20x memory saving), then binary quantized to 1 bit/dim (16x more). Queries stay float. Dot products use precomputed lookup tables held in CPU registers. IVF-style k-means puts documents into **100,000 clusters**, giving ~1000x throughput, and the top candidates are reranked with uncompressed vectors. **Inverted indexes are kept for filters** (date, domain, category, keyword). The targets are <100 ms and >500 QPS, at "10x cheaper than cloud vector database quotes" [vendor claim] — [Exa vector DB blog](https://exa.ai/blog/building-web-scale-vector-db)
- [official] Perplexity: hybrid lexical + dense retrieval merged into one candidate set — [Perplexity Research](https://www.perplexity.ai/hub/blog/architecting-and-evaluating-an-ai-first-search-api)
- [official] Google: neural matching and RankBrain are concept-matching systems sitting on the classic index — [Google ranking systems guide](https://developers.google.com/search/docs/appearance/ranking-systems-guide)
- [reverse-engineered] OpenAI's shopping index uses BM25 narrowing plus ANN at 12,288/4,096 dims — [Peec AI](https://peec.ai/blog/chatgpt-built-its-own-search-index)
- [paper] Facebook search serves embedding-based retrieval **inside an inverted-index search system** (ANN as one more retrieval path) — [Huang et al. 2020](https://arxiv.org/abs/2006.11632)

**Billion-scale ANN building blocks**
- [paper, NeurIPS 2019] DiskANN indexes and searches **1B points on one workstation with 64 GB RAM + SSD**: >5,000 QPS, <3 ms mean latency, 95%+ 1-recall@1 on SIFT1B — [Subramanya et al. 2019](https://proceedings.neurips.cc/paper_files/paper/2019/file/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Paper.pdf)
- [paper, 2021] FreshDiskANN supports "thousands of concurrent real-time inserts, deletes and searches per second" on >1B points with >95% 5-recall@5, at 5–10x lower cost of maintaining freshness than periodic rebuilds — [Singh et al. 2021](https://arxiv.org/abs/2105.09613)
- [paper, 2021, Bing team] SPANN keeps centroids in memory and posting lists on SSD (an inverted-index layout for vectors). It is 2x faster than DiskANN at the same recall and memory, reaching 90% recall@1/@10 in about 1 ms with 32 GB memory on billion-scale sets — [Chen et al. 2021](https://arxiv.org/abs/2111.08566)
- [paper] Faiss is the standard toolkit of vector indexing, compression and clustering primitives — [Douze et al. 2024](https://arxiv.org/abs/2401.08281). Matryoshka Representation Learning allows up to 14x smaller embeddings at equal accuracy and 14x retrieval speed-ups — [Kusupati et al. 2022](https://arxiv.org/abs/2205.13147)
- [paper] Late interaction (ColBERT) is more effective but "inflates the space footprint … by an order of magnitude". ColBERTv2's residual compression cuts that 6–10x — [Santhanam et al. 2021](https://arxiv.org/abs/2112.01488). PLAID brings ColBERTv2 to tens of ms on GPU at large scale — [Santhanam et al. 2022](https://arxiv.org/abs/2205.09707)
- [paper] Learned sparse retrieval (SPLADE) keeps exact term matching and inverted-index efficiency while learning term expansion. It is a middle path between BM25 and dense retrieval — [Formal et al. 2021](https://arxiv.org/abs/2107.05720)

**Quality limits of pure vector retrieval (why everyone stays hybrid)**
- [paper, 2025, Google DeepMind] The number of top-k document subsets a single-vector embedder can return is bounded by its dimension. On the simple LIMIT dataset, "even state-of-the-art models fail" — [Weller et al. 2025](https://arxiv.org/abs/2508.21038)
- [paper] On BEIR's 18 zero-shot datasets, "BM25 is a robust baseline". Rerankers and late interaction do best "at high computational costs", and dense models often generalise worse out of domain — [Thakur et al. 2021](https://arxiv.org/abs/2104.08663). E5 was "the first model that outperforms the strong BM25 baseline on BEIR" zero-shot (2022) — [Wang et al. 2022](https://arxiv.org/abs/2212.03533)
- [paper] DPR beat Lucene BM25 by 9–19 points top-20 accuracy on open-domain QA (in domain) — [Karpukhin et al. 2020](https://arxiv.org/abs/2004.04906). RAG formalised retrieval over a dense index (Wikipedia) as LLM non-parametric memory — [Lewis et al. 2020](https://arxiv.org/abs/2005.11401)
- [official] "Vector databases could not reliably support even simple boolean filters" (Perplexity's reason for choosing a hybrid engine) — [Vespa case study](https://vespa.ai/case-studies/why-perplexity-chose-vespa-for-ai-search/)

**Cost inputs (all cited) for the "embed the web" math**
- Embedding compute: Qwen3-8B-Embedding saturates at about **45k tokens/s per H100**. At $2/hr and good batching that is about **$0.017 per 1M tokens**; at 10% utilisation, about $0.16 per 1M — [Tensor Economics, Sep 2025](https://www.tensoreconomics.com/p/why-are-embeddings-so-cheap)
- API embedding prices: text-embedding-3-small $0.02 and text-embedding-3-large $0.13 per 1M tokens — [OpenAI pricing](https://developers.openai.com/api/docs/pricing)
- Managed vector-serving reality check (Feb 2024): 3B × 1,408-dim image embeddings = 17 TB float32 (4.26 TB quantized). On Vertex AI Vector Search, a static batch index plus serving cost about **$99k/month**. Streaming updates cost about **$1.5M/month at daily** and **$37.2M/month at hourly** cadence — [GDELT Project](https://blog.gdeltproject.org/ai-in-production-a-deep-dive-into-the-costs-of-multimodal-embedding-search-over-3-billion-images/)
- Corpus sizes: FineWeb has 15T tokens from 96 Common Crawl snapshots after heavy filtering — [Penedo et al. 2024](https://arxiv.org/abs/2406.17557). RedPajama V1+V2 exceed 100T tokens of mostly web text — [Weber et al. 2024](https://arxiv.org/abs/2411.12372). For comparison, Google's text index is "well over 100,000,000 GB" (≥100 PB) — [How Search Works](https://www.google.com/search/howsearchworks/how-search-works/organizing-information/)

### Inferences
- **[inference] Back-of-envelope.** Assume ~1,000 tokens of extracted main text per page; this is my assumption and the results scale linearly with it.
  - *Exa / ClueWeb scale (10B pages)*: 1e13 tokens ÷ 45k tok/s ≈ 2.2e8 GPU-s ≈ **62k H100-hours ≈ $120k** self-hosted, or about $200k via text-embedding-3-small ($1.3M via -large). Vectors at one per page: 4096-dim fp16 (8 KB) ≈ **82 TB**; Exa-style 256-bit binary (32 B) ≈ **320 GB**, which fits in RAM on a few servers.
  - *Google scale (400B pages)*: 4e14 tokens ≈ **2.5M H100-hours ≈ $5M** (≈$8M at $0.02/1M). Vectors: fp16 4096-dim ≈ **3.3 PB**; 256-bit binary ≈ **13 TB**. At 5 passages per page, multiply by 5 (≈16 PB fp16 or 64 TB binary). That is still well below the ≥100 PB text index.
  - *Freshness*: Perplexity's "tens of thousands of index updates per second" works out to roughly 1–2B document updates per day. Re-embedding 1.5B pages/day × 1k tokens ≈ 1.5e12 tokens/day ≈ 9k H100-hours/day, about **400 H100s running continuously** just to keep embeddings fresh. Managed-service pricing for streaming updates (GDELT) shows why operators build their own.
  - Conclusion: the vectors are cheap. The crawl (~360 TiB raw HTML per 2B-page snapshot, by Common Crawl's ratio), the fleet that keeps it fresh, and serving with filters at <200 ms are what cost tens to hundreds of millions of dollars (see Kagi's citation of ~$100B Microsoft spend on Bing in section 4).
- "It is impossible for Codex to turn the whole internet into a local vector DB" is correct for a *local, per-user* index, both for storage and because freshness requires a crawl. It is wrong as a statement about the industry. OpenAI does it server-side (Codex's documented "OpenAI-maintained index of web results"), and Exa, Bing, Perplexity and Google do it as part of hybrid indexes.
- The pattern every serious system converges on, and the one most relevant to the user's toolkit, is: inverted index (exact terms, filters, IDs) + dense ANN (concepts) + learned sparse or late-interaction where affordable + cross-encoder rerank over a few hundred candidates + passage-level units. Single-vector-only retrieval is known to fail on combinatorial or precise queries (LIMIT, BEIR, Perplexity's boolean-filter finding).

### Gaps
- No official figures on how many vectors Google, Bing (post-2019) or Perplexity actually store, or what share of candidates comes from dense versus lexical retrieval.
- Exa's index size beyond "tens of billions" and its per-document vector count are undisclosed.
- Tokens-per-page for the indexed web is not officially published; the 1,000-token assumption is mine.

## 4. Caching, query economics, licensing, and the "search API scarcity" problem

### Takeaway
Web search for agents costs roughly **$0.75–$35 per 1,000 queries**, plus the LLM tokens for result content, which often dominate. Indexes behind first-party AI products (Google, Bing) are licensed only in restricted "grounding" forms: no raw results, mandatory display, no blending. Google has never offered a general web-results API and is closing its last programmable one. That scarcity drove OpenAI to scrape Google via vendors, drove Kagi and others to SERP scrapers, created a market for independent indexes (Brave, Exa, Perplexity, You.com, Parallel), and produced the 2025 US antitrust remedy that forces Google to share index data and syndicate results to "qualified competitors", including GenAI firms.

### Cited Findings

**Price points (per 1,000 queries; as of the cited page dates)**
- OpenAI `web_search` tool: $10/1k calls (all models) plus search-content tokens at model rates. The preview for non-reasoning models is $25/1k with free content tokens. The mini models bill a fixed 8,000-token block per call — [OpenAI pricing](https://developers.openai.com/api/docs/pricing)
- Anthropic `web_search`: $10/1k plus tokens. Results "are counted as input tokens" in later turns too. The Batches API throttles web search per organisation — [Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)
- Gemini grounding: Gemini 3+ costs $14/1k executed queries after 5,000 free per month; a single prompt can bill several queries — [Gemini docs](https://aistudio.google.com/docs/google-search). Vertex grounding is $35/1k — [Kagi](https://blog.kagi.com/waiting-dawn-search)
- Grounding with Bing: $35/1k, versus retired Bing API tiers of $6–25/1k — [PPC Land](https://ppc.land/microsoft-ends-bing-search-apis-on-august-11-alternative-costs-40-483-more/). Microsoft raised some Bing API tiers "up to 10x" in Feb 2023 — [Kagi](https://blog.kagi.com/waiting-dawn-search)
- Brave: Search plan $5/1k (includes LLM Context) at 50 QPS. Answers plan $4/1k plus $5/M tokens at 2 QPS. $5 of free credits per month. Rights to store results or train on them need a plan that includes them — [Brave Search API](https://brave.com/search/api/). An older Brave guide quoted $3 CPM and a 2,000/month free tier — [Brave guide](https://brave.com/search/api/guides/what-sets-brave-search-api-apart/), now superseded.
- Exa: `lite` $4, `auto` $7, `deep` $12, `deep-reasoning` $15 per 1k (≤10 results). Contents cost $1 per 1k pages per content type — [Exa pricing](https://exa.ai/pricing)
- Perplexity Search API: $5/1k ($1/1k Fast). Agent API `web_search` $2.50/1k, `fetch_url` about $0.50/1k — [Perplexity pricing](https://docs.perplexity.ai/getting-started/pricing)
- Tavily: basic search 1 credit, advanced 2 credits, at $0.008/credit pay-as-you-go ($8 / $16 per 1k). 1,000 free credits per month — [Tavily docs](https://docs.tavily.com/documentation/api-credits)
- DeepSeek Search/Fetch: $0.75/1k at 100 QPS — [DeepSeek docs](https://api-docs.deepseek.com/guides/search/). Firecrawl: 2 credits per 10 results — [Firecrawl docs](https://docs.firecrawl.dev/features/search)
- Google Custom Search JSON API: "closed to new customers". Existing customers must move by **January 1, 2027**. It costs $5/1k up to 10k/day, and Vertex AI Search covers only "up to 50 domains" — [Google CSE overview](https://developers.google.com/custom-search/v1/overview)

**Latency budgets and caching**
- Classic Google averaged <0.2 s per query (2009), with results and snippet caches at 30–60% hit rates — [Dean 2009](https://static.googleusercontent.com/media/research.google.com/en//people/jeff/WSDM09-keynote.pdf). Agent-API p50s run from ~350 ms (Perplexity, Exa Fast) to ~1.4 s (Exa auto, SERP-scrape APIs), and Web IQ claims <165 ms p95 [vendor claims] — [Perplexity Research](https://www.perplexity.ai/hub/blog/architecting-and-evaluating-an-ai-first-search-api); [Exa 2.0](https://exa.ai/blog/exa-api-2-0); [Web IQ](https://blogs.bing.com/search/June-2026/Announcing-Microsoft-Web-IQ)
- Codex's default is an OpenAI-maintained **cache** of pre-indexed results — [Codex config](https://learn.chatgpt.com/docs/config-file/config-basic.md). The OpenAI API offers cache-only mode (`external_web_access: false`) — [OpenAI guide](https://developers.openai.com/api/docs/guides/tools-web-search). Testing ChatGPT's lockdown mode suggested answers come from cached or offline results [reverse-engineered] — [Peec AI](https://peec.ai/blog/chatgpt-built-its-own-search-index)
- Token cost: Claude's dynamic filtering (code filters results before context) "reduces token use on search-heavy requests" — [Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool). Kimi Pro's passage extraction cuts tokens by about 10x — [Kimi docs](https://platform.kimi.ai/docs/guide/use-web-search)

**Licensing, scarcity, scraping and the antitrust remedy**
- Google offers no public general-web API. Its only path for general results is an ad-syndication bundle. Bing's terms banned reordering or blending results. Kagi describes building an index as "building a parallel national railroad" and cites ~$100B spent by Microsoft on Bing over 20 years — [Kagi](https://blog.kagi.com/waiting-dawn-search)
- Google refused OpenAI's request for search API access (2024) — [PYMNTS](https://www.pymnts.com/news/2025/antitrust-trial-reveals-google-rejected-openai-partnership/)
- Google sued SerpApi on **Dec 19 2025** (N.D. Cal., DMCA §1201), alleging circumvention of **SearchGuard** (a JS challenge launched Jan 2025). It alleges automated requests rose "as much as 25,000%" over two years to "hundreds of millions each day" — [IPWatchdog](https://ipwatchdog.com/2025/12/26/google-sues-serpapi-parasitic-scraping-circumvention-protection-measures/). OpenAI's logo reportedly once appeared on SerpApi's customer page [reverse-engineered/unverified] — [RESONEO](https://think.resoneo.com/chatgpt/)
- Remedies (ruling Sep 2 2025; final judgment Dec 2025, six-year term). Qualified competitors get a **one-time snapshot** of Google's index data (doc IDs, URL map, crawl timestamps, spam scores, device flags) at marginal cost, plus periodic "glue" and RankEmbed user-interaction data. Ranking IP and the Knowledge Graph are excluded. Eligibility covers firms competing "with" search, which is expected to include GenAI — [Capstone](https://capstonedc.com/insights/google-search-remedy-data-sharing-creates-opportunities-for-rivals/); [Hughes Hubbard](https://www.hugheshubbard.com/news/court-issues-remedies-ruling-in-united-states-v-google-search-case). Google must syndicate results to competitors; OpenAI, Anthropic and Perplexity are named as likely beneficiaries — [The Batch](https://www.deeplearning.ai/the-batch/google-must-share-its-search-index-but-can-keep-chrome-and-android). Kagi's summary of the memorandum mentions mandatory syndication, no ad bundling and index data at marginal cost — [Kagi](https://blog.kagi.com/waiting-dawn-search)

### Inferences
- [inference] For a typical agent search step (one query, ~5–10 results, ~5–20k content tokens into a frontier model), token cost usually exceeds the $5–14 per 1k query fee. So result compression (passages, dynamic filtering, extraction) matters more economically than the API price.
- [inference] Restrictive licensing explains why "grounding" APIs (Bing Grounding, Vertex grounding) return answers or citations rather than raw rankable results, and why agent toolkits that need raw results gravitate to Brave, Exa, Tavily, Perplexity or DeepSeek APIs.

### Gaps
- Final syndication details (duration, caps, LLM-training restrictions) appear only in law-firm commentary I could not open. Reports of a 5-year syndication license with declining caps and a ban on LLM training use remain unverified here.
- No current published xAI per-call search price; no Kimi per-call price found; You.com and Parallel prices not verified on official pages.

## 5. Crawling for AI: bots, robots.txt, pay-per-crawl, and what agents can see

### Takeaway
Each major lab now runs separate bots for training, search indexing and user-initiated fetches, so publishers can opt out of training while staying visible in AI search. Infrastructure intermediaries (Cloudflare) increasingly block or charge AI crawlers. Agents' visible web is therefore shrinking and fragmenting, and "user-initiated" fetchers are the contested grey zone.

### Cited Findings
- [official] OpenAI: GPTBot (training), OAI-SearchBot (search), ChatGPT-User (user actions; robots.txt "may not apply"), OAI-AdsBot — [OpenAI bots](https://developers.openai.com/api/docs/bots). Anthropic: ClaudeBot, Claude-SearchBot, Claude-User, all honouring robots.txt and Crawl-delay — [Anthropic help](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-the-web). Meta: Meta-ExternalAgent (training), Meta-WebIndexer (Meta AI search), Meta-ExternalFetcher (user-requested, "may bypass robots.txt") — [Meta docs](https://developers.facebook.com/docs/sharing/webmasters/web-crawlers/). Perplexity: PerplexityBot follows robots.txt and, absent rules, "industry-standard request-rate norms" — [Perplexity Research](https://www.perplexity.ai/hub/blog/architecting-and-evaluating-an-ai-first-search-api)
- [official, Microsoft] Web IQ "honors robots exclusion protocols and publisher controls" — [Bing blog](https://blogs.bing.com/search/June-2026/Announcing-Microsoft-Web-IQ)
- [official, Cloudflare, Jul 1 2025] **Pay per crawl**: a request for a paid URL returns HTTP 402 with a `crawler-price` header. The crawler retries with `crawler-exact-price` or sends `crawler-max-price` up front. Crawlers authenticate via **Web Bot Auth** (Ed25519 HTTP message signatures). Publishers choose Allow, Charge or Block per crawler, and Cloudflare acts as merchant of record — [Cloudflare](https://blog.cloudflare.com/introducing-pay-per-crawl/)
- [official, Cloudflare, Aug 4 2025] Cloudflare alleged that Perplexity used undeclared crawlers (a generic Chrome UA, rotating IPs and ASNs, ignoring robots.txt): about 3–6M requests/day across tens of thousands of domains, versus 20–25M/day from the declared Perplexity-User. ChatGPT-User fetched robots.txt and stopped when disallowed. Cloudflare delisted Perplexity as a verified bot — [Cloudflare](https://blog.cloudflare.com/perplexity-is-using-stealth-undeclared-crawlers-to-evade-website-no-crawl-directives/). The post contains no Perplexity response.
- [official, Cloudflare, Jan–Jul 2025] Crawls per referred visit: Anthropic fell from 286,930 to 38,066, OpenAI from 1,217 to 1,091, Perplexity rose from 54.6 to 194.8, and Google rose from 3.8 to 5.4. AI crawling by purpose was ~80% training, ~18% search and ~2% user actions over 12 months — [Cloudflare](https://blog.cloudflare.com/crawlers-click-ai-bots-training/)
- [official] Opting out of OAI-SearchBot removes a site from ChatGPT search answers, and a robots.txt change takes about 24h — [OpenAI bots](https://developers.openai.com/api/docs/bots). DeepSeek's Fetch "availability depends on the target site's access policies" — [DeepSeek docs](https://api-docs.deepseek.com/guides/search/)

### Inferences
- [inference] Publishers who block training bots but allow search bots (made possible by the bot split) let AI search indexes keep coverage that training corpora lose. This favours labs that run a search crawler (OpenAI, Anthropic, Meta, Perplexity) over those relying only on Common Crawl.
- [inference] For an open-source agent toolkit, identify the fetcher honestly (UA plus optionally Web Bot Auth), honour robots.txt, handle HTTP 402, and prefer licensed APIs for discovery. The legal exposure of SERP scraping (the Google v. SerpApi case) is real.

### Gaps
- No cross-industry measurement of what fraction of the web is now closed to AI search bots specifically (as opposed to training bots). Third-party 2026 crawl-ratio figures I saw (e.g. Anthropic 1,917:1 in Jul 2026) came from secondary sites I did not verify.

## 6. How this differs from typed databases and searchable knowledge bases (the user's comparison)

### Takeaway
Web search for agents is an open-world, adversarial, constantly changing retrieval problem solved with probabilistic ranking over a remote index. The user's typed databases and searchable knowledge bases are closed-world corpora they control, where exact typed queries, full re-indexing and local vector search are affordable. The two meet in the hybrid lexical + vector + rerank stack and in passage-level units.

### Cited Findings
- Web systems prioritise and refresh under a fixed budget, where refreshing existing pages competes with indexing new ones. They also filter spam and staleness and favour authoritative domains — [Perplexity Research](https://www.perplexity.ai/hub/blog/architecting-and-evaluating-an-ai-first-search-api). Google indexes the useful parts of the web and leaves out low-value pages: it discovers "trillions" of pages but indexes ~400B (2020) — [Zyppy](https://zyppy.com/seo/google-index-size/)
- Exact filters still require inverted indexes even in an embedding-first engine — [Exa vector DB](https://exa.ai/blog/building-web-scale-vector-db). Vector DBs struggled with boolean filters — [Vespa case study](https://vespa.ai/case-studies/why-perplexity-chose-vespa-for-ai-search/)
- At knowledge-base scale (millions to low billions of chunks), a single machine with DiskANN or SPANN handles 1B vectors — [DiskANN](https://proceedings.neurips.cc/paper_files/paper/2019/file/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Paper.pdf); [SPANN](https://arxiv.org/abs/2111.08566)
- Search providers increasingly return structured fields for agents: DeepSeek's `authority`, `rerank_score` and `date`; Web IQ's "structured evidence objects"; Firecrawl's typed vertical indexes (research, developer, government) — [DeepSeek](https://api-docs.deepseek.com/guides/search/); [Web IQ](https://blogs.bing.com/search/June-2026/Announcing-Microsoft-Web-IQ); [Firecrawl](https://docs.firecrawl.dev/features/search)

### Inferences
- [inference] What separates "how Codex/ChatGPT search" from a local KB is *who owns the index and its freshness loop*, not the retrieval maths. Locally you can embed everything and re-index on change. On the web you rent someone's crawl-and-index (or cache it, as Codex does) and compensate with query rewriting, many cheap searches and page fetches.
- [inference] The industry is moving toward the user's design: vertical, typed sub-indexes (OpenAI's Labrador verticals, Firecrawl's research/dev/gov indexes, Perplexity spans, Web IQ evidence objects) instead of one flat list of links. A toolkit that converts documents and tools into typed, chunked, hybrid-indexed records is structurally aligned with how AI-first search engines now organise the web.

### Gaps
- No vendor publishes how much of agent answer quality comes from index coverage versus query rewriting and iteration; that is covered by the agent-loop and ranking tracks.
