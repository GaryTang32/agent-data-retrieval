# Open-Source Knowledge Base Stacks and Engineering Case Studies for Searchable Agent Knowledge Bases (as of Nov 2026)

Scope: open-source tooling, reference architectures, and company engineering write-ups for building a searchable KB that agents use to find related topics, domain knowledge, rules, policies, and SOPs. Commercial products are covered by another track. Star counts, licenses, and last-push dates were checked on 2026-11-06 through the GitHub raw LICENSE files and ungh.cc. Where a number repeats the earlier snapshot in `Agent ready data lake toolkit/competitive_landscape_gaps.md`, it is not restated. "Vendor claim" marks a number published by the project or company itself without independent verification.

## 1. Open-source KB frameworks and platforms: KB features, license, maturity

### Takeaway
The OSS field now converges on one KB feature set: connectors with scheduled or webhook sync and deletion pruning; structure-aware chunking (heading paths, parent-child); LLM enrichment (keywords, generated questions, summaries, metadata); hybrid BM25+vector retrieval with reranking and metadata filters; citations; and a retrieval-test or golden-question screen. Three projects lead on KB features. **RAGFlow** (Apache-2.0) has the richest. **Onyx** is MIT core, but per-user permission sync from sources is paid. **Dify** has the most polished eval loop, under a non-OSI license. Source-ACL propagation is the clearest gap among permissive OSS projects: RAGFlow shares a dataset with "Only me / Team" only, Open WebUI and AnythingLLM use app-level groups, and only Onyx's paid tier mirrors source ACLs. A second trend: KBs are exposed to agents as tools or file systems (Open WebUI `grep_knowledge_files` and `kb_exec ls/grep/cat`, the Dify CLI, Onyx/Grab/Cognee MCP servers), not only as a top-k retriever.

### Cited Findings

**RAGFlow (infiniflow), Apache-2.0: the most complete OSS KB feature set**
- 2026 timeline: 1.0.0-rc1 (2026-09-29). Sitemap ingestion (2026-09-10). "Knowledge Compilation" (2026-08-19) generates Wikis, Graphs, Trees, PageIndex, Mind Maps, Timelines and Skills at document and dataset level. Agentic RAG with Low/Medium/High/Ultra thinking modes (2026-08-19). BigQuery source with incremental sync (2026-07-02). The README also advertises "multiple recall paired with fused re-ranking", grounded citations, and visualized chunking for human intervention. — [GitHub infiniflow/ragflow](https://github.com/infiniflow/ragflow)
- Built-in parsing templates: General, Q&A (one chunk per Q&A pair), Manual (section hierarchy), Table (one row per chunk), Paper, Book, Laws (legal structure), Presentation, Picture (OCR plus VLM), One (whole document), Audio (ASR), Email. Parser choices: DeepDOC (default; OCR, table structure, layout), Naive, Docling, OpenDataLoader, TCADP, MonkeyOCRv2, or an external VLM. — [RAGFlow docs: Dataset configuration](https://github.com/infiniflow/ragflow/blob/main/docs/guides/dataset/configuration.md)
- Chunkers, from the same configuration doc:
  - General: default 512 tokens, overlap %, table and image context windows, custom delimiters, and "Use sub-chunks for retrieval" (parent-child).
  - Title Chunker, Hierarchy mode: each chunk keeps its full heading path (e.g. `Part 1 > Chapter 3 > Section 2`). Regex rules for H1 to H5 detect headings. "Set first chunk as global context" makes the document's first chunk the background for the rest. The doc recommends this mode for "legal provisions, regulations, contracts, and technical specifications".
  - Extractor (LLM enrichment after chunking): auto keywords, auto-questions, tags from a prepared tag file, a per-chunk contextual summary, and typed metadata generation.
  - Indexer: full-text index plus a choice of field to embed (processed text, generated questions, or augmented context).
  - Dataset-level "PageRank" adds a constant to that dataset's hybrid score to prioritize it in multi-dataset retrieval.
  - Changing the embedding model triggers a dimension-compatibility check. — [RAGFlow docs: Dataset configuration](https://github.com/infiniflow/ragflow/blob/main/docs/guides/dataset/configuration.md)
- Metadata can be built in (`update_time`, `file_name`), generated by an LLM from typed field definitions, mapped from table columns, or entered manually. Changing the auto-metadata settings applies only to newly parsed documents; existing ones must be re-parsed. — [RAGFlow docs: Metadata management](https://github.com/infiniflow/ragflow/blob/main/docs/guides/dataset/metadata_management.md)
- Connectors by category:
  - Docs and wikis: Confluence, Notion, Feishu Wiki, Google Drive, OneDrive, SharePoint, Box, Dropbox, WebDAV, SeaFile.
  - Object stores: S3, GCS, R2, Azure Blob.
  - Databases: MySQL, PostgreSQL, BigQuery.
  - Code and project tools: GitHub, GitLab, Bitbucket, Azure DevOps, Jira, Asana.
  - Messaging and mail: Gmail, Outlook, IMAP, Teams, Slack, Discord.
  - Business apps: Salesforce, Airtable, Zendesk, Moodle.
  - Generic: REST API, RSS, Sitemap.

  — [RAGFlow docs: Data source categories](https://github.com/infiniflow/ragflow/blob/main/docs/guides/data_source/data_source_categories_and_selection.md)
- Sync behavior: the first sync imports everything in scope. Adds and changes arrive at the next refresh interval. Deletions are removed only if "sync deleted files" is enabled. Logs live under Logs > Data source. — [RAGFlow docs: Link and sync a data source](https://github.com/infiniflow/ragflow/blob/main/docs/guides/data_source/add_to_knowledge_base_and_sync.md)
- Permissions are coarse. Datasets, workflows, pipelines and memories have two sharing scopes, "Only me" and "Team". **There is no per-document ACL inherited from source systems.** — [RAGFlow docs: Resource sharing and permissions](https://github.com/infiniflow/ragflow/blob/main/docs/guides/team/resource_sharing/resource_sharing_and_permissions.md)
- The Retrieval Testing page offers:
  - Similarity threshold (default 20%).
  - Keyword-similarity weight (e.g. 0.7 full text / 0.3 vector).
  - Rerank model, with 64 to 256 rerank candidates.
  - Cross-language search and metadata conditions.
  - A per-file filter.

  The docs frame it as separating "content problem vs retrieval configuration problem". — [RAGFlow docs: Retrieval testing](https://github.com/infiniflow/ragflow/blob/main/docs/guides/dataset/retrieval_testing.md)
- Knowledge Compilation templates:
  - Graph, Tree (RAPTOR-like clustering, summarization and claim-extraction prompts), PageIndex, Mindmap and Timeline, each with Entity and Relation specifications.
  - Wiki, with an Entity mode or a Topic mode and blueprints (Brand, Engineering, General, Market).

  — [RAGFlow docs: Knowledge compilation templates](https://github.com/infiniflow/ragflow/blob/main/docs/guides/knowledge_compilation/built_in_templates_and_dedicated_configuration.md)

**Dify, "Dify Open Source License" (Apache-2.0 plus extra conditions, so not OSI)**
- Classic KB:
  - Chunk modes are General, or Parent-child with Paragraph or Full Doc parents. Full Doc processes only the first 10,000 tokens.
  - "The chunk mode cannot be changed once the knowledge base is created."
  - Parent-child requires the High Quality (embedding) index.

  — [Dify docs: Chunk settings](https://github.com/langgenius/dify-docs/blob/main/en/self-host/use-dify/knowledge/create-knowledge/chunking-and-cleaning-text.mdx); [GitHub langgenius/dify](https://github.com/langgenius/dify)
- Index methods:
  - High Quality offers vector, full-text or hybrid retrieval, plus a Q&A mode that generates Q&A pairs per segment and matches query to generated question ("Q to Q").
  - Economical uses an inverted index of 10 keywords per chunk with no token cost.
  - TopK defaults to 3 and score threshold to 0.5. These apply only with a rerank model enabled.

  — [Dify docs: Index method and retrieval settings](https://github.com/langgenius/dify-docs/blob/main/en/self-host/use-dify/knowledge/create-knowledge/setting-indexing-methods.mdx)
- Metadata fields are typed as String, Number or Time, with built-in fields disabled by default. — [Dify docs: Metadata](https://github.com/langgenius/dify-docs/blob/main/en/self-host/use-dify/knowledge/metadata.mdx)
- External Knowledge API contract: Dify POSTs `{knowledge_id, query, retrieval_setting{top_k, score_threshold}, metadata_condition{logical_operator, conditions[name, comparison_operator, value]}}` to `{endpoint}/retrieval`. A BYO retrieval service can therefore stand behind Dify. — [Dify docs: External Knowledge API](https://github.com/langgenius/dify-docs/blob/main/en/self-host/use-dify/knowledge/external-knowledge-api.mdx)
- Knowledge pipeline: Data Source (file upload, online drive, online documents such as Notion, web crawler such as Jina Reader or Firecrawl) → Extractor (Dify Extractor, Doc Extractor, or Unstructured from the Marketplace) → Chunker → Knowledge Base node. — [Dify docs: Knowledge pipeline orchestration](https://github.com/langgenius/dify-docs/blob/main/en/self-host/use-dify/knowledge/knowledge-pipeline/knowledge-pipeline-orchestration.mdx)
- New "Agent Knowledge Base" (cloud docs, beta): a reasoning model splits documents by meaning, writes section summaries, and builds a knowledge graph. Retrieval depths:
  - Fast: semantic plus keyword.
  - Deep: also follows the KG to related subjects.
  - Research: decomposes the question and uses section titles and summaries to choose sections.

  Coding agents can browse documents "like files in a folder" through the Dify CLI. — [Dify docs: Agent KB overview](https://github.com/langgenius/dify-docs/blob/main/en/cloud/use-dify/knowledge-base/overview.mdx); [Dify docs: Retrieval settings](https://github.com/langgenius/dify-docs/blob/main/en/cloud/use-dify/knowledge-base/retrieval-settings.mdx)
- Built-in eval loop, the best documented OSS pattern found:
  - "Golden questions" with expected chunks and all-or-any pass rules, importable from CSV (≤1 MB).
  - Golden questions become **Stale** when an expected chunk disappears (re-upload or sync) and **Paused** when its document is disabled.
  - "Bad cases" are classified as retrieval miss or low score. Production workflows that miss content open bad cases automatically.
  - Replay, promotion to golden, and full re-evaluation after each settings change.

  — [Dify docs: Test and tune retrieval](https://github.com/langgenius/dify-docs/blob/main/en/cloud/use-dify/knowledge-base/test-and-tune.mdx)

**Onyx (formerly Danswer): MIT core plus an "Onyx Enterprise License" for `ee/` directories**
- Positioning: "the knowledge/context layer for your team and AI agents" with 50+ connectors. It argues index-based retrieval is "more reliable, low latency, and low cost" than agents iterating over dozens of MCP servers. Access paths include an MCP server ("same access controls as the person running them"), a Slack/Discord bot, and a Chrome extension. The standard deployment adds vector+keyword indexes, background sync workers, model servers, Redis and MinIO. The README states CE (MIT) and EE editions. — [GitHub onyx-dot-app/onyx](https://github.com/onyx-dot-app/onyx); [Onyx LICENSE](https://github.com/onyx-dot-app/onyx/blob/main/LICENSE)
- The docs list 58 connectors plus an Ingestion API. Document Sets group content for agents and filters. Permission sync "requires the Enterprise Edition". — [Onyx docs: Connectors](https://docs.onyx.app/overview/core_features/connectors)
- Sync model:
  - Indexing every 30 minutes by default, with "Update Index" for deltas or "Full Re-index".
  - **Pruning** of documents deleted at source every 7 days by default.
  - Scheduled **permission sync** that also updates group membership, with propagation of "a few minutes to an hour".
  - An "Index Documents After" date cutoff.
  - Access types: Public, Specific Groups, or "Sync with the source". Changing the access type triggers a re-index.

  Connectors with permission syncing: Google Drive, Gmail, Confluence, Jira, Slack (indexed, not federated), GitHub, Box, Canvas, SharePoint (certificate auth), OneDrive, Teams, Outlook, Linear, HubSpot, YouTrack, Zoom. Salesforce does field-level hiding only. Permission sync is on Business, Enterprise and Cloud plans. — [Onyx docs: Connectors overview](https://docs.onyx.app/admins/connectors/overview)

**Open WebUI (custom "Open WebUI License" that requires keeping branding) and oikb (MIT)**
- Knowledge features:
  - "13 vector databases" (ChromaDB and PGVector maintained; Qdrant, Milvus, OpenSearch, Elasticsearch and others).
  - Hybrid BM25 plus vector with cross-encoder reranking.
  - Focused Retrieval vs Full Context modes.
  - Incremental directory sync, zip export, REST API, per-KB access settings.
  - Agentic tools under native function calling: `list_knowledge_bases`, `search_knowledge_bases`, `query_knowledge_files` (RAG), `grep_knowledge_files` (exact/regex with line numbers), `view_knowledge_file` with pagination, and a `kb_exec` shell (`ls`, `tree`, `cat -n`, `sed -n`, `grep`, `find`, `stat`). `kb_exec` "respects the same access control … files the user can't read are silently excluded".
  - Editing indexed text re-processes it in every KB that contains the file.

  — [Open WebUI docs: Knowledge](https://github.com/open-webui/docs/blob/main/docs/features/workspace/knowledge.mdx)
- RAG configuration:
  - Markdown-header splitting with a "Chunk Min Size Target" merge. The project claims a threshold of 1000 for 2000-char chunks "can reduce chunk counts by over 90% while improving accuracy" (vendor claim, no dataset given).
  - External knowledge sources (Qdrant, Milvus, pgvector) are queried live and must use the same embedding model as Open WebUI.

  — [Open WebUI docs: RAG](https://github.com/open-webui/docs/blob/main/docs/features/chat-conversations/rag/index.md); [GitHub open-webui/open-webui](https://github.com/open-webui/open-webui)
- oikb (409 stars, created 2026-05-20, MIT) syncs "47 supported sources" (directory, GitHub/Gitea, Confluence, S3, Zotero …) incrementally. It offers `diff` and `--dry-run`, cron or interval scheduling, webhooks (GitHub, GitLab, Gitea, Slack, Confluence), Prometheus `/metrics`, sync history, failure notifications, and an OpenAPI tool server so the LLM can trigger syncs. — [GitHub open-webui/oikb](https://github.com/open-webui/oikb)

**Graph and memory engines (KB-adjacent)**
- Microsoft GraphRAG (MIT) is described as a research project: "not an officially supported Microsoft offering". The README warns indexing "can be an expensive operation … start small", recommends prompt tuning, and says to re-run `graphrag init` between minor versions. — [GitHub microsoft/graphrag](https://github.com/microsoft/graphrag)
- The GraphRAG paper builds an entity KG plus pre-generated community summaries for global "sensemaking" questions over corpora around 1M tokens, improving comprehensiveness and diversity over vector RAG. — [Edge et al. 2024, arXiv:2404.16130](https://arxiv.org/abs/2404.16130)
- LightRAG (MIT) changelog:
  - 2026.05: four chunkers (Fix, Recursive, Vector, Paragraph); role-specific LLMs (EXTRACT, QUERY, KEYWORDS, VLM); RAG-Anything merged with MinerU and Docling parsing.
  - 2026.03: OpenSearch as a unified backend for all four storages.
  - 2025.11: RAGAS eval and Langfuse tracing; the API returns retrieved contexts.
  - 2025.08: reranker as default; document deletion with automatic KG regeneration.
  - 2025.03: citations.

  Default in-memory stores are "not for production". The embedding model cannot change after indexing. — [GitHub HKUDS/LightRAG](https://github.com/HKUDS/LightRAG)
- The LightRAG paper describes dual-level (low/high) graph+vector retrieval with an incremental update algorithm. — [Guo et al. 2024, arXiv:2410.05779](https://arxiv.org/abs/2410.05779)
- Graphiti (Apache-2.0):
  - Temporal "context graph" in which facts carry validity windows. Old facts are "invalidated — not deleted", giving bi-temporal history.
  - Every entity and edge traces to source "episodes" (provenance). Ontology can be prescribed through Pydantic types or learned.
  - Hybrid retrieval combines embeddings, BM25 and graph traversal.
  - Backends: Neo4j 5.26, FalkorDB, or Neptune plus OpenSearch Serverless; Kuzu is deprecated.
  - The README says query latency is "typically sub-second" vs GraphRAG's "seconds to tens of seconds" (vendor comparison).

  — [GitHub getzep/graphiti](https://github.com/getzep/graphiti)
- The Zep paper reports DMR 94.8% vs MemGPT 93.4%, LongMemEval accuracy gains "up to 18.5%", and 90% lower latency vs baselines (vendor-authored). — [Rasmussen et al. 2025, arXiv:2501.13956](https://arxiv.org/abs/2501.13956)
- Cognee (Apache-2.0):
  - Four operations: `remember`, `recall`, `improve` (apply feedback, bridge session lessons into the graph) and `forget`.
  - Custom ontologies; a "Company Brain" over docs, tickets and code; Claude Code and Codex memory plugins.
  - Multi-tenant access control by default (`ENABLE_BACKEND_ACCESS_CONTROL`). Can run "the whole memory layer on Postgres".
  - Local GLiNER extraction when no LLM key is set. COGX import from Mem0, Letta, Zep and Graphiti.

  — [GitHub topoteretes/cognee](https://github.com/topoteretes/cognee)
- The Cognee paper shows targeted tuning of chunking, graph construction, retrieval and prompts gives consistent but non-uniform gains on HotPotQA, 2Wiki and MuSiQue. — [Markovic et al. 2025, arXiv:2505.24478](https://arxiv.org/abs/2505.24478)
- Mem0 (Apache-2.0): an April 2026 algorithm with single-pass ADD-only extraction and multi-signal retrieval (semantic, BM25, entity). It reports LoCoMo 92.5 and LongMemEval 94.4, but the README says these "Scores reflect Mem0's managed platform, which includes proprietary optimizations not available in the open-source SDK". — [GitHub mem0ai/mem0](https://github.com/mem0ai/mem0)
- The 2025 Mem0 paper reports +26% relative LLM-judge score over OpenAI memory, 91% lower p95 latency, and >90% token savings vs full context. — [Chhikara et al. 2025, arXiv:2504.19413](https://arxiv.org/abs/2504.19413)
- Letta (Apache-2.0, 25,357 stars) is a stateful-agent platform. Its MemGPT origin is OS-style virtual context paging between memory tiers. — [GitHub letta-ai/letta](https://github.com/letta-ai/letta); [Packer et al. 2023, arXiv:2310.08560](https://arxiv.org/abs/2310.08560)
- MemoryOS: Apache-2.0, 1,620 stars, EMNLP 2025 oral. Short-, mid- and long-term personal memory tiers. — [GitHub BAI-LAB/MemoryOS](https://github.com/BAI-LAB/MemoryOS); [Kang et al. 2025, arXiv:2506.06326](https://arxiv.org/abs/2506.06326)
- PageIndex (MIT, 40,005 stars) does "vectorless, reasoning-based RAG". It builds a hierarchical tree index per document, which an LLM navigates. It claims its Page Search API cuts "97% token cost" (vendor claim) and offers a "PageIndex File System" for corpus scale. — [GitHub VectifyAI/PageIndex](https://github.com/VectifyAI/PageIndex)
- Earlier structure-aware methods:
  - RAPTOR (recursive cluster-and-summarize tree) gave +20% absolute on QuALITY with GPT-4. — [Sarthi et al. 2024, arXiv:2401.18059](https://arxiv.org/abs/2401.18059)

  - KAG (Ant Group) targets professional domains, including "expert rules" and numeric and temporal logic. — [Liang et al. 2024, arXiv:2409.13731](https://arxiv.org/abs/2409.13731)

### Inferences
- For an Apache-2.0/MIT toolkit, RAGFlow is the feature benchmark: templates by document type, title-path chunking, extractor enrichment, compilation artifacts and a retrieval-test UI. Dify's golden-question and bad-case loop is the eval UX to copy. Onyx's indexing/pruning/permission-sync triad is the sync model to copy. **Free source-ACL sync is the opening**: in permissive OSS it is either missing (RAGFlow, Dify, Open WebUI) or paid (Onyx EE). PrivateGPT's connectors are paid, and R2R, which had collections, is dormant.
- Wiki, tree and topic compilation (RAGFlow), Dify's agent KB, and Open WebUI's `kb_exec` filesystem tools all point the same way: the KB is no longer only top-k chunks. It is a navigable artifact (topic pages, section trees, files) plus a search tool. This suits SOPs and policies, where agents need to read a whole section in order.
- Churn is high. Verba was archived, Quivr and SurfSense pivoted, R2R went dormant, and LlamaCloud Index v1 was deprecated. A toolkit should own its data model and treat these projects as optional adapters, not foundations.

### Gaps
- Not verified: the Haystack, txtai and Khoj connector lists; Letta's filesystem tools (the docs URL returned 404); Open WebUI per-document ACL semantics beyond KB-level access. AnythingLLM's and Khoj's sync/pruning behavior was not checked.
- No independent benchmark compares these platforms' KB retrieval quality on the same corpus. EnterpriseRAG-Bench (section 4) is the closest; its leaderboard was not read.

## 2. Search engines for KBs: hybrid features and licenses

### Takeaway
Every serious engine now offers native hybrid lexical+vector retrieval with rank fusion. They differ in license, operations weight, and how fusion is tuned. For an embeddable, permissively licensed KB:
- **Postgres + pgvector** covers small and medium KBs with RLS-style filtering. ParadeDB adds real BM25 but is AGPL.
- **OpenSearch** (Apache-2.0) is the safest full-featured choice: hybrid query with RRF or normalization, document-level filters, and connectors via Haystack/LightRAG backends.
- **Qdrant**, **Milvus** and **LanceDB** (all Apache-2.0) suit vector-first stacks with built-in BM25/sparse.

Vespa's own benchmark shows BM25 alone beats a small dense model on NFCorpus and that RRF is not always the best fusion. Fusion must be tuned on the KB's own eval set.

  - Argues Postgres `ts_rank` "doesn't understand global corpus statistics". pg_search adds BM25 as an index type.

- Older evidence (2024) that blending dense and sparse retrievers beats either alone on NQ and TREC-COVID. — [Sawarkar et al. 2024, arXiv:2404.07220](https://arxiv.org/abs/2404.07220)

### Inferences
- A KB toolkit should ship one storage abstraction with two reference backends: Postgres (pgvector plus native FTS, optionally ParadeDB for users who accept AGPL) for single-node installs, and OpenSearch for scale. Everything else should go through adapters. Elasticsearch's AGPL option and Weaviate/Meilisearch enterprise carve-outs need license notes for embedders.
- Exact identifiers (CVE codes, versions, SKUs, policy numbers, error codes) are common in SOP and policy KBs. Lexical search with field boosts is mandatory there, not optional (see Elastic's case, section 3).

### Gaps
- No head-to-head benchmark of these engines on an enterprise-KB workload was found, and Tantivy/Quickwit KB features were not examined. Document-level-security implementations were checked only for Elastic (section 4), not OpenSearch or Qdrant.

## 3. Engineering case studies with numbers

### Takeaway
Real internal-KB and support-agent builds agree on six lessons. **Source document quality dominates answer quality**: Uber, DoorDash and Elastic all built document-quality loops. **Hybrid BM25+dense with metadata enrichment** beats pure vectors (Uber, Elastic, Dropbox). **Structure-preserving representations** win for policies and SOPs: Uber's table-aware chunking, LinkedIn's ticket-section KG, Airbnb's Intent-Context-Action pseudocode. **LLM judges calibrated against human labels** are the scalable eval (Dropbox, Shopify, Uber, DoorDash). **Fewer, broader retrieval tools** beat many connector-specific tools (Dropbox, Shopify). **Incremental, hash-based re-embedding and metadata-only patches** control cost (Notion).

### Cited Findings

**Uber Genie (internal on-call copilot)**
- Architecture:
  - Scrapes Engwiki, internal Stack Overflow and requirement docs.
  - Spark jobs chunk with LangChain and embed with an OpenAI model through PySpark UDFs.
  - Vectors go to Terrablob and Sia, Uber's in-house vector DB. A Knowledge Service serves retrieval.
- Usage: 154 Slack channels since Sept 2023, >70,000 questions answered, 48.9% helpfulness rate, ~13,000 engineering hours saved (company estimate; post dated 2024-10-10).
- Feedback and eval:
  - Users mark each answer Resolved, Helpful, Not Helpful or Not Relevant. Feedback flows Kafka → Hive → dashboard.
  - An LLM judge scores hallucination and relevancy.
  - A separate **LLM document evaluator** scores each KB document and returns improvement suggestions.
- Security: only "widely accessible, pre-curated" sources are embedded.

— [Uber Engineering: Genie](https://www.uber.com/blog/genie-ubers-gen-ai-on-call-copilot/)
- Enhanced Agentic RAG (2025-05-29) for 40+ security and privacy policy PDFs, tested against a golden set of 100+ SME queries:
  - PDF loaders broke multi-page tables. Policies moved to Google Docs (HTML plus native access control), and a custom loader with LLM table-to-Markdown and table-aware chunking was built.
  - Enrichment adds a document summary (applied to every chunk) plus per-chunk FAQs and keywords.
  - Agents: a Query Optimizer, a Source Identifier that narrows to candidate documents, and a Post-Processor that dedupes and orders chunks by document position.
  - Retrieval is the union of BM25 (over summaries, FAQs and keywords) and vector search, restricted to the identified documents.
  - An LLM judge scores 0–5 against SME answers. Results: relative +27% acceptable answers and −60% incorrect advice. Experiment turnaround went from weeks to minutes.

  — [Uber Engineering: Enhanced Agentic-RAG](https://www.uber.com/en-GB/blog/enhanced-agentic-rag/)

**LinkedIn customer-service KG-RAG (SIGIR 2024)**
- Construction:
  - Each ticket becomes an intra-issue tree of sections (Summary, Description, Priority …), parsed by rules plus an LLM guided by a YAML section template.
  - Explicit inter-ticket links come from Jira fields. Implicit links come from title-embedding similarity.
  - Text nodes are embedded with E5/BERT into Qdrant. Query entities are matched to section nodes, then an LLM writes Cypher (Neo4j) to fetch the subgraph, with fallback to text retrieval.
- Results:
  - MRR 0.522→0.927 (+77.6%); Recall@1 0.40→0.86; BLEU 0.057→0.377.
  - Deployed ~6 months: median resolution time 7→5 hours (−28.6%), mean 40→15 hours.
- Limits: the golden set size is not reported and the template is manual.

— [Xu et al. 2024, arXiv:2404.17723](https://arxiv.org/abs/2404.17723) ([HTML](https://arxiv.org/html/2404.17723v2))

**Airbnb, Intent-Context-Action (ICA) policy representation (COLING 2025 Industry)**
- Converts support policies and workflows into pseudocode: Intent = root condition, Context = internal if-else nodes, Action = leaf. Action text is replaced by IDs from an action map.
- Conversion pipeline: HTML tree parse → binary classifier labels condition vs action → decision tree → ICA pseudocode → human review. One-time legacy conversion "took months".
- Runtime: retrieval matches the query to each workflow's Intent; context comes from backend APIs; the LLM outputs an action ID.
- Offline accuracy: rich text 0.57 → ICA 0.70 → ICA+CoT 0.92. Mistral-7B with ICA+CoT went from 0.16 to 0.70; fine-tuned it reached 0.85 at 4.5 s vs 46.4 s for the large model.
- Online: −13% manual processing time with fine-tuned Mistral-7B. Internal experiments only, "not applied to Airbnb products".

— [Su et al. 2025, arXiv:2510.10331](https://arxiv.org/abs/2510.10331) ([HTML](https://arxiv.org/html/2510.10331v1))

**DoorDash Dasher support RAG (2024)**
- Pipeline: condense the conversation → search KB articles and past resolved cases → generate.
- Two-tier guardrail: a cheap sliding-window semantic-similarity check, then an LLM groundedness check only on flagged responses. A heavier guardrail was dropped for latency and cost.
- Reported numbers (company, no methodology): −90% hallucinations and −99% severe compliance issues.
- LLM Judge on five dimensions: retrieval correctness, accuracy, grammar, coherence, relevance. Judge findings drive KB article rewrites.
- Process lessons: Promptfoo regression tests on every prompt change, a fallback to human agents, and multilingual output identified as a weakness.

— [ZenML LLMOps DB summary of DoorDash post](https://www.zenml.io/llmops-database/llm-based-dasher-support-automation-with-rag-and-quality-controls) (the primary careersatdoordash.com post returned 403)

**Dropbox Dash (universal search to agentic context engine)**
- Pipeline:
  - Custom connectors, each handling an app's rate limits and its own ACL model.
  - Content normalized to Markdown, with CLIP for images, transcription for audio, and scene understanding for video.
  - Hybrid BM25 plus dense; the team calls BM25 "strong on its own". Ranking passes enforce per-user ACLs.
- Federated vs index tradeoff: the index wins on quality and latency but costs connector work, freshness under rate limits, and hosting.
- Knowledge graph: canonical person IDs across apps. **Not stored in a graph DB** (latency and query-pattern problems). Instead it is materialized asynchronously into "knowledge bundles" that go through the same chunk/embed pipeline.
- MCP lessons:
  - Context is capped at ~100k tokens. One MCP-based query could take up to 45 s vs seconds on the raw index.
  - Replaced 5–10 retrieval tools with one "super tool"; added sub-agents with a classifier.
- Eval:
  - NDCG with an LLM judge rating 1–5.
  - Judge–human disagreement started at 8% and fell with explanation prompts, o3, and "RAG as a judge" (the judge fetches context for acronyms).
  - DSPy optimizes 30+ prompts edited by 5–15 engineers. (2026-01-28)

— [Dropbox Tech: Knowledge graphs, MCP and DSPy in Dash](https://dropbox.tech/machine-learning/vp-josh-clemm-knowledge-graphs-mcp-and-dspy-dash)
- Follow-up post (2025-11-17): one retrieval tool backed by the universal index replaced per-app tools (Confluence, Google Docs, Jira). The Dash MCP server exposes one retrieval tool. Query construction moved to a dedicated search sub-agent. No quantitative results. — [Dropbox Tech: Context engineering in Dash](https://dropbox.tech/machine-learning/how-dash-uses-context-engineering-for-smarter-ai)

**Notion vector search (Q&A over workspaces, 2023–2026)**
- Pipeline: Spark offline batch plus Kafka online path (sub-minute). Pages are split into spans, sharded by workspace ID, with "generation" routing.
- Change detection:
  - Each span stores author and permission metadata. A permission change is a metadata PATCH with no re-embedding.
  - Two 64-bit xxHash values per span (text and metadata), stored per page in DynamoDB, cut data volume by ~70%.
- Infrastructure progression: pod clusters → serverless (May 2024, −50% from peak) → turbopuffer (−60% search spend, −35% EMR, p50 70–100 ms → 50–70 ms) → Ray on Anyscale for embeddings (projected >90% infra-cost cut, still rolling out).
- Overall: ~10x scale at ~1/10th cost; 600x daily onboarding capacity (post dated 2026-02-19).

— [Notion: Two years of vector search](https://www.notion.com/blog/two-years-of-vector-search-at-notion)

**Elastic Support Assistant (2024)**
- Corpus: >300,000 documents (support articles plus crawled docs and blogs).
- Failures: wrong product versions, near-duplicate article versions, multi-CVE queries, and weak `summary` fields (first N characters of the body).
- Fixes:
  - Regex version extraction with boosting on a `version` field; CVE title boosting.
  - `collapse` on a `slug` field for dedup.
  - GPT-4 enrichment (subtitle, summary, answered questions, tags) with ELSER embeddings on those fields.
  - Hybrid BM25 + ELSER.
- Eval: 12 curated queries, Ranking Evaluation API, P@3. Average P@K +78.41% with no regressions.

— [Elastic Search Labs: Tuning RAG search for relevance](https://www.elastic.co/search-labs/blog/elser-rag-search-for-relevance)

**Shopify Sidekick (2025-08-26)**
- Tool sprawl: 0–20 tools have clear boundaries, 20–50 have blurry ones, and 50+ offer multiple ways to do the same task ("Death by a Thousand Instructions").
- Fix: **Just-in-Time instructions** returned with tool results instead of in the system prompt. This also preserves the prompt cache.
- Eval:
  - Ground Truth Sets sampled from real conversations replace curated golden sets.
  - Judge Cohen's κ went from 0.02 to 0.61 vs a human baseline of 0.69. An LLM merchant simulator runs pre-production tests.
  - Reward hacking observed: opt-out answers, tag misuse, schema violations.

— [Shopify Engineering: Building production-ready agentic systems](https://shopify.engineering/building-production-ready-agentic-systems)

**Grab SpellVault (2025-11-21)**

— [Grab Engineering: SpellVault's evolution](https://engineering.grab.com/spellvault-evolution-beyond-llm)

**Research experience reports**
- NVIDIA built three enterprise chatbots (IT/HR benefits, earnings, general content). ### Inferences
- Policy, SOP and rule content needs a **structured representation in addition to chunks**. ICA decision trees, section trees with heading paths, and table-intact chunks all beat flat text in the cases above. The measured gains (Airbnb +0.35 accuracy; LinkedIn +77.6% MRR) are far larger than typical embedding-model swaps.
- "Document quality evaluator" loops recur (Uber's per-document scorer, DoorDash's judge-driven article rewrites, Elastic's "curate low-value pages"). A KB toolkit should treat KB linting (stale, duplicate, contradictory or underspecified articles) as a first-class output.
- Agent-facing surface: one or a few broad search tools plus "read section/file" tools, with instructions delivered just in time. Not dozens of per-connector tools.

### Gaps
- No primary-source engineering write-ups with numbers were found for Ramp, Booking.com, Canva, Stripe (internal support), Pinterest (knowledge-search part), or Airbnb (production). Searches surfaced only secondary or unrelated material. The DoorDash and Vimeo primaries were blocked (403); their facts come from ZenML summaries.
- Most numbers are company-reported without baselines (DoorDash −90%, Uber hours saved, Klarna). Only LinkedIn and Airbnb give methodology, and both are single-company internal studies.

## 4. Practical patterns: connectors, sync and ACL propagation, chunk/metadata schemas, evaluation, feedback, cost

### Takeaway
The production pattern is consistent across sources:
- **Index-based ingestion** (not federated search) with three independent loops: content delta sync, deletion pruning, and permission sync.
- **ACLs resolved at ingest** to stable principal IDs on every chunk, and **pre-filtered at query time**, never post-filtered or left to the prompt.
- Stale-ACL windows that are explicit, with fail-closed behavior.
- **Hash-based change detection**, so permission-only changes patch metadata without re-embedding.
- **Golden-question regression suites plus calibrated LLM judges**, fed by production misses and user feedback.

### Cited Findings
- Connector licensing: the Elastic `connectors` framework (with DLS) is ELv2, and Airbyte's top-level LICENSE is ELv2. Permissive alternatives are Unstructured's `unstructured-ingest` (Apache-2.0) and the per-platform connectors in RAGFlow (Apache-2.0), oikb (MIT) and Onyx CE (MIT). — [GitHub elastic/connectors](https://github.com/elastic/connectors); [GitHub airbytehq/airbyte](https://github.com/airbytehq/airbyte); [GitHub Unstructured-IO/unstructured-ingest](https://github.com/Unstructured-IO/unstructured-ingest)
- Elastic DLS reference pattern:
  - Connectors write `_allow_access_control` on each document plus a per-source access-control index (`.search-acl-filter-<index>`) holding each user's identities and groups.
  - At sign-in the backend mints a per-user API key whose role descriptor embeds the DLS query. Keys must be recreated when permissions change.
  - Without DLS, "all documents indexed … will be visible to all users with access". Confluence DLS was Cloud-only.

  — [Elastic docs: DLS end-to-end guide](https://www.elastic.co/docs/reference/search-connectors/es-dls-e2e-guide)
- Microsoft ISE pattern for SharePoint ACLs (2026-04-30):
  - Graph `Sites.Selected` least-privilege access. Effective ACLs (inheritance resolved) are computed at ingest.
  - Principals are stored as Entra object GUIDs, not emails. `allowedUsers` and `allowedGroups` are stored per chunk.
  - Query-time trimming on caller ID and groups; "post-retrieval filtering is an anti-pattern".
  - Revoked users can see content until the next ingestion run. Mitigations: schedules, webhooks, and communicating the delay.

  — [Microsoft ISE Dev Blog: Propagating SharePoint permissions to RAG](https://devblogs.microsoft.com/ise/?p=16628)
- Cross-source ACL pitfalls (2026):
  - Change feeds: Drive Changes API (ACL changes visible only to certain principals), SharePoint delta queries, Confluence polling plus webhooks. Run periodic reconciliation for inherited permissions, with a fail-closed freshness threshold.
  - Entra token group-claim overage at 200 groups (JWT) and 150 (SAML).
  - Confluence page restrictions inherit from ancestors.
  - Use Graph `grantedToV2`. Postgres RLS can be bypassed by superusers and `BYPASSRLS` roles.
  - "The model is not your access control."

  — [Wavect: Permission-aware RAG across SharePoint, Confluence, Drive](https://wavect.io/blog/rag-permissions-sharepoint-confluence-drive/)
- Onyx's defaults: 30-minute indexing, 7-day pruning, and permission sync with propagation of minutes to an hour, all as separate jobs. — [Onyx docs: Connectors overview](https://docs.onyx.app/admins/connectors/overview)
- Notion: metadata-only permission updates without re-embedding, and text and metadata hashes per span. — [Notion: Two years of vector search](https://www.notion.com/blog/two-years-of-vector-search-at-notion)
- Embedding or chunking changes force full re-embeds (GitLab). Dify locks chunk mode after creation. LightRAG and Open WebUI external sources require a fixed embedding model. — [GitLab Handbook](https://handbook.gitlab.com/handbook/engineering/architecture/design-documents/gitlab_rag/); [Dify docs: Chunk settings](https://github.com/langgenius/dify-docs/blob/main/en/self-host/use-dify/knowledge/create-knowledge/chunking-and-cleaning-text.mdx); [GitHub HKUDS/LightRAG](https://github.com/HKUDS/LightRAG)
- Chunk context enrichment: Anthropic's contextual retrieval (2024-09-19) prepends LLM-written context to each chunk.

  | Setup | Failed-retrieval rate (top-20) | Reduction vs baseline |
  |---|---|---|
  | Baseline | 5.7% | — |
  | Contextual embeddings | 3.7% | −35% |
  | + contextual BM25 | 2.9% | −49% |
  | + reranking | 1.9% | −67% |

  Generating the context costs ~$1.02 per million document tokens with prompt caching. For KBs under 200k tokens, skip RAG and put the whole KB in the prompt. — [Anthropic: Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)
- Late chunking embeds the full document before pooling per chunk, preserving context without LLM cost. — [Günther et al. 2024, arXiv:2409.04701](https://arxiv.org/abs/2409.04701)
- Article structure standards usable as a KB schema:
  - KCS articles have Issue (requestor's words), Environment, Resolution (numbered steps), optional Cause plus a "Cause Test", and an "Internal Resolution" hidden from requestors. Metadata covers reuse counts, versions, audience and quality. — [KCS v6 Practices Guide: Article structure](https://library.serviceinnovation.org/KCS/KCS_v6/KCS_v6_Practices_Guide/030/040/010/020)
  - DITA information types: concept, task (general/strict/machinery), reference, troubleshooting, glossentry (one sense of one term, with acronyms). — [OASIS DITA 1.3 information types](https://docs.oasis-open.org/dita/dita/v1.3/os/part2-tech-content/archSpec/technicalContent/dita-technicalContent-InformationTypes.html)
  - Diátaxis: tutorials, how-to guides, reference, explanation. — [Diátaxis](https://diataxis.fr/)
  - SKOS for glossaries: `prefLabel`, `altLabel` (synonyms, acronyms), `hiddenLabel` (misspellings, search only), `definition`, `scopeNote`, `broader`/`narrower`/`related`, `exactMatch`/`closeMatch` (W3C 2009). — [W3C SKOS Primer](https://www.w3.org/TR/skos-primer/)
- Evaluation:
  - Benchmarks and frameworks: EnterpriseRAG-Bench (MIT; ~500k synthetic docs across Slack, Gmail, Linear, Drive, HubSpot, Fireflies, GitHub, Jira, Confluence; 500 questions in 10 categories including Conflicting Info, Completeness, Constrained and Info Not Found, plus 100 metadata-dependent questions; realistic noise such as near-duplicates and outdated info; internal jargon). — [GitHub onyx-dot-app/EnterpriseRAG-Bench](https://github.com/onyx-dot-app/EnterpriseRAG-Bench); [Sun et al. 2026, arXiv:2605.05253](https://arxiv.org/abs/2605.05253)
  - Ragas offers reference-free metrics (Apache-2.0, 16,247 stars, last push 2026-02-24, so slowing). — [Es et al. 2023, arXiv:2309.15217](https://arxiv.org/abs/2309.15217); [GitHub explodinggradients/ragas](https://github.com/explodinggradients/ragas)
  - ARES uses synthetic data plus small LM judges plus prediction-powered inference with "a few hundred human annotations". — [Saad-Falcon et al. 2023, arXiv:2311.09476](https://arxiv.org/abs/2311.09476)
  - Tooling licenses: DeepEval Apache-2.0 (19,319 stars); promptfoo MIT (26,870 stars, used by DoorDash for prompt regression); Langfuse (copyright "ClickHouse, Inc.", open core); Arize Phoenix ELv2. — [GitHub confident-ai/deepeval](https://github.com/confident-ai/deepeval); [GitHub promptfoo/promptfoo](https://github.com/promptfoo/promptfoo); [GitHub langfuse/langfuse](https://github.com/langfuse/langfuse); [GitHub Arize-ai/phoenix](https://github.com/Arize-ai/phoenix)
- Feedback loops in production:
  - Uber: Resolved/Helpful/Not Helpful/Not Relevant buttons → Kafka → Hive. — [Uber Genie](https://www.uber.com/blog/genie-ubers-gen-ai-on-call-copilot/)
  - Dify: auto-opened bad cases when apps miss content. — [Dify docs: Test and tune](https://github.com/langgenius/dify-docs/blob/main/en/cloud/use-dify/knowledge-base/test-and-tune.mdx)
  - DoorDash: open-ended judge → clustered issues → permanent monitors. — [ZenML/DoorDash](https://www.zenml.io/llmops-database/llm-based-dasher-support-automation-with-rag-and-quality-controls)
- Cost data points:
  - Notion: −70% data volume from hashing; ~90% overall cost reduction at 10x scale. — [Notion](https://www.notion.com/blog/two-years-of-vector-search-at-notion)
  - Contextual retrieval: $1.02 per M tokens one-time. — [Anthropic](https://www.anthropic.com/news/contextual-retrieval)
  - GraphRAG: "expensive", start small. — [GitHub microsoft/graphrag](https://github.com/microsoft/graphrag)
  - Dropbox: graph data materialized as bundles instead of a runtime graph DB, for latency. — [Dropbox Tech](https://dropbox.tech/machine-learning/vp-josh-clemm-knowledge-graphs-mcp-and-dspy-dash)

### Inferences
- The ACL model should be built into the core chunk schema from day one: `acl.allow_principals[]`, `acl.deny_principals[]`, `acl.source_version` and `acl.synced_at`. Enforcement belongs in the retrieval service as a mandatory pre-filter. Permission sync is a separate job from content sync, with per-source change feeds plus reconciliation sweeps.
- Store **text_hash, metadata_hash and acl_hash** per chunk. They make incremental re-embedding, cheap ACL patches, and golden-question staleness detection (Dify's "Stale") mechanical.
- KCS, DITA and SKOS give an established, explainable typed-article schema. Use them instead of inventing one.

### Gaps
- No OSS project was found that implements end-to-end ACL sync for Confluence, SharePoint, Drive and Slack under a permissive license (Onyx EE is paid; Elastic connectors are ELv2). Airbyte's permission-transfer mechanics were not documented in what was read.
- Concrete per-query cost figures for agentic multi-step retrieval (e.g. RAGFlow Ultra mode, Dify Research depth) were not published.

## 5. Recommended end-to-end blueprint for a searchable agent KB

### Takeaway
Build a **compiler-style pipeline**: connectors → canonical documents → typed knowledge units (article, procedure, rule, glossary term, FAQ, ticket resolution) → multi-view indexes (lexical, dense, section tree, entity/topic graph materialized as text bundles) → a small set of agent tools (search, read, lookup term, find procedure/rule, related). Every unit carries ACLs, provenance, version and validity. A golden-question regression suite and a KB lint report gate every change. Each choice below is backed by the evidence above.

### Cited Findings (evidence behind each component)
**A. Ingestion and sync**
- Use index-based ingestion, not federated search. It gives quality and latency at the cost of connector work. — [Dropbox Tech](https://dropbox.tech/machine-learning/vp-josh-clemm-knowledge-graphs-mcp-and-dspy-dash); [Onyx README](https://github.com/onyx-dot-app/onyx)
- Run three loops per connector: delta index (≈30 min), prune deletions (≈7 days), permission sync (≈hourly). — [Onyx docs](https://docs.onyx.app/admins/connectors/overview)
- Use webhooks where available: Zendesk at Vimeo; GitHub, GitLab, Confluence and Slack in oikb. Add `diff`/dry-run and Prometheus metrics. — [ZenML/Vimeo](https://www.zenml.io/llmops-database/building-an-ai-powered-help-desk-with-rag-and-model-evaluation); [oikb](https://github.com/open-webui/oikb)
- Keep every version and make the index rebuildable from storage. — [Quivr](https://github.com/QuivrHQ/quivr)

**B. Parsing and structuring**
- Use type-specific templates (Manual, Laws, Q&A, Table) and title-path chunking that keeps `Part > Chapter > Section` paths, with tables kept intact plus context windows. — [RAGFlow config](https://github.com/infiniflow/ragflow/blob/main/docs/guides/dataset/configuration.md); [Uber EAg-RAG](https://www.uber.com/en-GB/blog/enhanced-agentic-rag/)
- Convert policies and SOPs to decision-tree, ICA-style pseudocode with action IDs, plus human review. — [Airbnb ICA](https://arxiv.org/abs/2510.10331)
- Parse ticket and case history into section trees with explicit and implicit links. — [LinkedIn KG-RAG](https://arxiv.org/abs/2404.17723)

**C. Data model (typed knowledge units)**
- Article and troubleshooting units follow KCS fields: issue, environment, resolution, cause, internal_resolution. — [KCS](https://library.serviceinnovation.org/KCS/KCS_v6/KCS_v6_Practices_Guide/030/040/010/020)
- Procedures follow DITA task fields: prereqs, steps, result. Concepts and references follow the matching DITA types. — [DITA](https://docs.oasis-open.org/dita/dita/v1.3/os/part2-tech-content/archSpec/technicalContent/dita-technicalContent-InformationTypes.html)
- Glossary entries use SKOS: `prefLabel`, `altLabel`, `hiddenLabel`, `definition`, `broader`/`narrower`/`related`. — [SKOS](https://www.w3.org/TR/skos-primer/)
- Rules have intent, conditions and action IDs. — [Airbnb ICA](https://arxiv.org/abs/2510.10331)
- Temporal validity windows (`valid_from`, `valid_to`) apply to facts and rules, with supersession instead of deletion and provenance to source episodes. — [Graphiti](https://github.com/getzep/graphiti)
- Typed metadata (string, number, time) supports filtering. — [Dify metadata](https://github.com/langgenius/dify-docs/blob/main/en/self-host/use-dify/knowledge/metadata.mdx); [RAGFlow metadata](https://github.com/infiniflow/ragflow/blob/main/docs/guides/dataset/metadata_management.md)
- ACL fields use stable principal IDs. — [Microsoft ISE](https://devblogs.microsoft.com/ise/?p=16628)

**D. Enrichment**
- Per chunk: a doc summary, generated FAQs/questions, keywords and tags. Index the generated questions for Q-to-Q matching. — [Uber EAg-RAG](https://www.uber.com/en-GB/blog/enhanced-agentic-rag/); [RAGFlow extractor](https://github.com/infiniflow/ragflow/blob/main/docs/guides/dataset/configuration.md); [Dify Q&A mode](https://github.com/langgenius/dify-docs/blob/main/en/self-host/use-dify/knowledge/create-knowledge/setting-indexing-methods.mdx)
- Contextual chunk prefixes (~$1/M tokens). — [Anthropic](https://www.anthropic.com/news/contextual-retrieval)
- AI-generated summary fields where native summaries are weak. — [Elastic](https://www.elastic.co/search-labs/blog/elser-rag-search-for-relevance)

**E. Indexes**
- Hybrid BM25 plus dense with field boosts for identifiers (versions, CVEs, policy IDs), dedup via collapse on a canonical slug, and a reranker. — [Elastic](https://www.elastic.co/search-labs/blog/elser-rag-search-for-relevance); [Qdrant hybrid](https://qdrant.tech/documentation/concepts/hybrid-queries/); [OpenSearch hybrid](https://github.com/opensearch-project/documentation-website/blob/main/_query-dsl/compound/hybrid.md)
- Tune fusion on your eval set; RRF is not always best. — [Vespa tutorial](https://docs.vespa.ai/en/learn/tutorials/hybrid-search.html)
- Parent-child and section trees for reading context. — [Dify chunking](https://github.com/langgenius/dify-docs/blob/main/en/self-host/use-dify/knowledge/create-knowledge/chunking-and-cleaning-text.mdx); [Haystack AutoMergingRetriever](https://docs.haystack.deepset.ai/docs/retrievers); [PageIndex](https://github.com/VectifyAI/PageIndex)
- Entity and topic graph materialized as text "bundles" or wiki pages through the same index, not a runtime graph DB. — [Dropbox](https://dropbox.tech/machine-learning/vp-josh-clemm-knowledge-graphs-mcp-and-dspy-dash); [RAGFlow compilation](https://github.com/infiniflow/ragflow/blob/main/docs/guides/knowledge_compilation/built_in_templates_and_dedicated_configuration.md)
- Reference backends: Postgres (pgvector plus FTS or ParadeDB) or OpenSearch. — section 2 sources

**F. Agent tools**
- Prefer one broad `search_kb` (hybrid, ACL-filtered, metadata filters) over per-source tools. — [Dropbox](https://dropbox.tech/machine-learning/how-dash-uses-context-engineering-for-smarter-ai); [Shopify](https://shopify.engineering/building-production-ready-agentic-systems)
- Add `read_unit`/`read_section` with pagination, exact `grep_kb`, and `list/browse` tools. — [Open WebUI knowledge tools](https://github.com/open-webui/docs/blob/main/docs/features/workspace/knowledge.mdx)
- Expose over MCP with the caller's permissions. — [Onyx](https://github.com/onyx-dot-app/onyx); [Grab SpellVault](https://engineering.grab.com/spellvault-evolution-beyond-llm)
- Publish Markdown views of units (Stripe's `.md` pattern). — [Stripe](https://docs.stripe.com/building-with-llms)
- Return just-in-time instructions with tool results. — [Shopify](https://shopify.engineering/building-production-ready-agentic-systems)
- Use a search sub-agent for query construction. — [Dropbox](https://dropbox.tech/machine-learning/how-dash-uses-context-engineering-for-smarter-ai)

**G. Evaluation and feedback**
- Golden questions with expected units, stale and paused states, a bad-case queue, and re-evaluation on every config change. — [Dify test and tune](https://github.com/langgenius/dify-docs/blob/main/en/cloud/use-dify/knowledge-base/test-and-tune.mdx)
- Retrieval metrics (P@k, NDCG, MRR) plus an LLM judge calibrated to human labels (κ, disagreement %). — [Elastic](https://www.elastic.co/search-labs/blog/elser-rag-search-for-relevance); [Dropbox](https://dropbox.tech/machine-learning/vp-josh-clemm-knowledge-graphs-mcp-and-dspy-dash); [Shopify](https://shopify.engineering/building-production-ready-agentic-systems)
- Groundedness guardrail tiers. — [DoorDash/ZenML](https://www.zenml.io/llmops-database/llm-based-dasher-support-automation-with-rag-and-quality-controls)
- Document-quality scoring. — [Uber Genie](https://www.uber.com/blog/genie-ubers-gen-ai-on-call-copilot/)
- Benchmark on EnterpriseRAG-Bench categories (conflicting info, completeness, not found). — [EnterpriseRAG-Bench](https://github.com/onyx-dot-app/EnterpriseRAG-Bench)
- Prompt regression in CI. — [promptfoo](https://github.com/promptfoo/promptfoo)

**H. Cost controls**
- Per-chunk text, metadata and ACL hashes; metadata PATCH for ACL changes. — [Notion](https://www.notion.com/blog/two-years-of-vector-search-at-notion)
- Plan for full re-embeds on model or chunking changes. — [GitLab](https://handbook.gitlab.com/handbook/engineering/architecture/design-documents/gitlab_rag/)
- Skip RAG for KBs under 200k tokens. — [Anthropic](https://www.anthropic.com/news/contextual-retrieval)
- Make LLM graph extraction optional and scoped. — [GraphRAG README](https://github.com/microsoft/graphrag)

### Inferences
Concrete blueprint, synthesized from the evidence above:

1. **Canonical store** (Postgres plus object storage): `source_document` (connector, external_id, uri, version, content_hash, fetched_at, deleted_at), `knowledge_unit`, `chunk`, `principal`, `acl_entry`, `sync_run`, `golden_question`, `eval_run`, `feedback`.
2. **Knowledge unit types and key fields.**
   - Shared fields: `unit_id`, `type`, `title`, `heading_path`, `body_md`, `summary`, `generated_questions[]`, `keywords[]`, `tags[]`, `owner`, `audience` (internal/external), `status` (draft/validated/archived, as in KCS), `valid_from`/`valid_to`, `supersedes`, `source_refs[]` (doc_id, version, char/page span), `acl{allow[], deny[], synced_at}`, `hashes{text, meta, acl}`.
   - Type-specific fields:
     - `article`: KCS issue, environment, resolution, cause.
     - `procedure`: prereqs, numbered steps with optional tool or action IDs, expected result, rollback.
     - `rule`/`policy_clause`: intent, conditions (structured predicates plus original text), action_id or obligation, exceptions, effective dates, jurisdiction or scope.
     - `term`: SKOS labels, definition, broader, narrower, related.
     - `faq`, `case_resolution`: from tickets, with LinkedIn-style section tree and links.
3. **Indexes**: (a) BM25 with field boosts on title, keywords, identifiers and altLabels; (b) dense on body, summary and generated questions (multi-vector optional); (c) section tree per document for navigation; (d) entity/topic pages compiled into units so they are searchable; (e) a term dictionary for query expansion (altLabel/hiddenLabel → prefLabel). Fusion uses weighted RRF tuned on the golden set, followed by a cross-encoder rerank and dedup by canonical slug.
4. **Agent tools (MCP)**: `search_kb(query, filters, types, k)`, `read(unit_id | doc_id, section, page)`, `grep_kb(pattern, scope)`, `define(term)`, `find_procedure(task)`, `check_rules(intent, context{})` (returns candidate rule clauses with conditions to evaluate), `related(unit_id)`, `cite(unit_id, span)`. All tools are ACL-filtered by the caller identity. Answers must cite unit and version.
5. **Quality gates**: retrieval eval (P@k, NDCG, MRR on golden questions) and answer eval (calibrated judge) run on every pipeline, model or config change. A KB lint report covers stale (past `valid_to` or not updated in N days), duplicate, contradictory (same intent, different action), orphan-term, and low-quality documents. Feedback and production misses become bad cases.

Licensing posture: Apache-2.0 core. Optional adapters for AGPL (ParadeDB) or ELv2 (Elastic connectors) components should be isolated behind interfaces.

### Gaps
- The blueprint's `check_rules` tool and contradiction linting lack published OSS reference implementations. Airbnb ICA is internal research, and KAG's rule handling was not examined in depth.
- No published cost model was found for running enrichment (questions, summaries, contextual prefixes) plus graph compilation at 1M+ document scale on open models. Estimates would need benchmarking.
