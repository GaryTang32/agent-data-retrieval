# Track 04: LLM-powered data systems over document collections (semantic operators, document-to-table, declarative LLM pipelines)

Scope: database-community systems that either (a) materialize tables from unstructured documents ahead of time (ETL, then deterministic SQL), (b) evaluate LLM-backed operators at query time, or (c) mix the two. The notes are written for a toolkit that converts heterogeneous documents into an agent-retrievable data lake, where "deterministic retrieval" means the same query over the same snapshot returns the same exact results through exact predicates over typed records, and each answer traces back to source spans. Dates are publication or first-arXiv dates; "(author-reported)" marks numbers from a system's own paper, and "(independent)" marks numbers from a third party's benchmark. As of November 2026.

Design taxonomy used below:
- **M (materialize-first):** LLM or synthesized code extracts typed tables offline, and queries run as ordinary SQL. Examples: Evaporate / Evaporate-Code+, TWIX, Doctopus, Text2DB/OPAL, Doc2DB-style construction, Aryn Sycamore's ETL step, warehouse batch `ai_extract` / `AI.GENERATE_TABLE` into tables.
- **Q (query-time operators):** each query calls an LLM per tuple or per pair. Examples: LOTUS, Palimpzest/Abacus, DocETL (run on demand), UQE, ThalamusDB, Galois, CAESURA, BigQuery `AI.IF` / Snowflake `AI_FILTER` / Databricks `ai_query` used inline, iPDB, Sema, FlockMTL, BlendSQL, SUQL.
- **H (hybrid):** structure is materialized offline and attributes are filled lazily at query time, or LLM judgments are persisted and reused, or the LLM is compiled into deterministic code. Examples: ZenDB (offline semantic hierarchical trees plus lazy extraction), QUEST (offline indexes plus query-time extraction), ScaleDoc (offline LLM representations plus online proxy), OCTOPUS (tags written back as columns), SemReuse (cached NL views as materialized views), SemBaker (compile the operator to a deterministic Python function), BigQuery offline proxy models.

## Key Question 1: Systems and papers. How each works, its determinism, accuracy evidence, cost, and failure modes

### Takeaway
The field has split into three camps. One materializes tables ahead of time (Evaporate, TWIX, Doctopus). One runs LLM operators at query time (LOTUS, Palimpzest, DocETL, UQE, ThalamusDB, warehouse AI-SQL). A fast-growing 2025–2026 middle ground persists or compiles LLM judgments into ordinary data or code (ZenDB, QUEST, OCTOPUS, SemReuse, SemBaker, offline proxies). Every query-time system gives up the property traditional databases rely on, that the physical plan does not change the answer, and the DocETL authors say so explicitly. Only the materialized or compiled designs give exact, repeatable results on a fixed snapshot.

### Cited Findings

**A. Materialize-first / document-to-table systems**
- **Evaporate / Evaporate-Code+ (Arora et al., Stanford; arXiv Apr 2023; PVLDB 17(2), 2023).** Takes semi-structured documents (HTML, PDF, TXT) and outputs queryable tables without domain training. It compares two strategies: prompting the LLM to extract values from each document directly, or prompting it to synthesize extraction code. Code synthesis is cheap but "far less accurate". Evaporate-Code+ generates many candidate functions and ensembles them with weak supervision, which needs only a sublinear pass of the LLM over the documents — [Arora et al. 2023](https://arxiv.org/abs/2304.09433)
- Evaporate-Code+ cuts LLM-processed tokens 110x on average across 16 settings of 10k documents each, and beats Evaporate-Direct by 10.1 F1 points (18%) in the headline Table 3 (text-davinci-003). A separate passage in Section 3 says 12.1 F1 points (22%) on average, so the paper is internally inconsistent here. Function aggregation adds 25.1 F1 over a single synthesized function. End to end, Evaporate beats the SoTA learned baselines by 3.2 F1 (author-reported) — [Arora et al. 2023](https://arxiv.org/abs/2304.09433)
- Evaporate cost motivation (2023 prices): running gpt-3.5 directly over 55M Wikipedia articles "would cost over $110k", and text-davinci-003 would cost $1.1M — [Arora et al. 2023](https://arxiv.org/abs/2304.09433)
- Independent result: in UDA-Bench, Evaporate scored the **worst accuracy** on extraction-only queries because "the code essentially corresponds to a limited number of rules, which tend to be less effective when handling complex documents". It was also the **most cost-efficient**, because the LLM analyzes only a small sample — [Deng et al. 2025, UDA-Bench](https://arxiv.org/abs/2510.27119)
- **TWIX (Lin et al., UC Berkeley; arXiv Jan 2025; PACMMOD/SIGMOD 2025).** For templatized documents such as invoices, tax forms and purchase orders, it infers the visual template (field co-location, row and column alignment) and extracts against that template instead of prompting per document. On 34 real datasets it beats Evaporate, Textract, Azure Document Intelligence and GPT-4-Vision by over 25% in precision and recall. On collections over 2,000 pages it is 520x faster and 3,786x cheaper than the most competitive tool (author-reported) — [Lin et al. 2025, TWIX](https://arxiv.org/abs/2501.06659)
- **Doctopus (Chai et al.; PVLDB 18(11), 2025).** Budget-aware extraction of attributes into tables. It mixes LLM and non-LLM strategies, uses an index to send only relevant chunks to the LLM, estimates quality per strategy per attribute, and chooses strategies under a user cost budget. It reports +11% quality at equal cost over SOTA baselines on a 4-document-set benchmark with manual labels (author-reported) — [Chai et al. 2025, Doctopus](https://www.vldb.org/pvldb/vol18/p3695-chai.pdf)
- **Text2DB / OPAL (Jiao et al., UIUC; arXiv Oct 2025).** Recasts information extraction as *updating a target database*: data infilling, row population, column addition. An Observer/Planner/Analyzer agent writes code plans that call IE models and adapts to the existing DB schema. The authors flag hard cases: large DBs with complex dependencies, and extraction hallucination (author-reported) — [Jiao et al. 2025, Text2DB](https://arxiv.org/abs/2510.24014)
- **Aryn (Sycamore + Luna + DocParse) (Anderson et al.; CIDR 2025).** DocParse turns PDFs into DocSets. Sycamore is a declarative, distributed document-processing engine with lineage, and its pipelines extract a schema (e.g., NTSB incident fields) into an OpenSearch index. Luna is an LLM planner that turns NL questions into Sycamore plans over that index plus LLM operators. On 30 questions over 100 NTSB reports, Luna answered 20 correctly (67%) and RAG answered 2 (6.7%), with 8 RAG refusals (author-reported, preliminary) — [Anderson et al. 2025, Aryn](https://arxiv.org/abs/2409.00847)
- Luna's 10 errors: 6 counting errors (duplicate incidents, a missing dedup step), 3 over-generous LLMFilter decisions ("Does the document indicate engine problems?" passes documents that only mention engines), and 1 schema misinterpretation. The authors argue that "an analytics system must provide explainability to be practical", exposing the plan, the generated code and per-operator data drill-down back to source documents — [Anderson et al. 2025, Aryn](https://arxiv.org/abs/2409.00847)

**B. Query-time semantic-operator systems**
- **LOTUS (Patel et al., Stanford/Berkeley; arXiv Jul 2024; PVLDB 18(11), 2025).** Defines semantic operators (sem_filter, sem_join, sem_topk, sem_agg, sem_group_by, etc.) on a pandas-like API. Each operator's behavior is defined by a "gold algorithm", and optimized plans come with statistical accuracy guarantees *relative to the gold algorithm*. It reports up to 1,000x speedups on filter/join/group-by/top-k, and pipelines that match or exceed recent LLM analytics systems by up to 170% quality while running up to 3.6x faster than the highest-quality baselines (author-reported) — [Patel et al. 2024/2025, LOTUS](https://arxiv.org/abs/2407.11418); [PVLDB version](https://www.vldb.org/pvldb/vol18/p4171-patel.pdf)
- LOTUS caching: `enable_cache` defaults to False and the docs recommend enabling it (SQLite cache). OCTOPUS notes that LOTUS's cross-query cache is keyed on the rendered prompt, so "a later query reuses an answer only if it renders the same text for the same row" — [LOTUS docs](https://lotus-ai.readthedocs.io/en/latest/configurations.html); [Zhang et al. 2026, OCTOPUS](https://arxiv.org/abs/2610.32586)
- **Palimpzest (Liu et al., MIT; arXiv May 2024; CIDR 2025)** and **Abacus (Russo et al.; PVLDB 19(5), 2026).** Palimpzest compiles declarative AI-analytics programs into plans chosen for runtime, cost and quality. One plan was 3.3x faster and 2.9x cheaper than the baseline with better quality. With parallelism it was up to 90.3x faster at 9.1x lower cost, at an F1 within 83.5% of a single-threaded GPT-4 baseline (author-reported) — [Liu et al. 2024, Palimpzest](https://arxiv.org/abs/2405.14696)
- Abacus is a cost-based optimizer that estimates operator quality from a few validation examples, priors and/or an LLM judge, and optimizes quality, cost or latency under constraints. On BioDEX, CUAD and MMQA it reports 6.7–39.4% better quality, 10.8x cheaper and 3.4x faster than the next best system (author-reported) — [Russo et al. 2025/2026, Abacus](https://arxiv.org/abs/2505.14661)
- PalimpChat adds a ReAct chat agent (Archytas) that writes Palimpzest pipelines from natural language (SIGMOD'25 demo) — [Liu et al. 2025, PalimpChat](https://arxiv.org/abs/2502.03368)
- **DocETL (Shankar et al., Berkeley; arXiv Oct 2024; PVLDB 18(9), 2025).** Declarative YAML/Python map/reduce/filter/resolve pipelines. An agentic optimizer applies "rewrite directives" (split/gather, decomposition, etc.) and synthesizes validation prompts to judge candidate plans. It reports outputs 25–80% more accurate than well-engineered baselines in the arXiv version; the PVLDB version says 21–80% (author-reported) — [Shankar et al. 2024, DocETL](https://arxiv.org/abs/2410.12189); [PVLDB version](https://www.vldb.org/pvldb/vol18/p3035-shankar.pdf)
- DocETL optimization is a one-time, amortized cost. In one case study the optimizer cost about $100 and 20 minutes, evaluating more than 200 plan variants, for a pipeline that costs under $3 per run on the sample. The team had already spent over $50,000 processing that dataset (author-reported) — [Shankar et al. 2024, DocETL](https://arxiv.org/abs/2410.12189)
- DocETL's authors on determinism: "LLMs are inherently non-deterministic and not always accurate… traditional database systems guarantee correct and consistent outputs, regardless of physical implementation choices… In contrast, DocETL's output quality and correctness can vary dramatically based on physical operator parameter choices" (e.g., fold batch sizes). They also note that "Due to the optimizer's nondeterministic nature, some plans" differ across runs — [Shankar et al. 2024, DocETL](https://arxiv.org/abs/2410.12189)
- DocWrangler (2025) is a mixed-initiative IDE for DocETL, evaluated with 1,500+ public playground sessions. Users turned open-ended operations into classifiers "for easier validation" — [Shankar et al. 2025, DocWrangler](https://arxiv.org/abs/2504.14764)
- **UQE (Dai et al., Google DeepMind; NeurIPS 2024).** A Universal Query Language, a SQL dialect with NL conditions, over unstructured collections. It uses sampling and online learning (embedding-based proxies) and compiler-style workflow orchestration for conditional aggregation, semantic retrieval and abstraction aggregation. Aggregates are *statistical estimates*, not exact counts — [Dai et al. 2024, UQE](https://arxiv.org/abs/2407.09522); the description of UQE's stratified-sampling estimation is from [Chung et al. 2026](https://arxiv.org/abs/2603.15970)
- **ThalamusDB (Jo & Trummer, Cornell; PACMMOD 2(3), SIGMOD 2024).** SQL with NL predicates on images, audio and text. "Deterministic approximate query processing": it runs models on a subset and returns deterministic *bounds* on the result, with user-chosen trade-offs between approximation error, time and labeling. 35.0x average speedup over MindsDB (exact baseline), and it beats ABAE sampling in 78.9% of cases (author-reported) — [Jo & Trummer 2024, ThalamusDB](https://par.nsf.gov/servlets/purl/10577787)
- **Galois (Saeed, De Cao, Papotti; EDBT 2024 vision → Satriani et al. SIGMOD 2025).** Runs SQL with the *LLM itself as the storage layer*: physical operators are prompts that retrieve tuples from the model's parametric knowledge, and optimization metadata is gathered at runtime because LLMs have no catalog. It reports up to 144% quality improvement over NL questions and 29% over direct SQL-to-LLM execution. The authors observe that cost-driven pushdown can hurt quality (author-reported) — [Saeed et al. 2023](https://arxiv.org/abs/2304.00472); [Satriani et al. SIGMOD 2025](https://iris.unibas.it/bitstream/11563/200136/1/GALOIS_SIGMOD.pdf)
- **CAESURA (Urban & Binnig, TU Darmstadt; 2023).** A GPT-4 "language-model-driven query planner" that turns NL queries into multi-modal plans (text, images, tables) for data lakes. Its evaluation is a feasibility study on two datasets — [Urban & Binnig 2023](https://arxiv.org/abs/2308.03424)
- **ELEET (Urban & Binnig; 2024).** Deliberately *avoids* LLMs at query time and uses a small pre-trained extraction model for multi-modal joins/unions over text and tables. Up to 575x faster than GPT-4-based execution "without sacrificing accuracy" (author-reported) — [Urban & Binnig 2024, ELEET](https://arxiv.org/abs/2410.22522)
- **SUQL (Liu et al., Stanford; 2023).** SQL extended with `summary()` and `answer()` free-text primitives for conversational agents over hybrid data. On HybridQA it comes within 8.9% EM of SOTA with in-context learning only. On a Yelp restaurant KB it finds an entity satisfying all requirements 90.3% of the time vs 63.4% for linearization (author-reported) — [Liu et al. 2023, SUQL](https://arxiv.org/abs/2311.09818)
- **BlendSQL (Glenn et al., Capital One; 2024).** A SQLite superset with LLM ingredient functions inside SQL for hybrid QA, using 35% fewer tokens. Follow-ups infer type constraints for LLM functions in SQL (2025) and report that quantized 16 GB-VRAM open-weight models match or beat API models at 390x lower cost and 3.8x lower latency inside BlendSQL (2026, author-reported) — [Glenn et al. 2024](https://arxiv.org/abs/2402.17882); [Glenn et al. 2025](https://arxiv.org/abs/2509.20208); [Glenn & Samuel 2026](https://arxiv.org/abs/2606.31808)
- **In-DBMS semantic SQL engines (2025–2026).** FlockMTL is a DuckDB extension with `PROMPT` and `MODEL` as first-class DDL schema objects, plus batching and caching (PVLDB 18(12) demo) — [Dorbani et al. 2025](https://arxiv.org/abs/2504.01157). iPDB is a relational predict operator for semantic select/join/group-by, with a 2.5x mean and 30x max speedup over SOTA (author-reported) — [Kumarasinghe et al. 2026](https://arxiv.org/abs/2601.16432). Sema runs on DuckDB with SemaSQL and adaptive query execution and is 2–10x faster on 20 queries; its authors cite "the high cost and non-deterministic nature of LLM invocation" as making conventional cost models inapplicable — [Qi et al. 2026](https://arxiv.org/abs/2603.11622)
- **Unify (Wang, Li, Feng, Tsinghua; PVLDB 18(12) 2025 demo; full paper).** NL questions over unstructured data are decomposed into logical plans over predefined operators, with LLM-based or programmed implementations, and a semantic cost model. Up to 40x faster "while preserving high accuracy" (author-reported) — [Wang et al., Unify full paper](https://dbgroup.cs.tsinghua.edu.cn/ligl/papers/Unify.pdf); [Unify demo, PVLDB 18(12)](https://www.vldb.org/pvldb/vol18/p5287-wang.pdf). The successor AgenticData (2025) uses data-profiling, cross-validation and memory agents to plan relational and semantic operators — [Sun et al. 2025](https://arxiv.org/abs/2508.05002)
- **Nirvana (Zhu et al.; Nov 2025).** Multi-modal analytics with an *agentic logical optimizer*: NL-specified rewrite rules plus random-walk plan search, and per-operator LLM backend selection — [Zhu et al. 2025](https://arxiv.org/abs/2511.19830)
- **NL→plan front-ends.** TAG (Table-Augmented Generation) generalizes Text2SQL and RAG: query synthesis, then exact DB execution, then LM generation over the results — [Biswal et al. 2024, TAG](https://arxiv.org/abs/2408.14717). SEMA-SQL generates "Hybrid Relational Algebra" with LLM UDFs and batches semantic joins (−93% LLM calls) — [Lin et al. 2026](https://arxiv.org/abs/2604.23477). NL2Pipe compiles NL questions into Palimpzest/LOTUS pipelines (up to 60% higher F1 on cross-source workloads) — [Dong et al. 2026, NL2Pipe](https://arxiv.org/abs/2606.04641). EnumGRPO optimizes agentic query execution, with up to 317x lower LLM-operator cost than LOTUS/Palimpzest on SWAN (author-reported) — [Nie et al. 2026](https://arxiv.org/abs/2606.03152)
- **RUBICON (Wenz, …, Stonebraker; Apr 2026)** argues against text-centric agentic pipelines. It uses a restricted SQL-like Agentic Query Language over wrapped sources, with tables as the integration abstraction, and calls full SQL "explicit, optimizable, and reproducible". It reports 100% end-to-end accuracy on its own enterprise benchmark, where ReAct baselines got none right. On SemBench E-Commerce it reports +14.7% accuracy, −62.64% latency and −98.64% tokens vs LOTUS/Palimpzest. A pilot customer reported that prior agentic attempts gave "poor results with respect to reproducibility" (author-reported) — [Wenz et al. 2026, RUBICON](https://arxiv.org/abs/2604.21413)

**C. Warehouse "AI functions" as SQL operators (industrial)**
- **Snowflake Cortex AISQL (SIGMOD Companion '26 industry).** Native semantic operators in SQL (AI_FILTER, AI_CLASSIFY, AI_AGG, AI_EXTRACT, AI_COMPLETE…). It has AI-aware optimization that treats inference cost as a first-class objective (2–8x speedups), adaptive model cascades from a proxy model to an oracle (2–6x speedups at 90–95% of oracle quality), and semantic-join rewriting into multi-label classification, which takes the join from quadratic to linear (15–70x) (author-reported, production data) — [Liskowski et al. 2025/2026, Cortex AISQL](https://arxiv.org/abs/2511.07663). Snowflake docs say the functions "are optimized for throughput" and that "Batch processing is typically better suited for AI Functions"; the docs do not discuss determinism — [Snowflake Cortex AISQL docs](https://docs.snowflake.com/en/user-guide/snowflake-cortex/aisql)
- **Google BigQuery AI functions.** AI.GENERATE (structured STRUCT output with a schema), AI.GENERATE_TABLE (table-valued, custom schema), AI.IF (NL filter in WHERE/JOIN), AI.SCORE (ORDER BY), AI.CLASSIFY (GROUP BY), AI.AGG. "Optimized mode" (Preview) for AI.IF/AI.CLASSIFY trains a distilled lightweight model on a sample and uses it for most rows. Failed rows return NULL, governed by `max_error_ratio` (default 1.0). A LIMIT is applied after the model processes a batch of rows. The docs do not discuss determinism — [BigQuery generative AI overview](https://docs.cloud.google.com/bigquery/docs/generative-ai-overview)
- Google's proxy-model paper: embedding-based logistic-regression proxies for AI.IF on a 10M-row table give 329x latency and 728x cost reduction with online (ad hoc) training, and 991x latency and 792x cost reduction with *offline* pre-trained proxies (AlloyDB/HTAP). Accuracy is "preserved and occasionally improved". Offline proxies need periodic retraining as data changes (author-reported) — [Chung et al. 2026](https://arxiv.org/abs/2603.15970)
- **Databricks AI Functions.** Task-specific `ai_parse_document`, `ai_extract` (schema-defined fields), `ai_classify`, `ai_enrich` (schema-defined new columns) and general `ai_query`. Scheduled "AI Function tasks (Beta)… process only the inputs that are new or changed since the previous run", which is an incremental-materialization pattern. The docs do not discuss output determinism or caching — [Databricks AI Functions docs](https://docs.databricks.com/aws/en/large-language-models/ai-functions)

**D. Hybrid / persist-or-compile systems (mostly 2025–2026)**
- **ZenDB (Lin et al., Berkeley; arXiv May 2024).** It builds a *Semantic Hierarchical Tree* (SHT) per templatized document offline (header phrases plus NLTK extractive summaries per node). Users declare a schema in an SQL extension, and attributes are then populated by tree search plus LLM calls at query time. It tracks **provenance as text spans** per tuple, "analogous to classical relational provenance". Cost savings are about 29x, 10x and 4x vs a whole-document GPT baseline on three datasets, with comparable or better precision/recall (+28% P / +39% R on civic data). Against RAG baselines it is up to 61% higher precision and 80% higher recall at slightly higher cost (author-reported) — [Lin et al. 2024, ZenDB](https://arxiv.org/abs/2405.04674)
- Independent result: in UDA-Bench, ZenDB and QUEST "perform worse because they only provide relevant chunks to LLMs to save cost. However, chunking often misses relevant information". They were nonetheless the most latency-efficient and cost-effective on long documents — [Deng et al. 2025, UDA-Bench](https://arxiv.org/abs/2510.27119)
- **QUEST (Sun et al.; VLDB 2025).** Index-based retrieval of attribute-relevant segments, evidence-augmented retrieval to reduce misses, per-document (instance-optimized) filter ordering, and join-to-filter transformation. 30%–6x cost savings and +10–27% F1 vs SOTA baselines (author-reported) — [Sun et al. 2025, QUEST](https://arxiv.org/abs/2507.06515)
- **ScaleDoc (Zhang et al.; 2025, ACM DOI 10.1145/3802106).** Offline LLM-generated semantic representations per document, then online per-query contrastively trained proxy plus adaptive cascade. Over 2x end-to-end speedup and up to 85% fewer LLM calls (author-reported) — [Zhang et al. 2025, ScaleDoc](https://arxiv.org/abs/2509.12610)
- **OCTOPUS tag model (Zhang, …, Lin, Mehrotra; Oct 2026).** Every semantic judgment is written back to the relation as a "tag" column with a provenance side-table (model confidence, when produced). Later queries reuse tags through exact-match, complement and implication rules. On SemBench Movies it sent 10–108x fewer rows to the model than iPDB, ThalamusDB, Palimpzest and LOTUS at "broadly competitive quality", and 3 of 8 queries issued **no model call** ("milliseconds of pure SQL"). Pitch: "each semantic answer is paid for once, stays consistent across queries, and can be audited through its provenance" (author-reported) — [Zhang et al. 2026, OCTOPUS](https://arxiv.org/abs/2610.32586)
- OCTOPUS survey of caching in semantic systems: iPDB, PLOP and FlockMTL cache only duplicate tuples *within* a query. Cross-query caching exists only in LOTUS and AIDB, under an identical-prompt constraint. "None of the systems we run keeps a judgment past the query" — [Zhang et al. 2026, OCTOPUS](https://arxiv.org/abs/2610.32586)
- **SemReuse (Tran-Truong et al.; Oct 2026).** Stores each semantic-filter result as a materialized view. It uses an LLM reasoner to decide equivalence, implication or exclusion between new and cached NL filters, then *audits* every rewritten result with a pooled stratified audit (exact finite-population bounds), so wrong reuse judgments cost efficiency but not guarantee validity. Up to 15.4x reduction. "Cross-filter inconsistency" is the main source of repair cost (author-reported) — [Tran-Truong et al. 2026, SemReuse](https://arxiv.org/abs/2610.16035)
- **SemBaker, compilation-based execution (Dong & Wang; Jul/Aug 2026).** For selected filters, maps and joins it calls the LLM *once* to generate a **deterministic Python function** and runs it locally with no per-row LLM calls. A cost model routes each operator between native and compiled execution, with plug-ins for Palimpzest, LOTUS, Nirvana and DocETL. On three 200-query QA workloads: 4.8–6.3x faster and 5.4–10.7x cheaper "with competitive processing quality". Their refine and validate stages "may also decrease the quality in some cases… they are unstable" (author-reported) — [Dong & Wang 2026, SemBaker](https://arxiv.org/abs/2608.06677); [vision paper](https://arxiv.org/abs/2607.13407)
- **PLOP (Mang et al., incl. Parameswaran/Cheung; Apr 2026)** proves that deferring semantic filters to the latest possible position minimizes LLM invocations *under function caching*, and it optimizes placement in hybrid relational/semantic plans — [Mang et al. 2026, PLOP](https://arxiv.org/abs/2604.09944)
- **JEVDB (Wang et al.; Oct 2026).** Fast typed decision models instead of autoregressive LLMs for filters, joins, classification and ranking, with escalation to an LLM when uncertain. Exact Yannakakis semijoin reduction plus "Semantic Bloom Filters". On SemBench it reports the lowest latency on all 21 evaluated queries and the lowest cost on 19. On Shelob (TPC-DS-derived, 540K candidate pairs) it reports 95.7–97.5% mean F1 (author-reported) — [Wang et al. 2026, JEVDB](https://arxiv.org/abs/2610.02046)

### Inferences
- Every materialize-first system (Evaporate-Code+, TWIX, ZenDB's SHTs, Doctopus, Aryn's index, OCTOPUS tags, SemBaker's compiled functions) gets its cost win the same way: **pay the LLM once per document, attribute or judgment, then reuse as data or code.** That is also what makes results deterministic downstream. Query-time systems pay per query and can only approximate this with caches keyed on exact prompts.
- Synthesized code (Evaporate-Code, SemBaker) and template inference (TWIX) are the most deterministic extractors: a pure function over bytes. They are weakest on free-form, complex documents (UDA-Bench's Evaporate result), so they need an LLM-direct fallback and per-attribute routing (Doctopus- or Abacus-style).
- A trend is visible in 2026 papers (OCTOPUS, SemReuse, SemBaker, PLOP, offline proxies): the semantic-operator community is converging on **materialized views of LLM judgments with provenance and maintenance**. That is the design an agent-retrievable lake needs.

### Gaps
- No independent evaluation of TWIX, Doctopus, Text2DB, Unify or AgenticData was found. Their numbers are author-reported only.
- Aryn/Luna's evaluation is 30 questions on 100 reports, which is small. No follow-up independent Aryn evaluation was found.
- Unify's full-paper venue could not be confirmed (the PVLDB 18(12) demo is confirmed). The ZenDB arXiv preprint's final venue was not confirmed.
- No head-to-head study was found that compares the *same* workload run as (a) offline extraction then SQL vs (b) query-time operators, with repeated queries and measured cost amortization. OCTOPUS (tags) and DocETL (amortized optimizer) give partial evidence only.

## Key Question 2: Benchmarks and results (author-reported vs independent)

### Takeaway
Independent benchmarks from 2025–2026 (SemBench, UDA-Bench, Doc2DB-Bench, TAG-Bench) show that no system dominates. Quality on hard documents stays modest (about 0.5–0.75 F1 or accuracy), costs differ by 100x across systems on the same query, run-to-run variance is real even at temperature 0, and relation/join-level construction is the bottleneck. Author-reported headline speedups (100–1,000x) mostly come from cheap proxies or code and are not reproduced in independent head-to-head results.

### Cited Findings
- **SemBench (Lao et al.; VLDB 2026), independent of the systems tested.** 5 scenarios (Movies, Wildlife, E-Commerce, Cars, MMQA), 55 queries, text/images/audio/tables (~1.58M text rows, 84k images, 2k audio). Operators: 50 filters, 15 joins, 7 maps, 3 ranks, 4 classify. It evaluated LOTUS, Palimpzest, ThalamusDB and BigQuery, all on gemini-2.5-flash at temperature 0 where possible, with 5 repetitions each — [Lao et al. 2025, SemBench](https://arxiv.org/abs/2511.01716)
- SemBench aggregates across operators (base scale), quality / latency / cost: LOTUS 0.731 / 212.1s / $0.86; Palimpzest 0.715 / 165.0s / $1.06; ThalamusDB 0.592 / 244.2s / $0.17 (subset of operators); BigQuery 0.677 / 31.7s / $0.45. For semantic joins: Palimpzest 0.703 quality at $3.29 (naive nested loop), LOTUS 0.614 at $2.74 (embedding pre-filter "can miss valid matches"), ThalamusDB 0.487 at $0.14 (batched pairs) — [Lao et al. 2025, SemBench](https://arxiv.org/abs/2511.01716)
- SemBench: on Movies Q1/Q5/Q6 (LIMIT queries), "processing costs vary by more than a factor of 100x across different systems", because LOTUS applies LIMIT only after evaluating all rows. No system supports all queries. Systems "may stall for over 48 hours at large scale due to network issues, unstable API, or rate limiting". LOTUS, Palimpzest and ThalamusDB hit memory pressure on image joins. "The choice of the model has the biggest influence on system performance" — [Lao et al. 2025, SemBench](https://arxiv.org/abs/2511.01716)
- SemBench variance: "Variance in cost and quality mainly comes from randomness in LLM outputs". BigQuery "shows a relatively high quality variance across different runs… because the model temperature is set to zero for the other systems, whereas model-related parameters in BigQuery are controlled internally and are not exposed to users" — [Lao et al. 2025, SemBench](https://arxiv.org/abs/2511.01716)
- **UDA-Bench (Deng et al.; Oct 2025), independent, though from the QUEST/Doctopus group.** 5 datasets (WikiArt, NBA, Legal, Finance, Healthcare), manually annotated into relational tables by 30 graduate students over more than 10,000 hours (Finance documents up to 838k tokens), all on GPT-4.1-mini. Systems: Evaporate, Palimpzest, LOTUS, DocETL, QUEST, ZenDB, UQE — [Deng et al. 2025, UDA-Bench](https://arxiv.org/abs/2510.27119)
- UDA-Bench results: on short documents almost all systems reach about 0.85 F1, and DocETL is best. On long documents, LOTUS/UQE/Palimpzest (whole-document prompting) do best, at only ~0.66 (Legal), ~0.52 (Finance) and ~0.51 (Healthcare). DocETL's chunk-and-aggregate degrades on long noisy documents. QUEST/ZenDB lose accuracy from chunk misses but are the cheapest and lowest-latency on long documents. Evaporate is the least accurate and the most cost-efficient. "Extracting the attribute first and evaluating the filter thereafter lead to more accurate results than directly executing it with LLMs" — [Deng et al. 2025, UDA-Bench](https://arxiv.org/abs/2510.27119)
- **Doc2DB-Bench (Liang, …, Nan Tang; Aug 2026).** Document → *normalized multi-table database*: 203 long documents, 42 schemas, 117 entity tables, 132 relationship tables, 41,935 cells, temperature 0. Best overall F1 is GPT-5.4 at 75.25. DocETL (GPT-5.4 backbone) scores 74.91 entity F1 but only 41.51 relation F1 (60.82 overall). LlamaExtract scores 49.10 overall, LangExtract 28.72, Llama-3.1-70B 14.29. Findings: "Relation-level extraction is a major bottleneck" and "Database construction requires more than accurate extraction: maintaining relational consistency and valid entity references remains a critical challenge" — [Liang et al. 2026, Doc2DB-Bench](https://arxiv.org/abs/2608.08459)
- **TAG-Bench (Biswal et al.; Aug 2024).** Built on BIRD databases, with queries needing world knowledge or semantic reasoning. Text2SQL, RAG and similar baselines never exceed 20% exact match (ranking queries reach only 10%). A hand-written TAG pipeline reaches 55% overall and 65% on comparisons (author-reported; the hand-written pipeline is the authors' own) — [Biswal et al. 2024, TAG](https://arxiv.org/abs/2408.14717)
- **"Stochastic Shift" (Alrashed, Özcan et al., Google; Sep 2026).** For Text-to-SQL that emits AI operators (BigQuery, ThalamusDB), "Current metrics, which rely on exact query results and deterministic execution, systematically fail". Execution accuracy detects as few as 25% of correct translations, and an LLM autorater falsely rejects 32%. Separating relational logic from AI-operator semantics yields up to 97.2% evaluation accuracy — [Alrashed et al. 2026](https://arxiv.org/abs/2609.21133)
- **SemCEB (Zimmerer et al.; Jun 2026).** A cardinality-estimation benchmark for semantic filters/joins with 102 queries. Sampling is robust but costly and does not scale. Semantic Histograms are sensitive to predicate category. Bad estimates make bad plans "worse by orders of magnitude" given per-tuple LLM cost — [Zimmerer et al. 2026, SemCEB](https://arxiv.org/abs/2606.23081)
- Successor systems now report on SemBench: OCTOPUS (Movies, 10–108x fewer model rows), JEVDB (lowest latency on 21/21 queries), RUBICON (E-Commerce), EnumGRPO. All are author-reported — [OCTOPUS](https://arxiv.org/abs/2610.32586); [JEVDB](https://arxiv.org/abs/2610.02046); [RUBICON](https://arxiv.org/abs/2604.21413); [EnumGRPO](https://arxiv.org/abs/2606.03152)

### Inferences
- Independent quality on realistic long documents (UDA-Bench at about 0.5–0.66; Doc2DB relation F1 of 41–72) is far too low to treat any single LLM extraction or query pass as ground truth. An agent-facing lake must expose confidence and provenance per value, and should support re-extraction and human or validator correction.
- In independent results, the systems with the biggest author-reported speedups (ThalamusDB batching, LOTUS embedding pre-filters) are the ones that lose quality on joins. Cheap, approximate join strategies are the main quality risk.
- UDA-Bench's "extract the attribute, then filter" finding directly favors materializing typed attributes: a deterministic predicate over an extracted column is more accurate than asking an LLM to evaluate the predicate.

### Gaps
- No public independent leaderboard was found that runs DocETL, LOTUS, Palimpzest and a materialize-first pipeline on SemBench and UDA-Bench with identical models in 2026. Results come from different snapshots and models.
- None of the benchmarks measure *repeatability across days or model versions* (e.g., the same query re-run after a provider model update). SemBench measures only within-session variance over 5 runs.
- The independence of the TAG-Bench numbers is limited. No later third-party TAG-Bench results were checked.

## Key Question 3: Cost optimizations (cascades, proxies, code synthesis, caching, sampling) and their accuracy trade-offs

### Takeaway
Most of the savings come from not calling the large LLM per row: synthesized code (110x fewer tokens), proxies over embeddings (100–1,000x), cascades (2–6x, 36% beyond plain cascades for task cascades), batching joins (15–70x), and reuse (10–108x). Accuracy holds only when a guarantee mechanism (sampling-based thresholds, audits) calibrates the shortcut against an oracle. Without one, independent results show quality loss, especially on joins and LIMIT/early-termination heuristics.

### Cited Findings
- **Code synthesis:** Evaporate-Code+ cuts LLM tokens 110x and *raises* F1 over direct extraction on its 16 semi-structured settings (author-reported) — [Arora et al. 2023](https://arxiv.org/abs/2304.09433). Independently, it is the least accurate on complex documents — [UDA-Bench](https://arxiv.org/abs/2510.27119). SemBaker compiles operators to deterministic Python for a 5.4–10.7x cost reduction (author-reported) — [Dong & Wang 2026](https://arxiv.org/abs/2608.06677)
- **Model cascades with guarantees:** BARGAIN (SIGMOD'26) uses adaptive sampling plus statistical estimation to decide which records the cheap LLM handles, with guarantees on accuracy, precision or recall. Across 8 datasets it reduces cost "by up to 86% more than state-of-the-art" (SUPG) (author-reported) — [Zeighami et al. 2025, BARGAIN](https://arxiv.org/abs/2509.02896)
- **Task cascades (SIGMOD 2026)** vary the model, the *document portion* and the *operation* (simpler correlated proxy questions). At a 90% accuracy target they average 36% lower cost than model cascades across 8 tasks, with an extension giving statistical accuracy guarantees. Optimal cascade selection is intractable (Min Sum Set Cover) — [Shankar et al. 2026](https://arxiv.org/abs/2601.05536)
- **Proxy models:** Google's lightweight proxies over embeddings give over 100x cost and latency reduction for semantic filter, and offline-trained proxies give 991x latency and 792x cost reduction. Offline proxies require retraining when data drifts and validation on filtered slices — [Chung et al. 2026](https://arxiv.org/abs/2603.15970). Cortex AISQL cascades give 2–6x speedups at 90–95% of oracle quality — [Liskowski et al.](https://arxiv.org/abs/2511.07663). ScaleDoc reduces LLM calls by 85% — [Zhang et al. 2025](https://arxiv.org/abs/2509.12610). LOTUS uses small-LLM or embedding proxy scorers with accuracy guarantees relative to its gold algorithm — [Patel et al.](https://arxiv.org/abs/2407.11418)
- **Semantic joins:** Featurized-Decomposition Join extracts features into a CNF expression to prune non-matching pairs with guarantees; embedding-similarity pruning "may not reliably predict the join outcome" — [Zeighami et al. 2025, FDJ](https://arxiv.org/abs/2512.05399). Trummer's block-nested-loop prompt batching sizes batches to the context window — [Trummer 2025](https://arxiv.org/abs/2510.08489). Cortex rewrites semantic joins as multi-label classification (15–70x) — [Liskowski et al.](https://arxiv.org/abs/2511.07663). SEMA-SQL batches joins for −93% LLM calls — [Lin et al. 2026](https://arxiv.org/abs/2604.23477)
- **Chunk/index-based context reduction:** ZenDB (4–29x cost savings via SHTs) — [Lin et al. 2024](https://arxiv.org/abs/2405.04674); QUEST (30%–6x) — [Sun et al. 2025](https://arxiv.org/abs/2507.06515); Doctopus (budget-aware) — [Chai et al. 2025](https://www.vldb.org/pvldb/vol18/p3695-chai.pdf). Trade-off, independently: "chunking often misses relevant information, leading to lower accuracy" — [UDA-Bench](https://arxiv.org/abs/2510.27119)
- **Sampling-based optimization:** Abacus estimates per-operator quality from a small validation set, priors and an LLM judge (10.8x cheaper than the next best at better quality, author-reported) — [Russo et al.](https://arxiv.org/abs/2505.14661). Stretto gives *global* (whole-plan) accuracy guarantees via gradient-based error-budget allocation, with KV-cache compression as a family of physical operators — [Sanmartino et al. 2026](https://arxiv.org/abs/2602.04430). UQE and ThalamusDB use sampling for approximate aggregates and bounds — [Dai et al. 2024](https://arxiv.org/abs/2407.09522); [Jo & Trummer 2024](https://par.nsf.gov/servlets/purl/10577787)
- **Caching and reuse:** OCTOPUS tags (10–108x fewer model rows; some queries need zero LLM calls) — [Zhang et al. 2026](https://arxiv.org/abs/2610.32586); SemReuse (up to 15.4x with audited guarantees) — [Tran-Truong et al. 2026](https://arxiv.org/abs/2610.16035); PLOP's result that late filter placement minimizes calls under function caching — [Mang et al. 2026](https://arxiv.org/abs/2604.09944). SemBench's authors also recommend caching because "our scenarios entail multiple queries on overlapping data subsets" — [Lao et al. 2025](https://arxiv.org/abs/2511.01716)
- **Local open-weight models:** 390x cost reduction vs a proprietary API inside BlendSQL, at matching or better accuracy (author-reported) — [Glenn & Samuel 2026](https://arxiv.org/abs/2606.31808). ELEET's small extraction model is up to 575x faster than GPT-4-based execution — [Urban & Binnig 2024](https://arxiv.org/abs/2410.22522)
- **Optimizer cost itself:** DocETL's optimizer spent about $100 on a pipeline costing under $3 per run, which pays off only when amortized over very large corpora — [Shankar et al. 2024](https://arxiv.org/abs/2410.12189)

### Inferences
- For a lake that is built once and queried many times, the cost-optimal and determinism-optimal choices coincide. Put guarantee-backed cascades, proxies or code synthesis in the **ingest/ETL path**, where accuracy can be audited against a labeled sample. Store the outputs, so query time costs nothing in LLM calls.
- Guarantee-bearing methods (BARGAIN, task cascades, LOTUS, SemReuse, Stretto) give *statistical* guarantees relative to an oracle LLM, not correctness relative to ground truth. If the oracle model is 0.5–0.7 accurate on long documents (UDA-Bench), the guarantee only bounds how far results drift from a mediocre reference.

### Gaps
- No study was found that measures total cost of ownership over a realistic agent workload (thousands of repeated or similar queries) for materialize-first vs query-time designs.
- Offline proxy and tag maintenance costs under data or model change (retraining, re-judging) are flagged as open by their own authors and not quantified.

## Key Question 4: Determinism and reproducibility. Materialized tables vs query-time LLM calls, caching, and versioning

### Takeaway
Query-time LLM operators are not reproducible in practice. Even "deterministic" settings (temperature 0) vary run to run, managed warehouse functions hide the controls, and the physical plan changes the answer. Bitwise reproducibility needs batch-invariant inference, which is unavailable on commercial APIs. The only robust way to get "same query, same snapshot, same rows" is to **freeze LLM outputs as data**: materialized tables, tags or compiled code, with provenance and versioned model, prompt and code. That is the direction the 2026 database papers are taking.

### Cited Findings
- Five LLMs set to be deterministic, over 8 tasks and 10 runs, showed accuracy variations of up to 15% across runs, and a best-to-worst gap of up to 70%. "None of the LLMs consistently delivers repeatable accuracy across all tasks, much less identical output strings" — [Atil et al. 2024](https://arxiv.org/abs/2408.04667)
- Root cause: kernels lack batch invariance, so server load changes the batch size, which changes the numerics. At temperature 0, 1,000 completions of the same prompt on Qwen3-235B gave 80 unique outputs. With batch-invariant kernels all 1,000 were identical, at about 60% slower in an unoptimized vLLM test (Sep 2025) — [He / Thinking Machines 2025](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- 2026 serving work targets this: CoRun gets determinism via isolated prefill plus fixed-shape decode, with 15–324% better throughput than batch-invariant kernels — [Zhao et al. 2026](https://arxiv.org/abs/2608.14376). Vosti formalizes deterministic inference as bitwise-identical logits under fixed model and deployment config, finds that vLLM's batch-invariant mode and SGLang's deterministic mode "produce different logits under some execution variations", and ships a formally verified engine — [Qin et al. 2026](https://arxiv.org/abs/2609.38981)
- In semantic query engines: SemBench saw cost and quality variance "mainly" from LLM output randomness, and higher variance for BigQuery, whose model parameters are "controlled internally and are not exposed to users" — [Lao et al. 2025](https://arxiv.org/abs/2511.01716). The Databricks, Snowflake and BigQuery AI-function overview docs reviewed do not discuss output determinism — [Databricks](https://docs.databricks.com/aws/en/large-language-models/ai-functions); [Snowflake](https://docs.snowflake.com/en/user-guide/snowflake-cortex/aisql); [BigQuery](https://docs.cloud.google.com/bigquery/docs/generative-ai-overview)
- BigQuery's AI.IF/AI.CLASSIFY/AI.SCORE default `max_error_ratio` of 1.0 means failed rows silently become NULL unless the threshold is lowered, so the result set can differ when API failures differ — [BigQuery docs](https://docs.cloud.google.com/bigquery/docs/generative-ai-overview). SemBench also reports frequent invocation failures and stalls — [Lao et al. 2025](https://arxiv.org/abs/2511.01716)
- Plan dependence: in DocETL, unlike a relational DB where hash join and nested loop give identical results, "output quality and correctness can vary dramatically based on physical operator parameter choices" — [Shankar et al. 2024](https://arxiv.org/abs/2410.12189). Galois found that classic pushdown changes LLM result quality — [Satriani et al. 2025](https://iris.unibas.it/bitstream/11563/200136/1/GALOIS_SIGMOD.pdf). SemReuse identifies "cross-filter inconsistency" (the LLM judging related predicates incompatibly) as the main repair cost — [Tran-Truong et al. 2026](https://arxiv.org/abs/2610.16035)
- Evaluation is affected too: exact-result execution accuracy "systematically fail[s] against the flexible, non-deterministic outputs of AI operators" — [Alrashed et al. 2026](https://arxiv.org/abs/2609.21133)
- Persisting judgments as data: OCTOPUS writes each judgment as a column with provenance (confidence, time produced). It treats tags as partially materialized semantic views that need maintenance "not only when the data changes but when the model or the prompt that defines it does", and notes that "semantic staleness has no full treatment yet" — [Zhang et al. 2026](https://arxiv.org/abs/2610.32586). Its lineage goes back to MauveDB's model-based views; AIDB caches sparse model outputs in an RDBMS keyed by exact invocation (as described by OCTOPUS) — [Zhang et al. 2026](https://arxiv.org/abs/2610.32586)
- Compilation as determinism: SemBaker's compiled functions are "deterministic executable code that reproduces the intended behavior", "solidifying the decision" — [Dong & Wang 2026](https://arxiv.org/abs/2608.06677). Evaporate-Code's synthesized functions are likewise reusable, inspectable code — [Arora et al. 2023](https://arxiv.org/abs/2304.09433)
- Provenance to source spans: ZenDB keeps per-tuple text-span provenance through joins (aggregation provenance is left to future work) — [Lin et al. 2024](https://arxiv.org/abs/2405.04674). Aryn exposes the plan, generated code and per-operator records "linking back to the original source documents" — [Anderson et al. 2025](https://arxiv.org/abs/2409.00847). Sycamore supports explicit `materialize` of intermediate DocSets — [Anderson et al. 2025](https://arxiv.org/abs/2409.00847)
- Open-weight local models make pinning possible: inside BlendSQL they match API accuracy, and the authors stress cost; model and version pinning follows naturally — [Glenn & Samuel 2026](https://arxiv.org/abs/2606.31808). Databricks' scheduled AI Function tasks process only new or changed inputs, which is incremental materialization — [Databricks docs](https://docs.databricks.com/aws/en/large-language-models/ai-functions)

### Inferences
- Determinism in an agent lake should be defined at the **data layer, not the model layer**. Freeze each extracted value with (doc_id, span offsets, extractor = model id + version + prompt hash or code hash, timestamp, confidence), then answer agent queries with plain SQL, Cypher or key lookups over that snapshot. Re-extraction then becomes a versioned write (a new snapshot), never a side effect of reading.
- LLM caches keyed on exact prompts (LOTUS) only give determinism for byte-identical re-queries. Tag- or view-style persistence (OCTOPUS, SemReuse) generalizes this but brings inference-based reuse rules that can themselves be wrong. An agent lake should prefer explicit, declared columns over inferred implication rules for anything that must be exact.
- Batch-invariant or verified-deterministic inference (Vosti, CoRun) helps reproducible *re-extraction* when self-hosting open-weight models. It does not fix accuracy, and hosted APIs do not offer it.

### Gaps
- No vendor documentation found states determinism guarantees for BigQuery, Snowflake or Databricks AI functions. Whether these engines cache AI-function results across identical queries was not documented in the pages reviewed.
- No paper found evaluates schema or extraction *versioning* (snapshot diffing when the extractor model changes) for document-derived tables. OCTOPUS lists it as open.

## Key Question 5: Which design is most effective for agent retrieval, and under which workload (repeated vs ad hoc)?

### Takeaway
For agents that need deterministic, traceable answers over a stable corpus with recurring question types, the evidence favors **materialize-first with a hybrid escape hatch**. Extract typed, normalized tables (entities plus relationship tables) once at ingest. Use cheap, guarantee-backed extraction (code or template synthesis for templatized documents; cascades or proxies with sampled audits for the rest). Store span-level provenance and version every extractor, and let agents query with exact SQL or graph predicates. Reserve query-time semantic operators for genuinely ad hoc predicates. Even then, write their judgments back as versioned columns (OCTOPUS/SemReuse pattern) so the second ask is deterministic and free. Pure query-time evaluation fits only one-off exploratory analysis over data that will not be revisited.

### Cited Findings
- Agents generate high-volume, redundant, heterogeneous "agentic speculation" workloads. The Berkeley position paper calls for agent-first data systems that exploit this redundancy (scale, heterogeneity, redundancy, steerability) — [Liu et al. 2025, Supporting Our AI Overlords](https://arxiv.org/abs/2509.00997). Redundancy favors reuse and materialization over per-query LLM calls; OCTOPUS shows 3 of 8 benchmark queries need zero LLM calls once tags exist — [Zhang et al. 2026](https://arxiv.org/abs/2610.32586)
- Extract-then-filter beats LLM-evaluated filters on accuracy (UDA-Bench Summary II) — [Deng et al. 2025](https://arxiv.org/abs/2510.27119)
- Agentic or LLM-direct pipelines without structure lose to table-centric execution on enterprise data. RUBICON (tables as the integration abstraction, SQL "reproducible") got 100% vs 0% for ReAct baselines on its own benchmark, and −98.64% tokens on SemBench E-Commerce (author-reported) — [Wenz et al. 2026](https://arxiv.org/abs/2604.21413). Aryn's structured extraction plus planning got 67% vs RAG's 6.7% (author-reported) — [Anderson et al. 2025](https://arxiv.org/abs/2409.00847). TAG-Bench shows Text2SQL alone tops out at 20% when semantic reasoning is needed, so an LM step after exact retrieval is still useful for answer synthesis — [Biswal et al. 2024](https://arxiv.org/abs/2408.14717)
- Materialization must be relational, not flat. Doc2DB-Bench shows flattening "can duplicate entities, obscure many-to-many relationships", and relation-level extraction is the bottleneck (best relation F1 72.33; DocETL 41.51) — [Liang et al. 2026](https://arxiv.org/abs/2608.08459). Aryn's counting errors came from duplicate entities, a dedup or entity-resolution failure — [Anderson et al. 2025](https://arxiv.org/abs/2409.00847)
- Template-heavy corpora (invoices, filings, forms) suit template inference or code synthesis: TWIX is 3,786x cheaper and over 25% more accurate than competitors on templatized documents — [Lin et al. 2025](https://arxiv.org/abs/2501.06659). ZenDB's SHTs exploit shared templates too — [Lin et al. 2024](https://arxiv.org/abs/2405.04674)
- Ad hoc workloads: online proxies (329x latency, 728x cost) — [Chung et al. 2026](https://arxiv.org/abs/2603.15970) — and sampling with deterministic bounds (ThalamusDB) — [Jo & Trummer 2024](https://par.nsf.gov/servlets/purl/10577787) — make query-time operators affordable for exploratory, one-off questions, at the price of approximate or non-repeatable answers
- Fixed analytical schemas known up front: extract once with a budgeted optimizer (Doctopus, Abacus, DocETL's amortized optimization) — [Chai et al. 2025](https://www.vldb.org/pvldb/vol18/p3695-chai.pdf); [Russo et al.](https://arxiv.org/abs/2505.14661); [Shankar et al. 2024](https://arxiv.org/abs/2410.12189). Evolving schemas: Text2DB-style "column addition" or "row population" against an existing DB, and OCTOPUS's view that a database's "schema [can] grow from the questions its users ask" — [Jiao et al. 2025](https://arxiv.org/abs/2510.24014); [Zhang et al. 2026](https://arxiv.org/abs/2610.32586)

### Inferences
- **Workload rule of thumb:** if a predicate or attribute is likely to be asked more than once, or must be auditable, materialize it as a typed column with provenance at ingest or on first use. If it is genuinely one-off and approximate answers are acceptable, query-time operators (ideally with sampling bounds) are fine. Their outputs should still be logged as candidate columns.
- **Suggested pipeline:** parse (DocParse- or AI_PARSE_DOCUMENT-class) → classify document type → template/code synthesis for templatized types, LLM extraction via guarantee-backed cascade for free-form types → entity resolution and normalization into entity plus relationship tables → validation (type constraints, referential integrity, sampled audits vs an oracle or human) → versioned snapshot with span provenance → expose SQL, graph and key APIs to agents. A query-time semantic-operator layer whose results are written back as versioned tags covers the long tail.
- **What to avoid for deterministic retrieval:** warehouse AI functions inline in agent queries (hidden model parameters, silent NULLs on failure, no determinism docs); embedding pre-filters for joins (independently lossy); and LIMIT/early-termination heuristics whose result set depends on processing order.

### Gaps
- No controlled study was found that measures agent task success under materialized vs query-time back ends on the same corpus. The recommendation rests on component-level evidence (accuracy of extract-then-filter, reuse savings, determinism studies), not an end-to-end agent benchmark.
- How often agent workloads actually repeat predicates (the reuse rate that decides when materialization pays off) is asserted qualitatively but not quantified in the sources found.
- Graph (Cypher) targets are rarely evaluated. Doc2DB-Bench's relationship tables are the closest proxy. Knowledge-graph construction is presumably covered by another track.
